# 变异测试实操经验

> 最后更新：2026-10-24
> 出处：change `minute-byte-column` apply 期间实跑 9 个新变异目标（全部 KILLED）
> 审计结论与变异点清单见 [`../UT-AUDIT.md`](../UT-AUDIT.md)；脚本 `scripts/mutation-test.py`。

## 1. runner 指向铁律：先确认它在测哪棵树

tstrun 反射 runner 位于 `%TEMP%/tstrun`，其 `ProjectReference` **硬编码主仓测试工程路径**。
在 worktree 里跑变异 = runner 编译运行的是主仓旧代码 = **变异全部假 SURVIVED**。
本次 3 条 SURVIVED 全部源于此，一度被误判为测试覆盖缺口。

- 在 worktree 跑变异前：把 runner 的 ProjectReference 临时改指向 worktree 测试工程，
  `dotnet restore` 后重跑；**跑完还原**并重新 restore，避免影响主仓后续使用。
- 甄别任何 SURVIVED 的第一步：确认 runner / 测试进程真的在测当前工作树，
  再分析「变异是否真的改了行为」——用探针打印中间状态，别只静态推理。

## 2. 回滚绝不用 git checkout

变异脚本的回滚若用 `git checkout -- <file>`，在**未提交的工作树**上会把该文件
**全部**未提交改动打回 HEAD。本次实测丢失两次改动，靠事先的 tar 备份救回。

现行安全做法（已落入 `scripts/mutation-test.py`）：

- 变异前在内存保存原文，跑完测试**原地写回**，全程不调 git。
- 读写按行尾归一化：工作树 CRLF、变异串按 LF 维护，
  「读入转 LF → 替换 → 写回转 CRLF」。
- 在未提交树上跑变异前，先 `tar czf` 备份全部改动文件作为兜底。

## 3. 行号型变异会漂移

`FilterEngine` 的 ApplyFilter 与 FilterTail 存在逐字符相同的代码块
（pid/tid 排除、分钟守卫），文本替换会匹配 2 处而被跳过，必须用
「行号 + 行内容片段」双重校验定位（脚本 `LINE_MUTATIONS`）。行号随引擎增删漂移：
本次 FilterEngine 六个锚点 254/261/268/325/330/335 → **263/270/277/332/337/342**。

- 双重校验让漂移变成**安全失败**（报 SKIP、不会误改代码），但会**静默漏掉**变异点。
- 改完引擎务必回来核对行号；最快的校验是把脚本**干跑**一遍——
  所有 TEXT 条目旧文本唯一命中、所有 LINE 条目行号 + 内容对得上。

## 4. 测试账目：属性数 ≠ 用例数

删改测试后对不齐数是常态。本次轨迹（`dotnet test` 实测）：
**663 → 673**（Groups 1-5 新增 10 条）→ **650**（Group 6 删年份机制套件，净删 23 条）。

- Theory 要按数据展开数：`[InlineData]` 一行一条，但 `[MemberData]` 一行可能展开多条，
  还有跳过 / 条件执行用例——**静态数属性永远对不齐实际运行数**
  （本次静态数 706 → 691，实际 663 → 650，两套数的差不是常数）。
- 唯一可信口径是 `dotnet test` 实际输出；对不上时先怀疑自己数错了，
  **不要改数字迁就脚本**。

## 5. 新变异目标的选取规律

本次新增的 9 个目标端到端实跑全部 KILLED，选题规律：

- **哨兵值与边界判定**（分钟列 255 → 0、无时间戳行存 0）——行为契约的骨架，
  改坏一个哨兵能同时抓显示 / 过滤 / 崩溃三处消费点。
- **集合成员判定**（ApplyFilter / FilterTail 两处哨兵守卫）——同构代码各打一条。
- **排序稳定性**（崩溃次数降序 + 首次行号升序、末次取行序最后）。
- 选取标准：该行坏了**测试必须红**；红不了说明契约没钉死，回去补测试，
  而不是把变异目标降级为「只影响性能」的对照组。
