# Bug 修复报告：空行导致崩溃堆栈行在打开文件时丢失

> **日期**：2026-10-14
> **状态**：修复方案已确认（方案 A），待实施
> **严重度**：中——低频、不可预期、不可恢复，丢失的恰是崩溃排查最关键的证据行

---

## 1. 现象

实时采集日志的过程中，崩溃堆栈显示是完整的。将同一个日志文件保存下来、事后重新打开，堆栈中偶有空行位置之后的若干行消失。

用户视角：采集时明明看着堆栈在，保存下来再打开，堆栈少了几行。没有任何报错——用户不会知道自己打开的这份文件缺了什么。

## 2. 影响范围

**受影响**：

- 打开本地日志文件（一次性全量读取路径）
- 丢失形态仅一种：多行记录（如崩溃堆栈）中间夹了空行，空行之后的缩进续行

**不受影响**：

- 实时采集路径——同样内容不丢（这正是「采集能看到、打开会丢」的原因）
- 不含空行的正常多行合并
- 崩溃事件的识别与摘要（按字节提取，与记录结构无关）
- 过滤、统计、列表显示（均读列存储，丢失发生在写入侧）

**频率**：对一份 1 GB 真实样本的统计，该形态约 21 处（约 0.02% 的行）。低频，但崩溃堆栈的 `Caused by:` 段之间、Dalvik 堆栈段之间偶发空行——丢的正是 triage 现场最关键的证据行。

## 3. 根因

日志记录不等于物理行：一条崩溃记录是「一条记录头 + 几十行缩进续行」，逻辑上算一条。读取器为此维护一个「续行合并」状态——遇到缩进行就并入上一条记录，直到遇见新的记录头。

「空行中断合并」是既定语义，但实现只切断了合并状态的一部分：空行之后的缩进行仍被判为「某条记录的续行」，而此时读取器认为本批次没有可并入的记录，于是把这行登记为「跨批次续行」，留给后续批次吸收。

问题就在这个「后续批次」：

- **实时采集**（增量读取）确实有后续批次 → 该行被吸收，保留；
- **打开文件**（一次性全量读取）没有后续批次 → 这个登记无人处理，该行被丢弃。

同一段字节，两条读取路径结论相反：一个保留、一个丢弃。这就是「采集能看到、打开会丢」的根源。

## 4. 实测证据

构造最小样本（记录头 + 空行 + 缩进堆栈行），同一字节、两种读入方式：

| 读入方式 | 结果 |
| --- | --- |
| 打开文件（全量） | 堆栈行**消失** |
| 实时采集（增量） | 堆栈行保留（并入上一条记录） |
| 对照组（无空行） | 两条路径一致，均合并 |

探针工程为仓库外临时工程，验证后已删除，未入库。

## 5. 修复方案（方案 A）

让空行真正「中断合并」：空行之后的缩进行不再被当作任何记录的续行，而是成为一条独立的记录（无时间戳、无级别的「未知」行形态——该形态早已存在，列表界面有对应处理）。

两条路径从此走同一判定、结论一致：内容不丢。

**为什么不选反向方案**（让打开文件路径也把缩进行吸收进上一条记录）：

- 那意味着已经显示出来的行事后被改写（行内容变长、过滤判定可能翻转），与「记录收完整再显示」的方向相反；
- 改动面大一个量级；
- 违背「空行中断合并」的既定语义。

**附带收益**：采集路径的「跨批次续行」命中减少，采集性能的相关触发面随之缩小。

## 6. 修复后的行为变化

| | 修复前 | 修复后 |
| --- | --- | --- |
| 打开文件 | 空行后的堆栈行消失 | 显示为独立行（无时间戳），内容不丢 |
| 实时采集 | 被吸收进上一条记录 | 同样显示为独立行 |

代价说明：这些行不再挂在原记录名下，而是独立显示。内容可见总比消失好——且「未知行」形态本就在既有支持范围内。

## 7. 测试计划

**新增**：

1. 空行后的缩进行成为独立记录（全量路径）
2. 同一数据「全量读入」与「增量读入」结果逐行一致（数据含空行场景）
3. 用例 2 的数据同时含横幅行，确保「横幅行不中断合并」的既有行为不漂移

**回归**（既有用例全量执行，不新增）：空行不进索引、追加纯空行、横幅行不打断合并、全量-增量等价性、崩溃提取全部用例。

## 8. 验收判据

1. 新增用例全绿；既有全部用例无新增失败。
2. 第 4 节探针场景复测：两条路径结论一致（独立记录、非合并行）。
3. 横幅行行为零变化（新增用例 + 既有护栏双保险）。
4. 采集路径探针：同样字节不再触发「跨批次续行」。

## 9. 不在本次修复范围

堆栈中间插入「带头部的其他日志行」时，堆栈后半段会挂到插入行名下——内容不丢，但原崩溃记录的行数统计少算后半段，界面上堆栈视觉断裂。

该形态的「堆栈尾归属」需要启发式判定（存在误并风险），留作后续设计。本次修复只保证：**内容不丢 + 两条路径结论一致**。
