## 现象

单实例互斥量使用 `Local\` 前缀，作用域是**每个 Windows 会话**而非整机。远程桌面多会话并发、快速切换用户（不注销切换账户）两种场景下，两个 Windows 会话可以各运行一个应用实例，互斥量互不感知，「已有实例运行时第二实例提示后退出」的承诺在这两种场景下不成立。

此时启动清理（暂存根目录全部子目录无时间阈值删除、只跳过本进程活跃集合）会把另一实例正在使用的暂存目录当作崩溃残留删掉：实例 B 启动的瞬间即删除实例 A 的活跃暂存目录。主规范「单实例守卫」需求把「单实例」写成「暂存启动清理安全的前提」，但该前提只在同会话内成立——跨会话并存时这个前提是破的，且无任何机制兜底。

危害窗口比「拉取进行中」更宽：spool 写盘期间暂存文件以排他共享打开、删不掉；**无保护窗口在「spool 完成 → 文档关闭」之间**——此时暂存文件已关闭、目录无任何保护，被删意味着代理文档的索引构建读不到文件或读到残缺内容（直接失败，或更坏地部分读到）。另有一个微秒级窗口在「暂存目录已创建、活性锁未创建」之间（修复方案 D3 处置）。

## 根因

1. 单实例互斥量 `Local\logcat-viewer-single-instance`（Services/SingleInstance.cs）：`Local\` 前缀 = 本会话范围。选 `Local\` 是 fileproxy change 的刻意决策（规避跨会话 DACL 坑，`Global\` 在提权/普通权限混用场景会让第二实例互斥量访问被拒），本身不是缺陷；缺陷在于把「暂存目录安全」建立在「互斥量覆盖所有并存实例」这个并未成立的前提上。
2. 启动清理 `CleanupStaleSpoolDirs`（Services/FileProxyService.cs）：跳过判据只有「本进程活跃集合」（`activeDirs` 参数），且入口程序启动时实际传参恒为 null——本进程启动时必然没有活跃目录，该判据在启动路径上从未生效，等价于「见目录就删」。
3. 暂存根目录固定在应用所在目录下（`temp\logcat-proxy`），同安装路径的所有会话实例共享同一个根——并存实例的目录天然混在同一根下。

触发场景（均不需要任何异常操作）：远程桌面多会话并发各开一个实例；或本机会话 A 开着应用、快速切换到用户 B 的会话再开一个。

## 为什么不是「设计接受的权衡」

fileproxy 立项时（design D13）的推理链是「单实例 ⇒ 残留必为死亡目录 ⇒ 无阈值全删安全」。该推理在**同会话**内成立，但互斥量的实际覆盖范围从未与推理前提对齐——spec 写了「本机」、实现是「本会话」。这不是新引入的风险，是 V0.1.5 发布即存在的潜伏缺陷：多 RDP 会话用户（或任何跨会话并存路径）在今天就可能丢失代理文档的暂存数据。

## 修复

新建 OpenSpec change `fix-spool-multisession`（已归档：`openspec/changes/archive/2026-10-18-fix-spool-multisession/`）：暂存目录活性锁——每个暂存子目录创建即持锁（目录内锁文件，`FileShare.Delete` 句柄），覆盖「创建 → 删除」全生命周期；启动清理对每个候选目录先做活性探测，被任何存活实例持有（含本实例）即跳过。暂存安全性从此与互斥量覆盖范围解耦；互斥量保持 `Local\` 不变，spec 措辞收敛为「本会话范围」，跨会话并存明确为设计容忍状态。

修复同时消灭一个双轨制：活性探测对「本进程自持锁」同样判定有主（Windows 文件共享校验按句柄、不按进程），现有 `activeDirs` 参数随之删除。

## 验证

- 自动化（随 change 实施）：`SpoolLivenessTests`（锁语义四边界：持有即跳过、释放即删除、无锁文件判无主、自持锁探测失败）、`SpoolCleanupTests`（判据改锁持有）、`LogDocumentProxiedTests`（Close 后释放）、`FileProxyLoopbackTests`（取消/短读无泄漏）；tstrun 全量口径数字随实施报告
- 维护者手工（先例：SingleInstanceTests 的真双进程冒烟）：双 RDP 会话并存，会话 A 打开代理文档后，会话 B 启动新实例——A 的文档不报错、暂存目录不被删；同会话第二实例仍即退
