# Design

## Context

- 动机见 `proposal.md` 的 Why；行为契约见 `specs/next/app-storage/spec.md`。
- 新壳现状（事实）：设置只有 `Lang` / `Theme` 两项，存应用目录旁的 `next-settings.json`；写入是整文件覆盖、非原子、无版本号、失败无留痕（`logcat-next/Next.App/Localization/NextSettingsStore.cs`）。语言与主题是两条独立的「读-改-写全文件」路径（`Next.App/Localization/LocalizationService.cs`、`Next.App/Views/MainWindow.axaml.cs`）。请求构造把临时目录与缓存目录都指向系统临时目录（`Next.App/ViewModels/MainViewModel.cs`）。
- core 侧：索引缓存的目录由宿主经请求 JSON 传入，容量上限、身份校验、LRU、损坏降级均由 core 实现并有规范覆盖（`crates/core/src/request.rs`、`crates/core/src/sidecar.rs`、`openspec/specs/logcore/source-acquire/spec.md`）。本 change 不改 core。
- 旧壳可参照的行为（不复制代码，新壳不引用旧工程）：exe 同目录三份配置、原子写、容错读、版本判定（`logcat-uicore/Services/SettingsIO.cs`、`logcat-viewer/Services/LogcatSettings.cs`）；旧壳索引缓存在自身应用目录下（`logcat-viewer/Services/SidecarCacheStore.cs`）。
- 约束：新壳不引用 `logcat-uicore` / `logcat-viewer`；不改 `crates/`；不接发布链；产物语言为简体中文。

## Goals / Non-Goals

**Goals:**

- 一个可测的持久化根解析器，启动时解析一次，设置、日志、缓存共用结果。
- 设置层具备版本锚点、原子写、单写入入口与失败降级，为后续加键留出迁移入口。
- 索引缓存从系统临时目录迁到持久目录，重开大文件有机会命中缓存。
- 持久化失败可查（最小诊断日志），且不打断任何功能。

**Non-Goals:**

- 不新增设置键（窗口几何、最近文件、字号、上次过滤条件均不在本轮）。
- 不改 core 的缓存内容格式、容量与淘汰规则，也不在宿主侧重写缓存逻辑。
- 不做设置界面（菜单项与现有交互不变）。
- 不做旧壳设置 / 旧壳缓存的迁移与清理（归将来的替换 change）。
- 不引入配置写锁或跨进程协商。

## Decisions

### D1：存储模块放在 `Next.App/Storage`，不新建工程

- **理由**：当前三工程的语义是「互操作 / UI / 测试」；存储不属于 C ABI，也还不到独立成型。`Next.Tests` 已引用 `Next.App`，可测性不受影响；将来拆分只是搬命名空间，成本低且可逆。
- **备选**：① 新建 `Next.Storage` 工程——现阶段只有一个 .NET 消费者，属提前抽象；② 放进 `Next.Interop`——破坏「唯一懂 C ABI」的边界；③ 静态类直接读 `AppContext.BaseDirectory`——只读分支无法自动化测试。
- **升级触发条件**（任一满足再拆工程）：出现第二个 .NET 宿主需要复用；模块文件数增长到约 5 个以上；需要不同的目标框架或裁剪配置。

### D2：可写根解析是纯函数，候选目录与探测函数都注入

- 解析器接收候选目录列表与「目录是否可写」的探测函数，返回不可变结果（根目录、设置目录、缓存目录、日志路径、是否仅会话内）。三种分支用假探测即可覆盖，不依赖真实 ACL。
- **理由**：`AppContext.BaseDirectory` 在测试进程内无法替换，把探测做成注入是唯一能让「不可写」分支可测的方式。
- **备选**：在解析器内直接 `File.WriteAllText` 探测——逻辑与副作用耦合，测试必须造只读目录，Windows 上受 ACL 与权限影响不稳定。

### D3：根内布局

```text
<持久化根>\
  next-settings.json     设置（带 SchemaVersion）
  next-startup.log       诊断日志（追加，不轮转）
  cache\core\            索引缓存（core sidecar，*.lcs）
```

- 缓存单独一层 `cache\core`：与旧查看器的缓存格式不兼容（旧为 C# 缓存，新为 core 的 `.lcs`），分目录避免混放。
- **备选**：缓存直接放根下——设置、日志、缓存混在一层，清理与排查都容易误伤。

### D4：设置模型与版本

- 设置对象带 `SchemaVersion`，当前值为 `1`。读取时：文件缺失、JSON 非法、版本不是 `1`，一律按「无设置」处理；未知键忽略（反序列化默认行为）。
- **理由**：版本位是将来加键与迁移的唯一入口；缺失版本（旧开发文件）按无设置处理，避免为未发布版本设计迁移。
- **代价**：开发者的 `next-settings.json` 会重置一次，接受。
- **备选**：把无版本文件当作 v1 读取——省一次重置，但会引入「同版本两种形态」的隐式约定。

### D5：设置采用原子写

- 写入同目录临时文件后整体替换目标文件（与旧壳 `SettingsIO.AtomicWrite` 同款思路），中途中断不会留下新旧混合。
- **理由**：整文件覆盖在断电 / 强杀时会留下半截 JSON；容错读会回默认，用户设置丢失。
- **备选**：写前备份 `.bak`——多一份残留，收益有限。

### D6：设置层只有一个写入入口

- 新增设置服务持有内存模型；语言与主题的修改都只改该模型并由它整体落盘。现有 `INextSettingsStore` 保留为测试缝（现有测试通过它注入假实现）。
- **理由**：现状两条路径各自「读-改-写」，加键后极易丢更新；单 owner 也让「保存失败仍当次生效」自然成立（内存模型一直是权威值）。
- **备选**：每次修改读取当前文件再合并——多一次 IO，且并发写仍会互相覆盖。

### D7：诊断日志最小实现

- 追加写入 `<持久化根>\next-startup.log`，记录启动（版本、根目录、是否仅会话内）与持久化失败；写入失败吞异常，不再尝试。
- **理由**：设置与缓存的静默降级必须可查；新壳日志点极少，单文件足够。
- **备选**：按日期分文件 + 大小上限——当前无需求，等日志点变多再升级。

### D8：缓存目录接入点

- 请求构造把 `options.sidecar.dir` 改为 `<持久化根>\cache\core`；持久化根不可用（仅会话内）时退回系统临时目录下的应用子目录，不承诺跨重启命中。目录创建、容量与淘汰、损坏降级全部交给 core。
- **理由**：core 已有完整缓存契约，宿主只负责「把目录指到哪里」；重复实现缓存治理会产生两套事实。
- **备选**：宿主自行管理缓存目录与清理——与 core 契约重叠，且跨进程在用判定无法在宿主侧做对。

### D9：临时目录保持系统临时目录

- `options.tempDir` 继续指向系统临时目录下的应用子目录，不跟持久化根。
- **理由**：采集与暂存产物按定义可丢；放进持久化根会制造无法自动回收的垃圾。

### D10：探测实现与初始化时机

- 探测 = 在目标目录创建一个临时文件后删除；异常一律视为不可写。
- 解析在 `Program.Main` 内、Avalonia 启动前完成一次，结果放入应用级静态入口，供 `App`、设置服务、日志与请求构造使用。
- **理由**：启动早期就需要日志与设置；放在 `App.OnFrameworkInitializationCompleted` 会让启动阶段的失败无处记录。
- **备选**：懒加载单例——首次访问时机不确定，日志可能晚于需要它的失败。

### D11：测试策略

- 假探测覆盖三种分支（应用目录可写 / 回退用户目录 / 全不可写）；真探测只测可写正路径，避免 Windows ACL 依赖。
- 设置测试用临时目录：往返读写、损坏回默认、版本不识别回默认、临时文件残留不生效、保存失败不抛、语言与主题互不覆盖。
- 请求构造测试断言 JSON 中 `sidecar.dir` 与 `tempDir` 各自指向预期目录。
- 约束测试：源码扫描断言 `AppContext.BaseDirectory` 只出现在存储模块，防止后续切片绕过解析器。

## Risks / Trade-offs

- **多用户共享应用目录** → 接受（语言/主题被同机用户共享）；装在受保护目录时本就不可写，会走用户目录。
- **用户应用数据目录也可能被安全软件拒写** → 回退链末端为「仅会话内」，仅日志留痕，不弹窗。
- **只读目录分支只能靠假探测验证** → 真探测只测正路径；集成风险由手测（只读目录部署）覆盖。
- **每次设置变更整文件写** → 低频、体积小，可接受；若将来键面变大再评估。
- **设置文件无历史版本迁移** → 首次运行会重置一次开发设置，接受。
- **会话内模式下缓存退到临时目录** → 重启不命中，符合降级语义，但性能会回到全量解析。
- **SMB 源文件的缓存命中收益未实测** → 记为待实测，不阻塞本轮正确性。

## Migration Plan

- 无外部用户：新壳未发布。设置文件首次以 `SchemaVersion = 1` 写入；已存在的无版本文件按无设置处理（开发环境语言 / 主题重置一次）。
- 回滚：删除存储模块、把请求中的缓存目录改回系统临时目录即可，不涉及数据格式兼容问题。

## Open Questions

- SMB 源文件的冷 / 热重开耗时是否满足「亚秒重开」目标（需实测后决定是否调整目录策略或容量参数）。
- 诊断日志是否需要体积上限与轮转（取决于后续日志点数量）。
