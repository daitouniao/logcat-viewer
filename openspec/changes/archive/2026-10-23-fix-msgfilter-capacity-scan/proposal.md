# Proposal

## Why

打开网络驱动器上的日志文件后，每次修改 message 过滤关键字都要约 1.7 s（用户现场 176 MB / 140 万行）或 12~17 s（复现环境 176 MB / 272 万行），本地文件同样慢。探索已定稿根因（见 `openspec/notes/NETWORK-FILE-FILTER-PERF.md`）：与网络完全无关，是 message 大小写不敏感过滤路径按「缓冲区容量」而非「行内字节」逐行扫描的 CPU 侧缺陷——主因是每行遍历整个 scratch 容量（最大 8 KB），次因是残留字节污染导致 Unicode 回退率从数据下限 10.8% 抬到 27.4%。修复面极小（一处折叠函数 + 一处调用点），实测修复形态 17.4 s → 0.5 s，命中数不变。

## What Changes

- 修复：message 大小写不敏感过滤的大小写折叠判定改为只扫描当前行自身字节（切片折叠），消除「按缓冲区容量逐行全量扫描」与「残留字节污染回退判定」两层缺陷。
- 可观测行为不变：命中数、过滤语义（含非 ASCII 行的 Unicode 回退路径）在全部对照实验中全等；只改变扫描的字节量与回退触发率。
- 新增 G′ 对照实验（探针口径）：把「容量扫描是主因」从反算坐实为实测，作为修复前的基线留证。
- 新增回归测试：钉死「每行只扫自身字节」不变式 + 折叠函数直测。

非目标（out of scope）：

- 不做「删除 scratch、对消息缓冲原地折叠」的备选形态（方案 2）——核查无破坏面，记为可选后续优化另议。
- 不给 scratch 设容量上限、不加超长行特殊处理——修复后单行成本与容量无关。
- 不改 `LogDocument.Build` 索引扫描（27~29 s 是独立问题，不在本根因范围）。
- 不做网络文件本地缓存、块读等 IO 侧优化——已证实瓶颈不在传输。
- 不改 BATCH 分批、进度上报、取消检查——实测均不是瓶颈。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

（无）——本修复不改变任何系统级可观测行为，`.openspec.yaml` 已声明 `skip_specs: true`。

## Impact

- 影响代码：`Services/FilterEngine.cs` 的 message 大小写不敏感过滤路径（折叠函数及其唯一调用点），约 2 处改动。
- 测试面：`tests/logcat.Tests/` 新增折叠函数直测与扫描字节计数断言（工程已配 `InternalsVisibleTo`，需将折叠函数从 private 放宽为 internal）。
- 用户可感收益：网络/本地大文件的 message 忽略大小写过滤从秒级（1.7~17.4 s）回到亚秒级（0.1~0.5 s 量级）；大小写敏感路径与 tag 过滤不受影响（本就不走该路径）。
- 无 API、数据模型、依赖、UI 变化。
