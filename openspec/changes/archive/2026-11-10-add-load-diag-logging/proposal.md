# Proposal

## Why

V0.1.9 上出现「第一个文件加载完、过滤完成后再拖入新文件，列表偶发空白」：滚动条仍在（行已进视图）、清空过滤条件依旧空白、拖动滚动条或重载后才恢复。

现有 `Log` 目录下的启动日志只记录窗口几何、DPI、缓存命中/失败等零散事件，缺少「打开链路 → 过滤分支 → 视图绑定」三者的时序。结果就是现场只能靠用户回忆状态栏数字、操作顺序和试错，排查已经卡住两轮。先把这条链路留痕，发版后由用户复现一次，把「命中 0（条件把内容滤光）/ 解析 0 行 / 加载被中止 / 行有但未绑定或未重绘」四类一次性分开，再据实修根因。

## What Changes

- 新增**打开链路轨迹**（单次打开约 10 行）：入口（路径、大小、代理模式、代际、进入时的加载标志）、分流（缓存命中及其行数 / 进入分块编排）、分块发布（节流记录：每块终止行号、本轮命中、累计命中、过滤条件摘要）、收尾（完成与否、代际是否匹配、取消清理是否执行、加载标志最终值）、视图接管（成功 / 跳过及跳过原因）。
- 新增**过滤分支记录**：每次过滤落在四个出口中的哪一个（加载中 / 无文档 / 代际不匹配 / 正常执行）及其代际值，用于判别「过滤没生效」与「过滤后为空」。
- 新增**视图一致性自检**：当「视图行数 > 0 而文档未绑定 / 绑定与当前文档不一致」时，记录现场（视图行数、绑定是否为空、文档行数、视口顶行、首条可见行解码出的字符数）。该记录仅在异常条件成立时写，常态零噪声。
- 诊断记录统一写入既有的启动日志文件（exe 同级 `Log` 目录），不新增依赖、不新增开关、不改任何控制流与用户可见行为。
- 明确**日志分级**：入口 / 分流 / 收尾 / 接管 / 过滤出口 / 视图自检为**常驻**；逐块发布明细为**临时**（根因定案后单独删除，不在本 change 内删）。

**非目标（out of scope）**

- 不修根因：空白本身、加载中断后加载标志不复位、缓存命中路径收尾被跳过等缺陷，另按 bug 修复流程处理，不在本 change 内改行为。
- 不新增设置项、开关、日志级别 UI；不做日志轮转、压缩、清理策略。
- 不改过滤、分块加载、缓存、文件代理的任何行为或性能契约。
- 不引入第三方日志框架。

## Capabilities

### New Capabilities

- `load-diagnostics`: 「打开链路与视图状态的诊断记录」这一系统行为——哪些事件必须留痕、记录落在哪、写入失败时如何降级、视图一致性异常的判定条件与现场字段。

### Modified Capabilities

（无。过滤与分块加载的行为契约不变，本 change 只增加记录。）

## Impact

- 代码：查看器主窗体的打开/加载编排与过滤编排、状态栏统计刷新、缓存接管路径，以及启动日志工具（多线程并发追加的可靠性）。
- 运行时：少量文件追加写；加载期每块一行，1 GB 量级文件仍只有几十行。
- 用户可见：`Log` 目录下日志内容变多；无 UI 变化、无设置项、无行为变化。
- 测试：为「视图自检判据」与「日志并发写入不抛异常」补单元测试。
- 发布：诊断包需随版本发布后由用户复现取log；临时逐块日志的删除时机记在 tasks 中。
