# Design

## Context

见 `proposal.md` - Why。影响设计取向的既有事实（均已读码确认）：

- 日志载体已存在：`StartupLog` 追加写「exe 同级 `Log` 目录、带毫秒时间戳、异常全吞」，窗口几何、DPI、缓存命中/失败都走它。
- 一次打开由三段串起来：入口（停采集、换代、关旧文档）→ 装载（缓存装配 / 分块渐进）→ 收尾（接管视图、刷新统计）。三段分居不同方法，靠「代际序号」判失效。
- 视图行与文档绑定由同一控件持有：换文档必清行，改行必不动绑定；两处各有一把锁/一个代际门禁，但**没有任何一处校验「行有了、绑定对不对」**。
- 统计栏刷新（`UpdateStat`）是所有上屏路径的汇聚点：分块发布落地、过滤完成、缓存接管都会经过它。
- 装载期存在两个线程：界面线程消费发布缓冲，后台装载线程产生发布操作；现有多数日志只从界面线程写。

## Goals / Non-Goals

**Goals:**

- 一次用户复现即可判别四类结局：条件把内容滤光 / 解析出 0 行 / 装载被中止 / 行有但视图未绑定或未重绘。
- 记录可直接按「一次打开」为单位串起来读（同一代际序号贯穿入口、装载、接管、过滤）。
- 常驻记录零噪声（异常才写）；临时记录可整体识别、整体删除。
- 不加开关、不加依赖、不改任何控制流。

**Non-Goals:**

- 不修任何缺陷（空白本身、加载中断后标志不复位、缓存命中路径收尾被跳过）。
- 不做日志轮转 / 采样率 / 级别配置 / 远程上报。
- 不把诊断信息暴露到界面（不新增状态栏提示、不弹窗）。

## Decisions

### D1 载体：复用既有启动日志，不新建日志文件、不引入日志框架

理由：用户已知位置、Release 也生效、异常已全吞；新建独立文件要带来「开关 / 轮转 / 位置」三件套，全是本次不需要的复杂度。备选及否决理由：调试输出（用户取不到）、第三方日志库（新增依赖，违背最小改动）、独立诊断文件（要额外开关与清理策略）。

### D2 记录按前缀分类，临时记录只占一个前缀

| 前缀 | 类别 | 生命周期 |
| --- | --- | --- |
| `[Open]` | 入口、分流、代际、进入时状态 | 常驻 |
| `[Load]` | 收尾结论、视图接管结论 | 常驻 |
| `[Filter]` | 过滤四出口与命中行数 | 常驻 |
| `[View]` | 视图一致性现场快照 | 常驻（条件成立才写） |
| `[Chunk]` | 逐块发布明细 | **临时**，根因定案后整体删除 |

理由：「删临时记录」只要删一个前缀的写入点，不触碰常驻判读逻辑（对应 spec「常驻记录与临时记录可区分」）。逐块明细单独占前缀，是因为它是唯一按块产生的记录，也是唯一可能显著增加行数的一类。

### D3 所有记录带代际序号，且条件摘要只记结构不记原文

- 每行带 `gen=<代际>`：本案的核心不确定性就是「谁被谁抢占、谁放弃」，没有代际就无法把多段日志串成一次会话。
- 过滤条件记录**结构**（级别是否收窄、各类条件条目数、大小写/排除/与或开关、仅标记行开关），不记关键词原文。理由：① 判读只需要知道「有没有条件、条件形状」，不需要原文；② 日志常被粘贴进 issue，原文会带出用户日志里的关键词，可避免泄露；③ 现成的条件摘要文案随界面语言变化，跨语言环境不可检索，结构字段是语言中性的。

### D4 视图自检挂在统计刷新点，用去重键防刷屏

判据两条：视图行数 > 0 且绑定为空；视图行数 > 0 且绑定不是当前文档。落点选统计刷新（所有上屏路径的汇聚点），不放在控件内部（控件层不该依赖日志），也不放在换文档处（那里必然一致，测不到错位）。

去重键 =（代际，视图行数，绑定状态类别）。理由：条件成立时每 100 ms 就会刷新一次统计，不去重会在装载期刷出成百上千行；按三元组去重后，同一现场只记一次，状态继续变化（行数增长、绑定变化）才会再记一条。

现场字段：视图行数、绑定状态（空 / 异文档 / 同文档）、当前文档行数、视口顶行、首条可见行解码字符数。最后一项的作用是把「没画出来」和「解不出字（空文本）」分开。

判据与去重键抽成**纯函数**（输入：视图行数、绑定标识、当前文档标识、上一记录键；输出：是否记录 + 字段串），便于单测覆盖「不一致即记录 / 一致不记录 / 同一现场只记一次」三条结论，避免把可测逻辑埋在窗体里。

### D5 启动日志内部加锁，保证并发下单行完整

现状是每次追加直接 `File.AppendAllText`，本次会引入后台线程的逐块写入，与界面线程并发时会撞文件占用，异常被吞即丢行，严重时出现半行拼接。决定在写入口加进程内静态锁，串行化「格式化 + 追加」这一段；锁内只有一次短追加，开销可忽略，也不改变任何调用方语义。备选：单写线程队列（过度设计）、按线程分文件（用户取 log 要拼多个文件，判读更差）。

### D6 逐块记录只记三个数

每块一行：块终止行号、本轮命中数、累计命中数。理由：够判「块在推进」「过滤是否吃掉全部行」「累计命中与最终视图行数是否一致」；记每行会爆量。

### D7 插入点纪律：只读局部变量，不调整时序

所有记录点只允许「读已有局部变量 / 已有字段 + 写日志」，禁止为了打日志改动 `await` 顺序、加锁范围或提前赋值。理由：诊断代码若改变时序，会掩盖或制造本案正在追的竞态，得不偿失。

### D8 记录字段清单（实现与判读对齐用）

| 前缀 | 必含字段 |
| --- | --- |
| `[Open]` | `path`、`size`、`gen`、代理模式、进入时 `loading`/`hasDoc`、分流结论（缓存命中及其文档行数 / 进分块） |
| `[Load]` | `gen`、`completed`、收尾清理是否执行、收尾后 `loading`、最终 `docRows`/`viewRows`/`bound` |
| `[View]` | `gen`、`viewRows`、`bound`（none/other/same）、`docRows`、`topModelRow`、`firstRowChars` |
| `[Filter]` | `gen`、出口（loading/docNull/staleGen/normal）、`hitRows`（仅 normal）、条件结构摘要 |
| `[Chunk]` | `gen`、`to`、`hitInChunk`、`hitTotal` |

## Risks / Trade-offs

- [日志体积增长] → 单次打开约 10 行常驻 + 数十行临时；1 GB 文件仍只有几十行。逐块记录列入临时类别，定案后删除。
- [日志含本机文件路径] → 属功能所需（红线针对的是入库文档硬编码路径，运行期记录用户实际路径不在其中）；proposal 已声明非目标不含脱敏，实施后在交付说明中提醒「分享前自查」。
- [`[View]` 自检刷屏] → D4 的三元组去重键；若实测仍刷，退化为「每代最多 N 条」。
- [并发锁引入阻塞] → 锁内只有一次文件追加；与既有日志行为同一风险面（日志目录若在网络盘，既有代码已有相同耗时特征），不新增风险类别。
- [后台线程写日志影响装载吞吐] → 每块一行，文本格式化开销相对 32 MB 块的解析可忽略；不引入字符串拼接的大对象（单行长度受控）。
- [诊断代码成为新竞态源] → D7 纪律 + 实施时逐点 review；任何需要改变时序才能取到的信息，改为不记。
- [临时记录忘记删] → tasks 中显式登记「根因定案后另立删除动作」，本期不删；spec 已要求前缀可整体识别。

## Migration Plan

无数据迁移、无状态变更。发布后用户在发布包上复现一次并回收 `Log` 目录日志；若某类记录判读价值低于噪声，单独删该前缀即可回滚。
