# Design

## Context

关闭主窗口的当前流程（`frmMain.OnFormClosing`）：停 worker → 同步等待采集停止（上限 2 s）→ 同步等待文档互斥（上限 2 s）→ 保存设置 → 关闭文档映射 → 杀掉拉起的代理进程 → 交给基类销毁窗体。

列表控件是虚拟模式：行号保存在分段数组里，不持有行对象；但销毁窗口句柄时 WinForms 释放无障碍（UIA）provider 会**逐项枚举**列表行并回调逐行构造行对象。抓到的运行时栈（关闭大文件后、窗口消失约 1.4 s 时采样）：

```
logcat.Controls.LogListView.MakeItem(int32)
System.Windows.Forms.ListView+ListViewNativeItemCollection.GetItemByIndexInternal
System.Windows.Forms.ListView.ReleaseUiaProvider(HWND)
System.Windows.Forms.Control.WmDestroy
System.Windows.Forms.Control.Dispose(bool)
System.Windows.Forms.Form.Dispose(bool)
System.Windows.Forms.Form.WmClose
System.Windows.Forms.Application.Run
logcat.Program.Main
```

此时文档映射已被前面的关闭流程释放，逐行构造读正文只能落到异常兜底，单行成本进一步放大。

实测对照（同一台机器、同一发布版本）：

| 场景 | 关窗到进程退出 |
|---|---|
| 未打开文件（视图 0 行） | 73 / 77 / 111 ms |
| 184 MB 文件（百万量级行；按平均行长估算，未逐行统计） | 4.53 / 8.74 / 9.81 s |

耗时与视图行数近似线性，与磁盘、映射释放、ADB 采集无关（后三者均已单独排除）。

## Goals / Non-Goals

**Goals:**

- 关窗耗时与视图行数解耦，百万行与空视图同量级。
- 关闭顺序上消除「文档已释放、视图仍在逐行读正文」的组合。
- 用可自动化断言的行为测试锁住回归，不依赖计时。

**Non-Goals:**

- 不处理加载 worker 与文档关闭的并发竞态（关窗只取消不等待）。
- 不处理关闭流程中两处「UI 线程同步等待 async」的固定 2 秒上限。
- 不更换列表控件实现。

## Decisions

### D1 关闭流程开头先清空视图行数据，而不是改销毁路径

复用列表控件既有的「切换文档」清空语义：清行号分段、行数归零、清渲染缓存。销毁时枚举依据（行数）为 0，逐行构造不再发生。

备选与取舍：

- **仅解绑逐行构造回调**：枚举仍会按行数跑一遍，虽然每行快速返回，但百万行的空转仍不是零成本；不如行数归零彻底。
- **改自绘 / 换控件**：成本远高于收益，且会牵动现有渲染与选中逻辑。
- **在窗体销毁阶段拦截**：销毁由 WinForms 内部控制，只能靠覆写窗口过程，脆弱且难测试。

### D2 清空必须发生在文档关闭之前

若先释放文档映射再清空视图，中间窗口内仍可能被枚举，逐行读正文又会撞上已释放资源（异常兜底或更坏）。顺序固定为：清空视图 → 释放文档。

### D3 清空与停 worker 同批，并顺手断开加载期发布缓冲

关窗第一步已是停 worker（取消 + 代际递增），清空紧接其后。同时清掉加载期发布缓冲引用：代际守卫已能挡住绝大部分残留发布，但清空后不应存在任何把行加回视图的路径，双保险更可靠。

### D4 抽一个 internal 的关闭前清理方法供测试直接驱动

沿用项目已有做法（取消清空路径已从异步收尾中抽成 internal 方法供单测直接驱动）。关闭流程只多一行调用，测试可直接调用该方法，不依赖消息循环时序。

### D5 回归测试断言「行为」而非「耗时」

CI 机器噪声下计时断言不稳定。测试改为：给视图装入大量行并统计逐行构造回调次数 → 执行关闭前清理 → 触发窗体销毁 → 断言行数归零且销毁期间回调次数不再增长。耗时验收放到手动端到端复测（D6）。

### D6 端到端复测用一次性探针，不进产品代码

用后台脚本监控进程：窗口句柄消失时刻 → 进程退出时刻，差值即关窗耗时；与修复前基线（同文件 9.81 s）对比。探针不落仓库、不改产品代码，复测后清理。

### D7 规划文档与归档留在 master，代码修改在 V0.1.8

本 change 属 V0.1.8 预发布分支的 bug 修复。规划文档与归档放 master（规范主线的归宿），修复代码在 `V0.1.8` 分支的 worktree 中直接实施并提交，不新建 `wt/` 分支——沿用 `fix-chunked-final-flush` 于 2026-11-05 由用户指令确定的改道方案。

理由：V0.1.8 分支按版本生命周期会在稳定版发布后删除；若 change 与 `app-shutdown` spec 只存在于该分支，规范沉淀会随分支消失。上一轮先例已用同一结构（master 归档、V0.1.8 承载代码）验证可行。

备选与取舍：

- **`wt/fix-close-dispose-slow` 分支合入 V0.1.8**（AGENTS.md §2.3 的字面约定）：代码路径多一次合并，且 spec 沉淀仍会随分支删除丢失；本次明确不采用。
- **change 放 V0.1.8 分支**：本次已尝试后回退（规划文档曾建在该分支 worktree，确认分支归宿问题后迁到 master）。

## Risks / Trade-offs

- **关窗瞬间列表变空白** → 窗口已在销毁过程中，用户不可见；且当前关闭流程没有取消关闭（`e.Cancel`）的分支，不存在「取消后视图已被清空」的状态。
- **残留异步发布把行加回视图** → 代际守卫 + 关闭时清发布缓冲引用，双保险；测试覆盖「清理后不重新出现行」。
- **结论绑定 WinForms 无障碍 provider 的销毁行为** → 未来若更换控件或关闭无障碍支持，该结论需重估；回归测试（行构造回调计数）会先亮红灯。
- **耗时断言不进 CI** → 避免噪声翻车，但意味着性能回归只能靠人工复测发现；用 D5 的行为断言兜住根因层面的回归。
- **代码与文档分居两个分支** → 需要在两处分别提交与核对（D7）；tasks 3.2 以「两处 git 状态干净」作为验证口径。
