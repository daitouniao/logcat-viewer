# Design：设备文件传输的进度可观测性与传输后一致性

动机与范围见 proposal.md，行为契约见 specs/device-file-transfer/spec.md。本文只写实现层面的决策、理由与接入点。

## Context

现状关键事实（均已代码核实；行号为 2026-10-21 评审时点快照，随演进可能漂移，以符号名为准）：

- **进度条不是没有，是全程停在空档**。文件浏览对话框底部操作栏有一条 `ProgressBar`（Forms/FileBrowserDialog.cs:100-109），传输编排 `RunTransferAsync`（:224）里 `Maximum = files.Count`（:264），但更新点写在每个文件**开始之前**且值是「已完成数」（`_pbar.Value = ok + failed`，:271）——单文件传输时 `Maximum=1 / Value=0`，填充比恒为 0，肉眼一条空条；多文件最高停在 `(N-1)/N`，100% 那一帧从不渲染，`finally` 直接隐藏（:310-316）。用户描述的「进度没有显示」与此完全吻合。
- **字节维度没有观测点**。设备管理层 `Pull/Push`（Services/AdbManager.cs:387-418）是 `Task.Run` 一刀切，同步通道的进度回调形参留空；上层设备文件面板的上传/下载方法（Controls/DeviceFilePane.cs:545-619）同样是一串 `await`，无进度形参。
- **但字节回调是现成的**。实测反射（AdvancedSharpAdbClient 3.6.16，`SyncService`）：`Push/Pull/PushAsync/PullAsync` 均带 `Action<SyncProgressChangedEventArgs>` 形参，回调参数公开 `ReceivedBytesSize` / `TotalBytesToReceive` / `ProgressPercentage`；同步版另有 `ref bool isCancelled`。**不需要换库、不需要自造分块协议**。
- **中转路径是一条多步流水线**，只有一步落在字节通道内。提权中转（root / run-as 且目标非 `/sdcard` 系）时，单个文件依次经过：查属主 → 建目录 → **推送到中转目录（唯一有字节回调的一步）** → 设备端拷贝到最终路径 → 放开读权限 → 改属主 → 删中转文件 → 刷盘（`DeviceFilePane.SyncAsync`，超时 120s，失败静默）。其中「设备端拷贝」是真实 I/O 但同样没有字节回调。
- **刷新已经接线，只是覆盖不全**。`RunTransferAsync` 尾部会刷目标栏当前目录（:302-303，上传刷设备栏、下载刷本机栏）；未覆盖的是：展开后无可传输文件（:255-262 直接返回）、外层异常（:305-309），以及目标落在子目录时当前视图里根本没有新文件。
- **本机内复制与设备传输共用同一条进度条，但只有设备传输设了闸门**。`CopyLocalFilesAsync`（:319-364）既不设占用标志、也不禁用按钮、进度条还没有 try/finally —— 两者并发时抢同一条条，异常时条会永久残留。
- **传输不可取消**：`CancelLoading()` 只取消目录列举；传输中关窗按 `OnFormClosing`（:398-406）弹「请等待完成后再关闭」。
- **项目已有进度范式可抄**：`IProgress<(double pct, string msg)>` + `new Progress<...>` 回调落 UI 线程（frmMain.cs:1403 等多处），无需发明新类型。
- **i18n 铁律**：控件文本必须 `Loc.Bind(ctrl, key)`（键=中文原文）、禁前缀拼接要走 `Loc.F()`；传输中的「序号/文件名」当前是硬编码插值（:272、:342），未走资源键。

## Goals / Non-Goals

**Goals：**

- 传输期间给出**真实**进展：字节百分比 + 非字节阶段的不确定态，两者都不撒谎
- 传输结束后界面状态与实际落盘一致：目标栏刷新、落点明确、进度条以满格收尾
- 对既有传输链路最小侵入：只加进度传参与 UI 呈现，不动权限与中转策略
- 进度映射逻辑可单测（口径为仓库内 tstrun 反射 runner）

**Non-Goals：**

- 取消能力（拍板不做）：不加快照按钮，不定义「取消到一半的落盘文件」语义
- 速率指标：不显示速度与剩余时间
- APK 安装/卸载的进度（另一处界面）
- 目录记忆策略（按设备记忆目录是独立议题）
- 传输通道的协议与权限模型变更

## Decisions

### D1 字节进度直接取用 ADB 同步通道自带的回调

接上同步通道已有的字节回调（`ReceivedBytesSize` / `TotalBytesToReceive` / `ProgressPercentage`），不自造分块协议。

**理由**：回调是库已提供的形参，接线成本是「传一个委托」；替代方案里，自行分块推送意味着自己实现 sync 协议（成本与风险都远超本 change）；用本地文件句柄位置估算拿不到设备端真实字节；走本项目的代理通道也不成立——那条通道是给**本机**受限日志文件用的，与设备侧传输无关。

### D2 进度模型 = 本次传输的总字节百分比

一次传输涉及多个文件时，进度条显示「已传总字节 / 全部文件总字节」，文件个数只出现在状态文案里。

**理由**：按文件个数折算会严重误导（1 个 1GB + 9 个 1KB 的集合，按个数走完前 90% 的条其实只传了 1KB）。总量在传输前可算清：上传侧取本机文件长度，下载侧取设备目录列表里已显示的大小。

**备选**：每个文件一条独立百分比（要在同一行里塞多行进度，与现有底栏单条布局不合，且用户看不出整体）；按文件个数折算（即现状）——否。

### D3 非字节阶段 = 控件原生不确定态（marquee），不造假权重

进度条的「样式」在不确定态（持续滚动）与确定态（显示百分比）之间切换：进入字节阶段切确定态并显示真实百分比，离开则切回不确定态。同期状态栏给出当前动作的具体说明。

**理由**：这一段只有耗时、没有字节概念，任何百分比都是编的。项目对「静态文案 + 静止进度条」的组合本来就敏感（代理能力的规范里明写禁止静止进度条配静态文案），不确定态是唯一既诚实又不打断操作的表达。控件原生支持该样式，实现成本最低。

**备选**：完全不表达（条静止）——用户在最需要"还活着"信号的阶段得不到反馈；按经验分配权重（准备 10% / 传输 60% / 收尾 30%）——权重是拍的，与真实字节脱钩；**两者均否**。

### D4 阶段边界按「是否落在字节通道内」划分

- 直连路径（同步通道可直达的目录前缀）：全程确定态，无阶段文案
- 中转路径：**准备**（查属主、建目录）→ **字节**（推/拉中转文件）→ **收尾**（设备端拷贝、放开读权限、改属主、删中转文件、刷盘）

**理由**：分界线必须是「有没有字节可报」，而不是「步骤好不好看」。「设备端拷贝」容易被误归到字节阶段——它其实是设备侧 shell 往返，库里回调覆盖不到，归错会让条在长耗时段静止。

### D5 进度传参沿用项目既有 `IProgress<(double pct, string msg)>` 范式

传输链路各层以 `IProgress<(double, string)>` 传进度，UI 侧用 `new Progress<...>` 消费。

**理由**：项目已有同形状的进度范式（文档装载、过滤、代理拉取都在用），不发明新类型；`Progress<T>` 依赖同步上下文回到 UI 线程，天然规避跨线程更新控件。

**注意**：同步通道的回调是同步版 API 上的 `Action<>`，需要在自己的委托里转成 `IProgress` 上报，避免把库的回调直接暴露到 UI 层。

### D6 不为同步通道调用加注入缝，改用纯函数单测

把「字节数 → 百分比」的映射抽成纯函数（含总字节为 0、进度回退、越界三类边界），单测覆盖它；不为「让库对象可替换」而改造生产路径。

**理由**：真正有逻辑的就是这个映射，库内部是协议实现、无业务分支；而给同步通道加缝会新增生产面复杂度、收益低。真机端到端验证由手工验收承担（本 change 不引入对设备的外挂自动化）。编排层用例（阶段序列、互斥拒绝、空集刷新）的可测性未经证实：apply 首步先立探针验证 tstrun 能否实例化并驱动对话框/面板，测不动则该组降级为手工验收并回写 tasks。

### D7 刷新统一在传输收尾处调用，并补齐三条路径

传输成功、传输异常、无可传输文件三条路径都刷新目标栏当前目录；刷新发生在结果提示之后，保证用户看到的顺序是「先告诉结果、再看到列表」。

**理由**：现状刷新机制已在（面板侧有现成的刷新入口），缺的只是覆盖面；沿用既有入口不引入新机制。

### D8 落点告知：目标目录 ≠ 当前目录时，状态栏说明落点

拖放到子目录项上时，传输落点是该子目录；此时当前视图里不会出现新文件，必须显式说明落点路径，否则「刷新了却看不到」会被读成「没刷新」。

### D9 互斥闸门扩展到本机内复制

占用闸门从「仅设备传输」扩为「设备传输 + 本机内复制」共用，两者在同一窗口内互斥；闸门是窗口内状态，不是全局单例。进度条的显示/隐藏统一收口到闸门的进入/退出，异常路径也保证收起。

**理由**：两者共用同一条进度指示，不互斥就会互相改写条的值与文案；进度条生命周期不收口，异常时条会永久留在界面上（现状即有此隐患）。

### D10 i18n：新增文案键入文件面板的文案表，传输中文案改用 `Loc.F`

传输中的「序号/总数 + 文件名」、阶段动作说明、结果统计、落点告知全部走资源键；新增键统一放进文件面板所属的文案表分片。

**理由**：项目 i18n 铁律要求用户可见文本以中文原文为键；文案表有扫描型守卫测试，新增键必须同步进表，否则守卫会报缺译文。

## Risks / Trade-offs

- **字节回调上报频繁，UI 线程更新过密** → 上报侧做节流：百分比变化不足一定幅度或时间间隔不足时不刷新控件（只更新内存里的最新值），避免大文件传输时界面卡顿
- **某些设备/协议组合下字节回调不触发** → 降级为不确定态（规范已覆盖「字节维度不可得不冒充」），不显示百分比
- **多文件总量算不准**（设备端文件大小未知或为 0） → 分母不可信时退回不确定态，而不是显示一个错的百分比
- **进度条在嵌入页签 + 高 DPI 下可能被裁** → 沿用现有布局与 DPI 兜底机制（显示后按内容实测撑开），不改布局策略
- **传输中切换界面语言** → 文案随语言重算；进度数值本身与语言无关
- **进度条终态改为满格后，用户可能误以为全部成功** → 结果提示仍分别给出成功/失败数量，进度条只表达"传输已结束"

## Migration Plan

- 无数据迁移、无配置项变更
- 用户可见变化：进度条形态（文件计数 → 百分比 / 不确定态）、传输中文案国际化、传输后列表刷新更及时
- 回滚策略：改动集中在传输编排与进度传参两层，回退即恢复现状行为；不涉及数据与协议

## Open Questions

无。唯一可能后移的细节（多文件总量不可信时的呈现）已在规范中定死为不确定态，不改变方案与任务拆分。
