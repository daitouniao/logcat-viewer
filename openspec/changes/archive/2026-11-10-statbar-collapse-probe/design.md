# Design

## Context

动机见 proposal.md「Why」。这里只记影响做法的现状事实（均已在本仓库代码中核对）：

1. 统计区是 `ToolStripStatusLabel`（`AutoSize=false`），尺寸由 `StatusStrip` 的布局引擎分配，代码只在 `UpdateStat()` 里显式定宽后调一次 `PerformLayout()`。
2. 全代码**唯一**把统计文本清空（连带项宽归零）的地方是打开文件入口；实机复现路径正好是「打开文件后不滚动」——两者 1:1 吻合，而过滤路径从不清空。
3. `UpdateStat()` 在打开路径上**不是**对状态栏的最后一次写入：其后还有文件名 / 渠道 / 消息 / 进度条可见性四处尾写。
4. 2026-11-03 的探针结论（`AutoSize=false` + 显式尺寸在 `PerformLayout` 后保留、相邻项文本搅动不会清掉显式尺寸）是 96 DPI 本机结论，在复现机器上没能解释现象——**该结论不可迁移，这正是本次要取证的缺口**。
5. 既有设施可复用：`StartupLog`（追加到程序目录 `Log/` 下的启动日志，带时间戳，异常全吞）与 `DpiDiag`（`[DPI]` 前缀的同类诊断流）。项目惯例是「诊断只读、异常吞掉、绝不影响主流程」。

## Goals / Non-Goals

**Goals:**

- 让复现机器的日志能**唯一**判定四种候选机制之一（项宽被算成 0 / 文本没刷新 / 整条溢出被裁切 / 只是没重绘）。
- 覆盖「打开文件 → 不滚动」这条既有两轮修复都没覆盖的路径，并拿到「滚动后恢复」的对照帧。
- 零行为变化、开销可忽略，且值得长期保留（下次复发自带日志）。

**Non-Goals:**

- 不解释 WinForms 内部为什么会这样算（结论拿到后再谈）。
- 不改状态栏结构、不调整任何布局调用顺序、不碰既有修复。
- 不新建日志框架、不引入诊断开关、不做日志轮转。

## Decisions

### D1 独立前缀 + 固定 tag 词表

用 `[StatBar]` 作独立前缀（与既有 `[DPI]` 平级，复用同一条启动日志），tag 固定为
`clear` / `stat` / `tail-file` / `tail-channel` / `tail-msg` / `tail-finally` / `scroll` / `idle+200` / `idle+2s`。

理由：判读是「拿两帧对比」，自由文本会逼着人逐行读；固定词表可以让取证结论用 grep 直接落表。
替代方案：泛化控件树 dump —— 噪声大、与本次四机制无关，否决。

### D2 字段按「能区分四机制」取舍

一条快照只记：状态条宽高、布局风格、能否溢出；以及每个项的
`w`（宽度）、`len`（文本长度）、`Avail`（是否可用）、`Place`（放置位置）、`vis`（可见性）。

理由：`w` 抓机制 A；`len` 抓机制 B（文本空 = 统计没刷）；`Avail`/`Place` + 状态条宽度抓机制 C；三帧（尾写后 / +200 ms / +2 s）宽度是否一致抓机制 D。其余字段（坐标、字体、渲染器）对判定无用，不进快照。

### D3 打点挂在「写入调用点」而非 StatusStrip 事件上

每次状态栏写入之后立刻拍一张，而不是订阅布局/绘制事件。

理由：事件只能看到「事后」，而本次要回答的正是「这一次写入之后项的尺寸是否还正确」。挂在调用点还能保证日志顺序与代码顺序一致，便于对齐时序图。
代价：需要在既有方法的多处加一行调用，但都是同一条路径上的相邻语句，不改动任何返回/顺序。

边界：`StartIndex` 开头那次文件名写入发生在清零**之前**，不参与收尾时序，因此不设帧（它不可能是「统计回写之后又被改掉」的那一环）。

### D4 延迟快照用一次性 Timer（+200 ms / +2 s）

理由：`BeginInvoke` 只保证「本条消息之后」，不保证布局与绘制跑完；一次性 Timer 落在消息泵空闲阶段，语义正好是「再过这么久还没好」。两枪分别覆盖「本次布局之后」与「后续偶发布局之后」。
句柄未创建/已销毁时静默丢弃（与项目既有后台投递纪律一致），不抛异常。

### D5 噪声预算即硬约束

进度回调、逐块发布、逐行扫描一律不打点；一次打开固定产出 9 行，一次滚动 1 行。
理由：取证版要发给别人跑真实文件，日志必须能整份发回；同时保证长期保留不会污染日志。
快照本体是同步字符串拼接，微秒级，且不触碰 UI 状态。

### D6 复用既有日志设施，不加开关

理由：项目已有「诊断写启动日志、异常吞掉」的成熟惯例，新建通道是重复建设；成本低于任何开关的维护成本，因此长期保留而不是取证后移除。
替代方案：只在调试构建输出 —— 复现机器拿到的就是发布包，做不到，否决。

### D7 判读表写进设计，而不是事后叙述

把「观测 → 结论」固定成表，取证时照表填：

| 观测 | 结论 |
| --- | --- |
| 尾写某帧里统计项 `w` 由正常值变 0 | 机制 A：显式尺寸被后续布局吃掉 |
| 全程 `w` 正常、`len` 正常，但对方仍看不见 | 机制 D：重绘/合成问题，与布局无关 |
| 某帧 `len=0` | 机制 B：统计没写回（时序问题，非布局） |
| `Avail=false` / `Place=Overflow` / 状态条宽明显不足 | 机制 C：整条溢出被裁切 |
| `scroll` 帧与尾写帧完全一致 | 滚动只是碰巧触发整条重排，印证布局引擎对项宽的判定被跳过 |

### D8 取消 / 失败路径同样落一行

`tail-finally` 放在 `finally` 里，取消、失败、抢占都会产出一行。

理由：否则「日志里没有 tail-finally」会被误读成「没走到收尾」，把取证带偏。

## Risks / Trade-offs

- [用户把诊断行当故障] → 前缀固定、一行一事件、只在启动日志里，proposal 已说明这是取证版本。
- [取证机器日志拿不回] → 取证指引压到最小：复现一次、滚动一次、发日志文件。
- [延迟快照正好卡在绘制前，出现假性「没重绘」] → 两枪（200 ms / 2 s）+ 用户手动滚动的 `scroll` 帧，三点对照。
- [探针改动被带进正式版] → 这是可接受的（长期保留），不列为发布阻断项；但必须在 change 里写明，避免下次被当成遗留垃圾清掉。
- [启动日志无上限增长] → 现状如此，本次不扩大规模；轮转属另一个话题。

## Migration Plan

1. 插桩落在以 `V0.1.9` 预发布分支为基线的独立 worktree，合回 `V0.1.9` 后按预发布流程出取证版（框架依赖包）。
2. 复现机器复现 → 回收启动日志 → 照 D7 表判定 → 结论写入 `openspec/notes/` 新笔记。
3. 回滚策略：本次改动可整段删除，不牵连任何行为；若取证后决定换掉状态栏结构，那是另一个 change。
