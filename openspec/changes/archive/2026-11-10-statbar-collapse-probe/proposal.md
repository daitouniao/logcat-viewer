# Proposal

## Why

V0.1.9 实机反馈：**打开文件后不滚动**，右下角统计区（总 / 命中 / 标记 / 索引 ms / 过滤 ms）不显示；拖一下滚动条即恢复。开发机（96 DPI）不复现。

同一症状已是第三轮：2026-10-28 首修（补强制重排）、2026-11-03 回炉（时序归位 + 显式定尺寸），两次都是凭时序假设改状态栏布局，实机验收碰运气。本次不再猜，先取证：把「到底是项宽被算成 0 / 文本没刷 / 整条溢出被裁切 / 只是没重绘」四选一钉死，再据事实决定修法。

## What Changes

- 状态栏收尾时序上新增一条 `[StatBar]` 诊断流（写入既有启动日志），固定 tag 词表、可 grep。
- 打点位置仅限打开文件这条路径：清空统计、统计回写、打开收尾的四处尾写、滚动恢复瞬间；另加打开后 +200 ms 与 +2 s 两张延迟快照（用于区分「布局被后续动静吃掉」与「从未重绘」）。
- 每次快照记录：状态条宽度与布局风格、每个项的宽度 / 文本长度 / 可用性 / 放置位置。
- 噪声预算：每次打开 ≤ 12 行，滚动一次 1 行；不在进度回调、逐块发布、逐行路径打点。
- 只读快照：不修改任何界面状态、不改变行为、不新增开关、不引入日志轮转。
- 交付一个预发布取证版（框架依赖包），复现机器复现后回收启动日志，按判读表给出结论。

## Capabilities

### New Capabilities

无。本次是纯诊断插桩：不新增、不修改任何行为契约，`.openspec.yaml` 置 `skip_specs: true`。

- 统计区目前**只有代码注释**承担（`openspec/specs/` 里只有渠道状态区有布局契约），本次不趁机虚构需求。
- 若取证把症状定性为布局缺陷，修复方案另开 change，并在那时把统计区的行为契约写进 `openspec/specs/`。

### Modified Capabilities

无。

## Impact

- 代码：`logcat-viewer` 主窗体的状态栏构建 / 统计回写 / 滚动位置回写路径；复用 `logcat-uicore` 既有诊断日志设施（不新建基础设施）。
- 对外可见变化：启动日志多出 `[StatBar]` 行；界面、性能、配置项均不变。
- 依赖 / API：无变更。
- 发版：需要一个预发布取证版，落在 `V0.1.9` 预发布分支（版本号同步与打 tag 属独立授权动作，不在本 change 的自动流程内）。
- 风险：启动日志本就无大小上限，本次不引入轮转，`[StatBar]` 行数在噪声预算内可忽略。

## 范围外

- 不修任何布局 / 重绘缺陷（结论出来后再开新 change）。
- 不改状态栏的项结构、不替换 StatusStrip、不引入日志轮转或诊断开关。
- 不改单元测试对统计文本的既有断言口径。
