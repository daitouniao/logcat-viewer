# Design

## Context

- 两个可执行程序（日志查看器、安卓工具箱）同目录分发，各自独立进程、独立配置。
- 当前两者共用同一枚图标资产：仓库内只有 `icon/app.ico` 一个图标资源（6 个尺寸：16/32/48/64/128/256，全部 32bpp，六个条目均为 PNG 压缩帧，共约 30 KB），两个工程都在构建配置里把它声明为应用图标。
- 窗体层没有任何显式设置窗口图标的代码；工具箱主窗体的既有注释已把「不设置即回退到程序文件的应用图标」写成约定。因此换图标只需要换程序文件内嵌的那枚图标，不需要改任何窗体代码，标题栏、任务切换视图、任务栏、文件管理器中的 exe 图标会一并跟随。
- 两个程序没有设置任何显式应用用户模型标识（AppUserModelID），Windows 按程序文件路径把两者分成两个任务栏按钮。也就是说任务栏按钮本来就是分开的，缺的只是图标差异——本次不触碰分组行为。
- 两者的窗口标题本就不同（查看器带产品名与版本，工具箱为「安卓工具箱」），悬停提示可以区分；不可区分的是不显示名称的固定按钮。
- **现有图标外观（已导出各尺寸预览核对）**：深绿色圆角方块底，内部为四行「彩色圆点 + 白色圆角长条」，圆点自上而下为绿/蓝/橙/红。256px 下层次清晰；16px 下圆点与条间距糊成一片，可辨特征退化为「绿底 + 横向白块」。这直接决定了新图标的差异必须落在最小尺寸仍可见的**大形状或底色**上，不能放在内部小元素（圆点、线条间距）上。
- Windows 对已固定的任务栏按钮缓存图标：更换程序文件图标后，旧固定项可能继续显示旧图标，取消固定再重新固定即刷新。属系统行为，本项目不处理，仅记录。

## Goals / Non-Goals

**Goals:**

- 两个应用在任务栏（含已固定项）、标题栏、任务切换视图、文件管理器、大小图标视图中的图标互不相同，且工具箱图标在各尺寸下完整清晰。
- 改动面尽量小：不触碰日志查看器的资产与工程配置，不改窗体代码，不改分发结构。
- 把「图标不同」「图标非空」「多尺寸齐全」变成发布校验中可以复核的硬判据。

**Non-Goals:**

- 不引入 AppUserModelID 或任何任务栏分组调整。
- 不改窗口标题、产品名、进程名、可执行文件名。
- 不重做日志查看器图标，不重命名现有图标资产。
- 不建矢量源图 → ico 的自动构建管线。
- 不处理历史固定项的图标缓存刷新（属系统行为，见 Context 末条）。

## Decisions

**D1 只给安卓工具箱换图标，查看器保持原样。**
理由：查看器的固定项与既有识别习惯不受影响，改动面最小（一个资源文件 + 一处工程配置）。备选「两个都重做同族」视觉更统一，但会让两个固定项都失效并要求重钉，收益不抵成本。

**D2 新资产放在既有图标目录，命名与现有资产同前缀（`app-tools.ico`），现有 `app.ico` 不改名。**
理由：同前缀表明两者是一套；不改名可避免查看器工程配置与相关文档的连带改动。备选「按角色重命名为 viewer/tools」需同时改查看器配置、两处 README 与历史引用，属无收益的连带改动。

**D3 只改工具箱工程的图标声明，不在代码里设置窗口图标。**
理由：窗体未显式设置时回退到程序文件图标，这一约定已在代码注释中固化并被当前行为验证；改代码需要把图标作为嵌入资源加载，反而引入资源查找、打包与失败回退三类新问题。备选「代码显式设置 Form.Icon」被否决。

**D4 新 ico 的尺寸集合必须与现有资产对齐：16/32/48/64/128/256，32bpp，条目用 PNG 压缩帧。**
理由：系统外壳按展示场景挑最接近的尺寸；缺 16px 会让小图标视图缩放发糊（正是任务栏的默认场景），缺 256px 会让大图标视图放大模糊。现有资产六帧均为 PNG 压缩，保持同一编码可避免高低 bpp 条目混用产生的边缘杂色。

**D5 同族不同形，且差异落在最小尺寸可见的层面。**
沿用深绿圆角方块底与白色主体（同族），内部符号由「四行横条」改为「2×2 四块圆角方块」的田字结构（工具/面板语义）。16px 下两者的剪影分别是「横纹」与「田字格」，差异在形状层面成立，不依赖色相与内部细节。
备选 A「只换基色、保留横条」：16px 下差异仅剩色相，深色任务栏与色弱场景不可靠，否决。
备选 B「换成扳手等细部图形」：该细节在 16px 会糊成一团，且丢失同族感，否决。
硬约束：不得把区分点放在圆点、线条间距一类内部小元素上（现有图标在 16px 已证明这类细节会消失）。

**D6 素材来源不在本设计中设约束。**
母图可由维护者提供，也可在实施阶段以图像生成产出；实际采用哪种由维护者届时确认可行性，实施记录写明真实来源。仓内不建矢量源图 → ico 的自动管线。

**D7 文档同步范围：两个 README 的仓库结构说明改写「程序图标」一行；构建文档的发布校验新增一条图标判据。**
理由：README 该行当前明确写着「两个 exe 共用」，改动后即成错误描述；构建文档只在新动作出现时更新（本次新增了一个校验动作）。

**D8 本次取代已归档的拆分决策「工具箱沿用同一枚应用图标」，但不改写归档记录。**
理由：归档笔记已冻结、不再维护；取代关系记录在本 change 中，归档时随 specs 合并进入持久规范。

## Risks / Trade-offs

**R1（中）最小尺寸的可辨性只能人工目视。** 「两个图标不同」「图标非空」「六尺寸齐全」都能脚本核对，但「16px 下能否一眼区分」没有自动化手段。对策：把「缩到 16px 与现有图标并排看」写入验收步骤，不宣称这一点被测试覆盖。

**R2（低）分发有两个包（自包含与框架依赖），各自都含两个可执行文件。** 只验一个包会漏掉另一半。对策：校验步骤按包逐一执行。

**R3（低）未来若引入安装器或快捷方式生成，图标需同步维护。** 本次为非目标，遗留为后续事项。
