# Design

## Context

动机见 proposal.md —— 这里只记录塑造技术方案的现状事实与实测约束。

### 现状实现的两段流水（`Services/FilterEngine.cs`）

`ApplyFilter` 分两段：

1. **段 1 预筛**：逐行读定长列（级别 / pid / tid / 分钟 / 标记 / tag），纯内存读。实测在 1 GB 样本上占 98–291 ms（空过滤条件），只占全量过滤的 4–9%。
2. **段 2 消息匹配**：对段 1 的每个候选行调用 `doc.MessageBytes(row)`，该方法**为每行 `new byte[]` 并 `ReadArray` 拷贝**（`Services/LogDocument.cs`）；随后按需折叠大小写再匹配。

段 2 的每行分配 + 拷贝是主要开销来源。1 GB / 1582 万行实测：段 2 的分配拷贝占绝大部分时间。

### 已确认的 API 事实（探针实测，2026-10-25）

| 事实 | 结论 |
| --- | --- |
| `SafeBuffer.ReadSpan<T>(ulong, Span<T>)` | 是**读入拷贝**语义（填充调用方提供的 span），**不是**零拷贝视图 → 不能用于本方案 |
| `SafeBuffer.AcquirePointer(ref byte*)` | 唯一零拷贝入口，需 `unsafe` + `AllowUnsafeBlocks` |
| `MemoryMappedViewAccessor.SafeMemoryMappedViewHandle` | 可取到 `SafeBuffer`，是 `AcquirePointer` 的合法宿主 |
| `view.PointerOffset` | 本仓库用法下恒为 0；`ptr + PointerOffset + 文件偏移` 与直接文件读一致（实测 `ptr+12345 == file[12345..]` 为真） |
| `AcquirePointer` 后 `view.Dispose()` + `mmf.Dispose()` + 强制 GC | 指针**仍可读且内容正确**（映射在 `ReleasePointer` 前不失效）→ 指针生命周期由 Acquire/Release 配对控制，不受 view 释放影响。**实测复核通过** |
| `System.Text.Ascii.IsValid(ReadOnlySpan<byte>)` | 可用于判定「整行是否纯 ASCII」，是分派快慢路径的依据 |
| `Span.IndexOfAny(byte, byte)` | 可用（.NET 8+ 字节域双值重载），用于候选位置定位 |
| 现状 `MessageBytes` 的行正文边界 | `msgStart = _offs[row] + _moff[row]`，`msgLen = _lens[row] - _moff[row]`；可由现有列直接推导，无需新增列 |
| **映射容量不随文件增长** | `view.Capacity` 固定为建映射时的文件大小；实测 1 MB 文件建映射 → 追加到 2 MB → `Capacity` 仍为 1,048,576。裸指针读越界处 → **进程段错误**（exit 139），`ReadArray` 则抛托管异常 → **必须复用随 `Append` 重映射的 `_view`**（见 D3） |

### 关于「现状语义」的精确刻画（探针实测，14 组过滤规格 × 1582 万行逐行比对一致，见 §5）

改造前的大小写不敏感路径**不是**「统一 OR 0x20 折叠」，而是**按行分派**：

- 行内**全部字节 < 0x80** → 行被就地 ASCII 折叠（仅 A–Z → a–z），needle 侧按 `ToLowerInvariant` 预编码 → 按字节找。
- 行内**含任意 ≥ 0x80 的字节** → 整行 `Encoding.UTF8.GetString(...).ToLowerInvariant()` 后按字节找。

该分派是**语义要求而非实现细节**：现状对 `ß`/`ẞ`、`İ`/`ı`、重音字符的结论只在「整行 Unicode 小写化」路径下成立，而现状测试 `message忽略大小写_重音不与非重音等价`、`message忽略大小写_德语eszett大小写等价`、`message忽略大小写_土耳其无点i不等于ASCII_I` 正是钉这一点的。

### 探索笔记与实测的差异（需要在本 change 内修正）

探索笔记 `openspec/notes/FILTER-ACCEL-ZERO-COPY.md` §3 记录的「变体 G′」与「变体 H」数字**不可直接用作验收线**：

- 笔记的 G′（945–1270 ms）**跳过非 ASCII 行**（探针代码里 `if (!ascii) continue;`），其命中数 362,895 之所以与现状 CI 相同，是因为该样本中 ASCII 行已覆盖全部命中；**它不构成与现状等价的实现**，无法作为语义正确的性能基线。
- 笔记的「现状 CI 2284–2945 ms」与本机同会话实测（6069–7809 ms）差 2–3 倍。复核发现：笔记的现状数字**未包含每行 `new byte[]` 的 GC 压力全貌**（同一进程连续跑多个变体时 GC 行为不同），且当时的探针未预热 mmap 缺页。

本 change 的验收线以**本机同会话、三轮取区间、视图常驻（生产口径：`_view` 建一次长期复用）**的实测为准，见 §5。

**连带风险（留给后续 change）**：兄弟笔记 `openspec/notes/UTF8-BYTE-SIMD-SEARCH.md` §4.2 仍把「两侧 OR 0x20 比较」列为**方案 A（推荐）**，并引用上述已失效的 2284–2945 ms / 945–1270 ms 基线。该 OR 0x20 方案**与现状语义不等价**（实测会把 `@` 与 `` ` ``、`[` 与 `{` 判为相等），后续 SIMD 路线的实现不应继承它 —— 该笔记属另一个 change 的探索产物，本 change 不代改，但其结论已被本 change 实测推翻（见 D4 / D5）。

## Goals / Non-Goals

**Goals:**

- 消除段 2 的每行字节数组分配与拷贝。
- 保持过滤命中集合与改造前**逐行完全一致**（含大小写不敏感的 Unicode 语义、and/or 组合、空过滤词、排除语义）。
- 让实时采集的增量过滤路径同样受益（走同一条段 2 逻辑）。
- 改动收敛在文档读取层 + 过滤引擎两处，不动列布局。

**Non-Goals:**

- 不引入 SIMD 块扫描 / 全文顺序扫描 / 并行分块（属 `UTF8-BYTE-SIMD-SEARCH.md` 的后续路线）。
- 不引入落盘缓存 / sidecar（属 `SIDECAR-CACHE-INDEX.md`）。
- 不重排列结构体（实测段 1 只占 4–9%，收益上限 9%，内存流量却恶化 32 倍）。
- 不改 tag / pid / tid / 分钟等其余过滤维度的实现。
- 不自持独立映射：复用文档已有的 `_view`（容量随 `Append` 重映射，见 D1/D3）。
- 不引入直接返回 `ReadOnlySpan<byte>` 的公开读取方法：会话 + 回调形态，避免 span 逸出导致悬垂读（见 D7）。

## Decisions

### D1：零拷贝读取路径 = 复用 `_view` + `AcquirePointer` + 指针算术

**决策**：`LogDocument` 暴露一个只读正文读取会话，**复用文档已有的 `_view`**（`MemoryMappedViewAccessor`）：从 `_view.SafeMemoryMappedViewHandle` 用 `AcquirePointer` 取得裸指针，按 `_offs/_moff/_lens` 三列直接切出每行正文的 `ReadOnlySpan<byte>`。

**理由**：
- `SafeBuffer.ReadSpan` 已实测为拷贝语义，无法零拷贝；`AcquirePointer` 是唯一零拷贝入口。
- 正文边界完全可由现有三列推导（`msgStart = _offs[row] + _moff[row]`），**无需新增列**，满足「不改列布局」的约束（`SIDECAR-CACHE-INDEX.md` 依赖此前提）。
- 行正文长度 = `_lens[row] - _moff[row]`，与现状 `MessageBytes` 的边界计算逐字一致。
- **复用 `_view` 的决定性理由是映射容量**（详见 D3）：`_view` 每次 `Append` 后由 `OpenMap()` 重映射，`Capacity` 始终等于当前文件大小；另开一个长驻映射的 `Capacity` 会冻结在创建时刻，文件增长后读新追加行即越界。

**为何不用 `MemoryMappedViewAccessor.ReadArray` 复用缓冲（变体 F）**：F 仍留一次每行拷贝，实测 1670 ms（1 GB）虽优于现状但显著劣于零拷贝；且每行调用 `ReadArray` 有跨边界的固定开销。零拷贝把这部分降到指针算术。

**代价**：需要 `unsafe` 上下文 → 主工程 csproj 需开 `AllowUnsafeBlocks`（当前仅 `.tmp-test/BenchLog` 探针工程开启）。该开关是**工程级**的，无法只对单个文件开启；缓解手段是把 `unsafe` 代码集中在一个文件的少数几个方法里（见 D7）。

**备选与否决**：
- *另开一个专用于读取的长驻映射*：**否决**。映射的 `Capacity` 不随文件增长（实测：1 MB 文件建映射 → 追加到 2 MB → `view.Capacity` 仍为 1,048,576），裸指针读越界处直接**进程段错误**（实测 exit 139），而 `ReadArray` 只会抛托管异常。实时采集路径的 `FilterTail` 读的正是新追加行，长驻映射必然越界。此外另开映射需多持一个文件句柄，代理文档场景下会与 `LogDocument.Close()` 的「先删暂存目录、后释放活性锁」顺序冲突（暂存目录可能删不掉）。
- *每次过滤重建独立映射*：安全，但每次多付 320~390 ms（实测 1 GB 新建映射 + 全文件触碰，对比复用映射 6~9 ms），吃掉部分加速收益。
- *把指针缓存进 `LogDocument` 长期持有*：换 view 时指针悬垂，需引用计数与退休队列，复杂度显著高于收益。

### D2：指针生命周期由 Acquire/Release 配对控制，不受 view 释放影响

**决策**：指针在**一次过滤调用内**获取与释放（`using` 语义），不跨调用持有；每次调用都从**当时的** `_view` 重新取指针。

**理由（探针实测）**：`AcquirePointer` 之后，即使 `view.Dispose()` + `mmf.Dispose()` + 强制 GC，指针**仍可读且内容正确** —— 映射由 Acquire 的引用计数托住，直到 `ReleasePointer` 才失效。这**消解了探索笔记 §5 担心的「换 view = 悬垂指针」风险**：指针是否有效只取决于 Acquire/Release 是否配对，与 `_view` 是否被 `OpenMap()` 换掉无关。

**为何仍要「一次调用内获取释放」**：`_view` 可能在两次过滤调用之间被 `Append` 换掉（`OpenMap()` 重映射）。若跨调用持有指针，读到的可能是**旧映射**的内容 —— 容量与内容都停留在旧文件大小。故每次调用都重新取指针，保证指针与当前 `_view` 同代。

### D3：读取视图与文档快照对齐 —— 靠「复用 `_view`」保证容量，而非靠额外同步

**决策**：每次过滤调用**现取**当前 `_view` 的指针；每行正文从**指针 + 该行记录的偏移**读取，且只读段 1 已确定的候选行。

**约束 1（映射容量 —— 本 change 最关键的一条）**：裸指针的合法读取范围是**建映射那一刻的文件大小**（`view.Capacity`），**追加不会让既有映射变大**。实测：1 MB 文件建映射 → 追加到 2 MB → `view.Capacity` 仍为 1,048,576 → 裸指针读新追加行 = 越界 = **进程段错误**（实测 exit 139）；`ReadArray` 会抛托管异常，裸指针无任何保护。
  → 本方案靠**复用 `_view`** 消除该风险：`_view` 每次 `Append` 后由 `OpenMap()` 重建，`Capacity` 始终等于当前文件大小。任何「另开长驻映射」的变体都必须自己实现同等的刷新纪律，否则实时采集路径（`FilterTail` 读新追加行）必然越界。

**约束 2（行内容不变式）**：`Append` 只在文件尾部追加，已索引行的文件偏移与内容都不变；跨批续行会**拉长末行**（`_lens[n-1]` 改写），该行正文尾部随之前移，但仍在同一文件偏移区间内、且长度由 `_lens` 描述 → 按 `_lens` 取长度依然正确。

**约束 3（并发）**：`frmMain` 用 `_docBusy` 串行化 —— `ApplyFilter` / `ApplyIncremental` 与 `Append` / `Reload` 互斥（`frmMain.cs` 的 `_docBusy`）。故过滤期间文档不会并发增长，`Append` 只发生在两次过滤之间。这条不变式是「每次调用现取 `_view`」能成立的前提，也是本方案不需要自建退休队列的原因。

**结论**：按「每次调用现取 `_view` 指针 → 段 1 快照候选集 → 逐行从当前映射读取」执行，语义与现状等价，无需额外同步机制（复用 `_view` 即复用其重映射纪律）。

### D4：大小写不敏感匹配 = 按行分派双路径（保留现状语义）

**决策**：沿用现状的**按行分派**结构，但把两条路径的输入从「拷贝后的字节数组」改为「零拷贝 span」：

| 行内容 | 路径 | 与现状的关系 |
| --- | --- | --- |
| 全部字节 < 0x80 | 字节级忽略大小写比较（候选首字节定位 + 逐字节验证） | 与现状的 ASCII 折叠路径**逐位等价**（现状折叠只改 A–Z） |
| 含 ≥ 0x80 字节 | 整行 Unicode 小写化后按字节找 | 与现状**逐位等价**（同样的 `GetString(...).ToLowerInvariant()`） |

**关键约束（不可省略）**：非 ASCII 行走 Unicode 路径是**语义要求**。若把非 ASCII 行也按字节折叠处理，`ß`/`ẞ`、`İ`/`ı`、重音字符的结论会与现状不同（现有测试正是钉这一点）。探针已验证：把非 ASCII 行也走字节折叠时，中文 needle 的命中集合从 0 变成 14,120,625 —— 语义被破坏。

**该数字的准确含义（复核）**：14,120,625 恰等于本样本中「正文全为 ASCII 的行数」（总行 15,823,120 − 正文含非 ASCII 字节的行 1,702,495 = 14,120,625）。即：一旦非 ASCII 行错走字节路径，中文 needle 会在**全部 ASCII 正文行**上误命中 —— 破坏面是 14,120,625 行而非少数几行。此数字与探索笔记 D2 记录的「两侧 OR 0x20 比较」方案**无关**（实测该方案对中文 needle 命中 0 行）：它刻画的是「行分派写错」的破坏规模；D2 的 OR 0x20 方案另有独立缺陷（实测 OR 0x20 会把 `@` 与 `` ` ``、`[` 与 `{` 判为相等，与现状「只折 A–Z」不等价 —— 故本 change 不采用 OR 0x20，见 D5）。

**为何 needle 侧仍用 `ToLowerInvariant` 预编码**：现状如此，且它保证了 needle 自身的 Unicode 语义（`ß` 与 `ẞ` 都编码成 `ß` 的字节序列）。字节路径下 needle 已是小写字节，行侧只需折叠大写即可对齐。

### D5：字节级比较用「候选首字节定位 + 逐字节验证」，而非逐位置朴素比较

**决策**：纯 ASCII 行的忽略大小写比较，先用 needle 首字节的**小写与大写两种形态**做 `IndexOfAny` 定位候选位置，再对候选位置逐字节验证（验证时把行侧字节的 A–Z 折成小写）。

**理由（实测，同进程同会话）**：

| 形态 | 1 GB / 1582 万行耗时 | 说明 |
| --- | --- | --- |
| 逐位置朴素比较（笔记 G′ 形态） | 4461–5169 ms | 每个起点都要比较首字节，O(n×m) |
| 候选首字节定位 + 验证 | 2381–2426 ms | 定位阶段是向量化的 `IndexOfAny`，验证只在候选位置发生 |

候选定位法快约 2 倍，且两者命中集合完全相同（都验证过）。原理：needle 首字节的大小写两种形态覆盖了全部可能的首字节取值，其余字节的验证是确定性的。

**为何不用 `SearchValues` 做多子串预筛**：字节域无多子串重载（见 `UTF8-BYTE-SIMD-SEARCH.md` §4.1）；且本 change 只做单 needle 定位，引入额外抽象收益有限。

### D6：段 1 预筛保持原样

**决策**：段 1（列访问预筛）不改。

**理由**：实测段 1 只占全量过滤的 4–9%，即便优化到零，总收益上限也只有 9%；而结构体重排会让窄过滤的内存流量从 15.8 MB 涨到 506 MB（32 倍），绝对代价约 50 ms 且方向是变差。零拷贝改造的收益全部来自段 2。

### D7：零拷贝读取视图的归属与 API 形态

**决策**：读取能力放在文档层，接口形态为**会话对象 + 回调取正文**：`LogDocument` 暴露一个可获取的读取会话；调用方在会话作用域内通过**回调**取得正文片段，正文 span 只在回调执行期间有效。

**理由**：
- 行正文边界由文档的列（`_offs/_moff/_lens`）唯一决定，边界计算属于文档层职责；放在过滤引擎里会重复这份推导，两处一旦漂移就是静默的错行 bug。放在文档层也让「零拷贝读取」这一能力可被其他消费者复用（如导出、崩溃时间渲染同样在拷贝正文）。
- **采用回调而非直接返回 span**：会话底层是裸指针，`ReleasePointer` 之后 span 即悬垂。若会话方法直接返回 `ReadOnlySpan<byte>`，调用方把 span 存到会话之外就会读到已释放的映射 —— 这类错误不抛异常、只产出乱码，排查成本极高。回调形态让「span 不得逸出回调」成为**编译期即可检查**的结构约束（span 不能被存到字段，也不能跨 lambda 捕获成长期引用）。
- **采用会话对象而非裸方法**：会话负责 `AcquirePointer` / `ReleasePointer` 配对（见 D2），并把「指针必须来自当前 `_view`」这一纪律封装在一处，不散落到调用点。

**接口约束**：
- 会话必须实现 `IDisposable`；`Dispose` 负责 `ReleasePointer`，且**幂等**（重复 `Dispose` 不抛）。
- 回调参数为 `ReadOnlySpan<byte>`；调用方不得把该 span 存到任何超出回调生命周期的位置。
- 会话不可跨 `LogDocument.Close()` 使用；`Close` 释放 `_view` 后继续使用会话属误用。
- 会话应在 `using` 作用域内使用，尽早 `ReleasePointer`，避免长时间占住映射引用。

**实现细化（2026-10-25 apply 期补记）**：引擎热循环（`FilterEngine.MsgFilter`）不走公开回调，而用会话的 internal 直连接口 `MessageSession.MessageSpan(row)`——同一套边界与容量护栏（逻辑单源，`ReadMessage` 即其回调包装），span 只在调用语句内消费。理由：1582 万行的逐行过滤里，「每行一次方法调用 + 委托间接调用 + 闭包字段回写」合计可达数百 ms（JIT 实测：Debug 下每行三次真实 call；Release 下 `MessageSpan` / `MatchAny` / `MatchFolded` 全靠 `AggressiveInlining` 内联后才追平参考实现，见 §5）。公开回调契约（`ReadMessage`，span 逸出即编译期错误）保留给外部消费者与测试——「span 不得逸出」的防呆设计意图不变，变通的只是同程序集内热循环的消费方式。

## Risks / Trade-offs

- **[引入 `unsafe` 上下文]** → 指针算术越界会变成内存破坏而非托管异常。缓解：偏移量全部来自文档自身的列（`offs`/`moff`/`lens`），边界由这些列保证；正文长度由 `lens - moff` 得出且 `moff ≤ lens` 在扫描期已保证；验证用「构造 span 前检查长度非负、指针偏移不超映射容量」。同时把不安全代码集中在一个文件的少数几个方法里，不散落（`AllowUnsafeBlocks` 是工程级开关，无法按文件开启 → 只能靠约定收敛）。

- **[映射容量与文件增长脱节 → 越界读导致进程崩溃]** → 这是本 change 最需要防的失效模式：裸指针的合法范围是建映射时的文件大小，追加不会让既有映射变大；越界读**不抛托管异常**，而是段错误（实测 exit 139），即整个应用崩溃而非单次过滤失败。缓解：**复用 `_view`**（每次 `Append` 后由 `OpenMap()` 重映射，`Capacity` 始终等于当前文件大小）；每次过滤调用现取指针，不跨调用持有；实现时在构造 span 前校验「偏移 + 长度 ≤ 当前映射容量」。

- **[大小写不敏感语义被简化]** → 任何人把非 ASCII 行也改成字节折叠，就会破坏 `ß`/`ẞ`、`İ`/`ı`、重音的结论，且这类 bug 在普通日志里不出现、难以察觉。规模上也不小：本样本正文含非 ASCII 字节的行有 1,702,495 行，错走字节路径会让中文 needle 误命中 14,120,625 行（见 D4）。缓解：现有三条 Unicode 测试（`message忽略大小写_重音不与非重音等价` / `..._德语eszett大小写等价` / `..._土耳其无点i不等于ASCII_I`）必须在改造后全绿；新增一条测试钉住「非 ASCII 行不走字节折叠路径」这一分派事实本身。

- **[候选定位法的正确性依赖「needle 首字节的大小写两种形态」这一完备性]** → 若 needle 首字节不是 ASCII 字母（如数字、标点），两种形态退化为一种，仍完备（该字节无大小写之分）；若 needle 含非 ASCII 字节，字节路径整体不适用，需走 Unicode 路径。缓解：分派前先判定 needle 是否全 ASCII、是否为空，并在测试中覆盖「needle 首字节为数字/标点」「needle 含非 ASCII」「needle 为空」三类边界。**注意不可采用笔记 D2 记录的「两侧 OR 0x20 比较」**：实测 OR 0x20 会把 `@` 与 `` ` ``、`[` 与 `{` 判为相等，与现状「只折 A–Z」不等价。

- **[性能验收线依赖机器状态]** → 探索笔记的绝对数字在本机复跑差 2–3 倍，不可直接引用。缓解：验收线用**同会话相对倍数**（新实现 vs 现状实现，同一进程、同一视图、三轮取区间），不写死绝对毫秒值；绝对值只作为参考记录。CI 与 CS 分档（CI ≥ 2×、CS ≥ 1.9×），CS 的下界低于 2× 是实测事实而非实现缺陷。

- **[每行判定「是否纯 ASCII」有额外开销]** → 实测该判定单独约 482–563 ms（1 GB 全量），是零拷贝 CI 路径的主要成本之一。缓解：判定本身是向量化的（`Ascii.IsValid`），且已包含在实测倍数内；若后续 SIMD 路线落地，该判定可与块扫描合并（属后续路线）。

- **[映射会话的建立成本]** → 复用 `_view` 时无需额外建立映射（`_view` 已由文档持有并随 `Append` 重映射），每次过滤只付一次 `AcquirePointer` / `ReleasePointer`（可忽略）。若将来改为自持映射，则每次新建映射需 320~390 ms（实测 1 GB，含首次触碰建页表），须重新评估验收线。
