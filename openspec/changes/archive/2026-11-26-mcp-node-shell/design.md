# Design

## Context

本仓库当前的日志能力分布：桌面宿主是 C# / .NET 10 WinForms；日志引擎（获取、解析、索引、分页、过滤）由 Rust 内核承载并以 C ABI cdylib 形态暴露，C# 侧经 P/Invoke 消费。**本刀与该引擎无耦合，不读其实现、不改其任何行为。**

MCP 端在本仓库不存在任何实现——没有 SDK 依赖、没有工程、没有对应规范。相关设计只存在于探索笔记（`openspec/notes/MCP-FUNCTIONALITY.md` 等），其中工具面口径（检索型五工具 vs 分析型五工具）自 2026-11-06 起未拍板；笔记已明确标注自身「待评审、未实施」，故不作为实施依据，只作为背景。

本刀的技术前提是：MCP 端的对外契约必须能**在完全不接触日志数据能力**的前提下独立成立、独立可测。故引擎接入路径不在本刀讨论范围内。

工程侧约束（来自项目规范）：所有产物用简体中文；规范只写行为契约、实现细节归本文件；规范按实现代际分层，分类名须先在 `openspec/config.yaml` 登记；新能力须走 OpenSpec 变更流程，评审通过后才能编码；编码在变更专属的独立 worktree 中实施；测试用例数与覆盖率以 `docs/TESTING.md` 为唯一权威源。

工具链现状（实测）：Node v26.8.1 / npm 11.19.0；npm registry 指向 npmmirror 镜像；`@modelcontextprotocol/server` 最新 2.4.0（依赖 `@modelcontextprotocol/core` 2.4.0 与 zod ^4.2.0，要求 Node ≥ 20）；同名 v1 包 `@modelcontextprotocol/sdk` 最新 1.32.2（要求 Node ≥ 18）；TypeScript 5.9.3 为当前 5.x 线最新，7.0.2 已发布但生态适配面窄。

## Goals / Non-Goals

**Goals:**

- 产出一个可被真实 MCP 客户端拉起并完成全链路交互的服务端：握手 → 列举 → 调用 → 结果回填。
- 把输出信封、错误信封、通道分工、契约版本四项对外行为写成可测试的规范条款。
- 让服务端在不接触日志数据能力的环境中可独立启动、可独立测试。
- 为后续每一刀预留稳定的落点：工具注册机制与契约信封在后续刀中只扩展、不重写。

**Non-Goals:**

- 不选型业务工具面：工具名、参数形状、工具间语义边界均不在本刀冻结（`MCP-FUNCTIONALITY.md` §5 与 `MCP-LOG-ANALYSIS-API.md` 的口径冲突未解，留给后续刀）。
- 不涉及日志数据能力：不读取日志文件、不产出日志数据、不与既有引擎耦合。
- 不处理发布与版本：包名、发布通道、版本号同步点均不在本刀。
- 不定义 HTTP 传输、鉴权与远端部署。

## Decisions

### D1：SDK 选 v2（`@modelcontextprotocol/server`），不选 v1（`@modelcontextprotocol/sdk`）

**理由**：v2 是 MCP 项目当前的稳定线，实现 2026-07-28 版规范；包已拆分为 `@modelcontextprotocol/server` / `@modelcontextprotocol/client`，服务端只依赖其中 server 包，依赖面比 v1 单包更小（v1 单包把 express / hono / cors / jose / oauth 等 HTTP 与鉴权相关依赖一并带入，服务端只用 stdio 时这些全是无用负担）。v2 的模式校验走 Standard Schema，zod v4 即可。

**代价与缓解**：v2 较新、社区示例少于 v1。缓解方式是本刀只用到极小的 API 面（注册工具、stdio 传输、连接），该面在两版之间形态稳定；且本刀的测试覆盖全链路，API 变动会立即被测试捕获，而不是留到后续刀。

**替代方案**：v1（`@modelcontextprotocol/sdk` 1.32.2）生态成熟、教程多，但会把 HTTP/鉴权依赖拖进一个只跑 stdio 的工程，且后续迁 v2 是一次破坏性改动。已否决。

### D2：TypeScript 锁 5.9.x，不锁 7.x

**理由**：TypeScript 7 虽已发布，但其与 zod v4 及 SDK 类型推导的适配面尚未在本仓库验证过；本刀需要一个可复现、可 CI 复跑的构建。5.9.3 是 5.x 线的最新稳定版。

**代价**：放弃 7.x 的编译速度收益。对一个单进程小工程无实质影响。

**替代方案**：直接用 7.0.2——若其类型推导与 SDK 的 Standard Schema 泛型出现不兼容，需在编码期返工换版本。已否决。

### D3：工程放仓库根下 `mcp/` 目录，不进 Rust workspace，不进 .NET 解决方案

**理由**：本刀零 Rust 改动、零 .NET 改动。放进任一既有构建体系都会引入不必要的耦合（Rust workspace 需引入异步运行时依赖树才能承载 MCP 运行时；.NET 解决方案会要求该项目可被 `dotnet build` 解析，而它是 Node 工程）。

目录名取 `mcp/`：短、与分类名一致、语义即"模型上下文协议服务端"，且不与既有目录名冲突（仓库根已有 `crates/`、`docs/`、`openspec/` 等，无 `mcp/`）。包名与可执行名取 `logcat-mcp`（见 D14）。

**代价**：仓库多出一套构建体系（Node + npm + tsc + node:test），CI 多一个作业。这是采纳 Node 路线的固有代价，本刀已明确承担。

**工具链面收敛**：只引 SDK、模式校验库、TypeScript 三项依赖，不引入 lint 框架与格式化工具。理由：本刀代码量小（本仓既有 Rust 内核的 lint 工具链亦不引入），契约正确性由全链路测试兜底而非静态检查；每多一项工具就多一份 CI 时间与一份版本漂移面。

**替代方案**：放进 Rust workspace 并用官方 Rust MCP SDK——可省掉整套 Node 工具链；但与已定的「Node 提供 MCP」方向相悖。已否决（方向由维护者拍板）。

### D4：规范落 `specs/mcp/server-shell/`，分类名 `mcp` 需先在 `openspec/config.yaml` 登记

**理由**：项目规范层的落位判据是「这段契约由谁的代码执行」——本刀契约由 Node 侧 MCP 服务端代码执行，既不属于 `old`（既有 C# 实现承载），也不属于 `logcore` 或 `next`。故新开分类 `mcp`。

分类名按规范要求**不得随手新建**，须先在 `openspec/config.yaml` 的 context 段登记；登记动作列为本变更 tasks 的一条，与首个 MCP 契约同批评审生效。

**注意**：`openspec/config.yaml` 的 context 段已登记 `next` 分类（2026-11-24），本刀登记 `mcp` 时应比照其写法，一并写明该分类首个 capability 为 `server-shell`。

### D5：契约信封以「结构化内容 + 文本内容块同源」的方式下发

**理由**：MCP 工具结果可同时含文本内容块与结构化内容。二者同源的价值在于：文本内容块供模型直接消费（模型读文本比读 JSON 树更稳），结构化内容供客户端程序化处理；若二者由不同来源拼装，会出现「模型看到的」与「程序读到的」不一致的经典缺陷。

**代价**：每次产出需同时构造两份表示，实现上要求产出单一对象再由一处派生，而非各写一遍。

### D6：调用与结果的关联由协议层承担，不在结果体内自造标识

**理由**：实测所用协议版本的成功调用结果体只有内容块、结构化内容、错误标记与元数据四类字段，**没有承载调用标识的字段**。调用与响应的关联本就是 JSON-RPC 层的职责（请求标识随响应回传）。在结果体内自造标识字段，等于在协议外发明载体：客户端不会读它，反而制造「字段存在但无人消费」的死数据。

**代价**：无法从结果体本身反查是哪次调用——但这个信息客户端在协议层本就拿得到，不构成实际损失。

**替代方案**：把调用标识塞进结果的元数据字段。已否决——协议对该字段的定位是实现自用的松散键，不构成稳定契约，且仍是无消费方的死数据。

### D7：工具失败以「带错误标记的结果」返回，协议违规走协议错误通道

**理由**：实测协议对两类失败的载体有明确分工——工具调用的处理失败返回**带错误标记的结果**（而非协议错误），以便模型读到失败内容并据此调整；协议层违规（会话非法状态、请求形状非法）才走协议错误通道。把两者混同会让模型把「用法错了」误当成「业务失败」，浪费对话轮次。

错误码恒为英文的动因：MCP 服务端是给模型消费的机器接口，不跟随界面语言；项目既有规范亦有同类口径（错误码表为稳定英文标识，不随区域变化）。

**代价**：错误信息要走「结果」这条路，形状与成功结果同构，调用方需按错误标记判别而非按载体类型判别。

### D8：进程退出与资源释放纳入契约

**理由**：stdio 服务端是被客户端拉起的子进程，客户端退出后它必须跟着退出，否则会留下孤儿进程占住文件句柄。这是壳层真实存在的生命周期行为，不是实现细节——若不写进契约，实现者很容易做成「常驻不退」，且症状（残留进程）不易归因到本仓。

**代价**：退出路径需要单独测试，不能只测「能启动」。

### D9：stdout 只写协议消息，诊断一律 stderr，且必须有测试兜底

**理由**：stdio 传输下 stdout 即协议通道，任何一行多余文本都会让客户端的解析器失败或错位。这是 MCP 服务端最常见的致命错误，且症状往往是「客户端显示连接失败」而非指向 stdout 被污染，难以自查。

**故此项不只是实现约定，必须有自动化断言**：测试须在服务端产生诊断输出的同时捕获 stdout，逐行断言每行都是合法协议消息。

**替代方案**：不做 stdout 断言、靠人工注意——已否决，故障不可见。

### D10：`info` 自述工具作为唯一的内置工具

**理由**：一个零工具的 server 无法自证链路通畅，也无法在 CI 中断言「握手 → 列举 → 调用 → 结果回填」完整可用。`info` 工具不读日志文件、不产出日志数据，只回吐服务端版本、协议版本、契约版本与能力集，因此既能作链路探针，又不会让本刀意外长成业务实现。

**工具名定为 `info`**：工具名是模型直接看到的标识，一旦发布即是对外承诺。取 `info` 是因为它短、语义即"自述"、模型不易误解；将来新增业务工具时另起命名族（如 `logcat_*`），不与本工具混用。

**字段集（五项）**：服务端版本、协议版本、契约版本、能力集、传输形态。

**字段取值**：服务端版本取自该工程自身的版本声明（工程清单中的版本字段）——**本刀该字段留空**，因为本刀不发布，没有需要声明的版本，留空比编一个数字诚实；将来发布时再填，且不与仓库既有版本号同步机制挂钩（本刀无版本号同步点）。契约版本标识初值为 `0.1.0`——契约虽已冻结，但尚未经受过真实客户端检验，不宜宣称稳定。传输形态标识固定为标准输入输出。

**能力集粒度**：只声明工具相关能力，不声明资源与提示能力。理由：本刀不提供资源与提示，声明了会让客户端以为有、然后去问、然后得到空——不如不声明，客户端便不会问。工具能力中的"列举结果可变更"通知亦不声明，因为本刀工具集在进程生命周期内不变；此项留在本文件而不写进规范，是为了不限制后续刀引入动态注册工具。

### D11：未注册工具的调用返回带错误标记的结果，不走协议错误通道

**理由**：模型调了一个不存在的工具名，是「工具面理解有误」而非「协议用法错误」。返回带错误标记的结果，模型能读到"没有这个工具"并自行改用正确名称；若走协议错误通道，客户端通常把协议错误当作连接层故障展示给用户，模型反而拿不到可纠正的信息。

**代价**：错误信息要按结果体的形状组织，实现上比抛协议错误多一层转换。

### D12：壳层错误码固定为两个，且同属一个命名族

**理由**：本刀只有两类工具层失败——工具不存在、工具处理失败。固定为 `TOOL_NOT_FOUND` 与 `TOOL_FAILED` 两个稳定英文码后，错误面不会随实现漂移；后续刀新增错误码时以 `TOOL_` 为前缀扩展（如 `TOOL_TIMEOUT`），保持同一命名族。

**后续扩展预告**：后续刀若引入工具入参校验，其校验失败错误码另立（如 `INVALID_ARGUMENT`），不并入 `TOOL_FAILED`——入参非法与处理失败对模型的纠正方向不同（前者要改参数，后者要改用法或换路径），混在一起会让模型难以区分该重试还是该放弃。

**代价**：错误码粒度较粗——本刀无实际业务错误，无所谓。

### D13：退出时限限定为 5 秒

**理由**：客户端关闭连接后，服务端需要时间感知断开、收尾并退出。5 秒对本地进程而言足够宽裕（正常路径是毫秒级），又不会让"卡住不退"的实现拖垮测试；同时给 CI 留出机器繁忙的余量。

**代价**：超过 5 秒才退出的实现会被测试判失败——这正是意图。

### D14：本刀不发布

**理由**：发布需先定发布通道、版本号同步点与产物形态，这些在本刀都缺乏依据。暂不发布也避免过早占名。

**包名与可执行名定为 `logcat-mcp`**：两者一旦发布即不可撤销（包名在 registry 上被占用，可执行名写进用户的客户端配置）。现在定下比拖到发布前一刻草率拍定好；将来若改，只需改工程清单与文档，不动协议契约。

### D15：传输形态限定为标准输入输出

**理由**：本刀的服务对象是本机客户端以子进程方式拉起的场景，网络传输在本刀没有使用方。若不显式限定，下一刀很容易顺手把 HTTP 端做进来——那会引入鉴权、部署与端口占用等一整套本刀不需要的负担。

**代价**：未来若确有远程使用需求，需另立变更解除本约束。

### D16：规范只冻结信封骨架与错误码取值，其余具体取值归本文件

**理由**：本刀写完即归档，delta 会合并进主干规范——归档进主干就等于宣告长期契约。而「当前能力集只有工具」「自述工具当前返回五项字段」本质是**当前实现状态**：后续刀接入业务后，能力集会变、字段可能调整。若把这些写进规范，每加一项都要走一次规范修订评审。

故规范只冻结两类东西：

1. **任何后续刀都要遵守的骨架**——结果体的形状与同源性、错误以标记返回、错误码为稳定英文、stdout 只走协议、进程退出行为；
2. **取值本身即对外契约者**——错误码是唯一例外：客户端与模型会**按码分支**（`TOOL_NOT_FOUND` 与 `TOOL_FAILED` 导向不同的纠正动作），码值漂移等于行为变更，故锁进规范。

其余（能力集内容、字段清单、具体错误码之外的实现选择）归本文件，随刀演进。

**代价**：规范条款比"全冻结"粗，后续刀新增能力时无需修订规范，但也意味着规范对这些点的约束力较弱——由本文件与 tasks 承接。

### D17：把冻结粒度判据提炼为全仓规则

**理由**：D16 揭示的判据不是 MCP 专属——「行为契约 vs 当前实现状态」的区分对 `old`、`logcore`、`next` 各分类同样成立。而 `openspec/config.yaml` 的 context 段是**所有 change 的公共上下文**，规则放这里，下一刀读到它就知道边界，不必每刀重新推一遍；反之若只留在本 change 的 design 里，判据只对本刀有效，换刀即失效。

config.yaml context 段已有五段同类元规则（规范定位 / 规范分层 / 文档口径 / 工作流门禁 / 探索规范），增补第六段完全符合本仓既有惯例。

**适用范围**：全仓各分类一致适用。理由：这是"规范怎么写"的通用判据，与宿主无关；限定只对 `mcp` 生效反而制造特例。**不追溯**——已归档的规范不必回头修订，只是后续 change 按此写。

**落地方式**：措辞在 design 固定、写入动作列为 tasks 的一条，与 `mcp` 分类登记同批进行（同改 `openspec/config.yaml` 的 context 段，一次改到位，避免两次改动互相踩）。

**连带条款**：把 G 的教训一并固化——分类名须在「规范分层」段的当前分类清单与 rules 段的当前分类列表**两处**都登记，缺一视为未登记。因为漏登记不会报错，只会在数月后表现为规范分层静默错乱。

**代价**：context 段变长；且该规则从此约束所有 change 的写法，包括与本仓无关的纯文档类 change（但纯文档类 change 本就不写 spec，规则对其无实际影响）。

## Risks / Trade-offs

- **空壳被判定为无价值而搁置** → 以 `info` 工具 + CI 强制跑通作为完成标准，并在 tasks 中显式写明后续刀的接口边界，使本刀成为必要前置而非孤立产物。
- **多一套构建体系（Node + npm + tsc + node:test）带来长期维护成本** → 本刀不引入任何额外运行时依赖，工具链面收敛在最小集（无 lint 框架、无测试覆盖率工具的强制门禁）；若后续刀证明 Node 路线成本持续上升，可整体换语言而不动已冻结的契约。
- **v2 SDK 较新、API 可能变动** → 只依赖极小的 API 面；全链路测试作为变动探测器。
- **TypeScript 5.9 与 SDK 的类型推导若出现不兼容** → 已在 D2 排除 7.x 风险面；若仍出现，优先升级 TS 小版本而非改 SDK。
- **契约冻结过早，锁死了将来需要的字段** → 契约只冻结「信封结构」与「通道分工」两类与工具无关的骨架；业务字段一律不进本刀。
- **npm registry 为镜像源，与公网源可能存在版本差异** → 依赖版本用精确版本而非范围锁定，并在 lock 文件中固定，避免 CI 解析到不同版本。
- **`openspec/config.yaml` 的分类登记若与其他并行变更冲突** → 该文件当前已有未提交的分类登记改动；本刀登记 `mcp` 时须与在途改动同段落合并，确认不覆盖既有内容。
