# Proposal

## Why

Message 过滤的现状是「逐候选行零拷贝匹配」（`filter-msgfilter-zero-copy` 已落地），1 GB / 1582 万行热缓存下 case-insensitive 仍需 945–1270 ms。探索笔记《UTF8-BYTE-SIMD-SEARCH》已用探针证实目标形态——**并行分块 + SIMD 大小写不敏感扫描原始 mmap 字节**——可达 133–151 ms（约 7–9×），且全部决策（预筛范围 Q1=A、改动边界 Q3=A、CI 策略复用既有实现、非目标清单）已于 2026-10-29 拍板，排序上用户已确认本路线先于 sidecar 缓存实施。

## What Changes

- 在 Message 过滤内部新增「原始字节块扫描」路径：在 mmap 视图指针上按块并行扫描关键词字节序列（`Span<byte>.IndexOf` 向量化 / SIMD 大小写不敏感候选定位），命中后按行索引复核归属与 message 段边界，仅对命中行做必要复核。
- 新增分派逻辑：按「文档行数、候选行占比、关键词可用性（全 ASCII 且关键词数不超上限）」三条件在「逐行匹配」（现状路径，保留）与「块扫描」间选择；小文件、少候选、关键词过多或含非 ASCII 关键词时继续走逐行路径。
- 忽略大小写语义保持与现状逐位等价：全 ASCII 过滤词走字节级 CI 扫描 + 对含非 ASCII 字节的行回退既有「Unicode 折叠后匹配」路径；**过滤条件中任一关键词含非 ASCII 字节时整体回退逐行路径**（不加速，但结论不变）。
- **对外行为契约不变**：`ApplyFilter` / `FilterTail` 签名、进度上报语义、排除/与或/空词/大小写语义均不动；判定标准 = 同一输入同一过滤条件下新旧路径行号集合完全一致。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `message-filter`: 新增一条需求——全量过滤无论采用逐条匹配还是字节块扫描，同一输入同一过滤条件的命中结论必须一致（含跨块边界命中、头部区域命中不误报、非 ASCII 行的 Unicode 折叠语义不受影响）。既有五条需求（作用域、大小写等价、多关键词组合、排除语义、增量与全量一致）均不变。

## Impact

- **代码**：`Services/FilterEngine.cs`（`MsgFilter` 内部分派 + 新增块扫描实现）；`Services/LogDocument.cs` 仅复用既有 `MessageSession` 指针会话与列索引（`Offs` / `Lens` / `Moff`），不改公开 API。
- **测试**：`tests/logcat.Tests/FilterEngineTests.cs` 扩展等价性用例；新增块扫描专项用例（跨块、重叠区去重、非 ASCII 回退、空词组合）。
- **依赖**：无新增外部依赖（`System.Numerics` 向量化为 BCL 自带）。
- **性能预期（实测已完成，2026-10-30 接受现状）**：正确性硬门槛达成——200 MB / 1 GB 各 10 组用例命中集合逐位一致（含 3.7 M / 12.2 M 行的大命中集合）；冷缓存不劣化。性能未达设计期目标：1 GB CI 1.49×、200 MB CI 1.88×（目标 ≥5× / ≥2×），主因是非 ASCII 行折叠回退（design D3 红线）必付、短同义词逐条路径本就便宜、多词 `and` 逐条路径提前退出。CS 场景 1.5–2.9× 稳定正收益，最差情形 0.92–1.01× 落在测量噪声内、不劣化。处置：不改口径、不改结构，如实交付；发版说明与 README 不承诺任何倍数收益。普通档（4–8 核）未验证、为终态、不排补测；基准含高频短词组（`1` / `:` / `error` 类）以暴露头部命中复核成本。实测明细见 design.md「实测结论与门槛处置」与 tasks 4.1。
- **非目标**：正则匹配、跨行上下文匹配、Level/Pid/Tag 等其他列的字节级预筛（Level 已是定长列）、块内多模式匹配、含非 ASCII 关键词组合的加速（整体回退逐行）、sidecar 缓存（排在本路线之后）、Tag 过滤与导出路径复用（待后续需要再抽）。
