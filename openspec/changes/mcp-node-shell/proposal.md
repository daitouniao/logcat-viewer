# Proposal

## Why

MCP 端在本仓库至今**零实现**：全仓库无 MCP SDK 依赖、无 MCP 工程、无对应规范；相关设计只停留在 `openspec/notes/MCP-FUNCTIONALITY.md` 等探索笔记中，而这些笔记本身未拍板工具面口径。

现在要做的不是"把 MCP 做完"，而是**先把 MCP 端的运行骨架与对外契约立起来**：一个能在 stdio 上被真实 MCP 客户端拉起、能完成握手、能列举并调用工具的 Node.js 服务端，并把它的输出信封与错误契约冻结成规范。理由是这些契约与实现语言无关、与工具面口径无关，先立住能避免后续每一刀都在返工；反过来，若先做业务工具，工具面口径（D5/Q1 至今未拍板）一变，壳层与契约要跟着重写。

本刀刻意**不接日志数据能力**：本刀只立 MCP 端的运行骨架与对外契约，取日志数据整体后置到后续刀。故本刀只做壳。

## What Changes

- 新增一个 Node.js 实现的 MCP 服务端工程，以 stdio 为传输，供本机 MCP 客户端以子进程方式拉起。
- 冻结 MCP 端的对外行为契约：会话建立与能力声明、工具列举与调用的响应信封、错误响应信封、输出通道分工（stdout 仅承载协议消息，诊断信息走 stderr）。
- 提供一个不依赖日志数据能力的自述工具，用于验证握手、列举、调用与结果回填的完整链路。
- 新增规范分类 `mcp`，承载由 MCP 服务端代码执行的契约；该分类名在 `openspec/config.yaml` 登记。

**范围外（out of scope）：**

- 不接入日志数据能力：不读取任何日志文件、不产出任何日志数据；不实现列表、检索、上下文、统计、崩溃清单中的任何一个。
- 不定义业务工具面：工具命名、参数形状、工具间语义边界均不在本刀冻结；本刀只提供注册机制与一个自述工具。
- 不发布：不出 npm 包、不占包名、不发版本、不进版本号同步点；只保证本地可运行。
- 不提供 HTTP 或其他非 stdio 传输；本刀的服务对象是本机客户端以子进程方式拉起的场景，网络传输在本刀没有使用方。
- 不改动既有 C# 宿主、Rust 内核与既有规范。
- 不引入对原生库的运行时依赖。

## Capabilities

### New Capabilities

- `mcp/server-shell`: MCP 服务端壳的行为契约——stdio 传输下的会话建立与能力声明、工具注册与列举、调用结果信封、错误结果信封、标准输出与诊断输出的通道分工、契约版本标识。

### Modified Capabilities

- 无。本刀不改动任何既有 capability 的需求。

## Impact

- **新增工程**：仓库根下新增 `mcp/` 目录（Node.js 工程，包名与可执行名 `logcat-mcp`），含工程清单、构建与测试配置、源码与测试。其构建产物不入库（不入 git）。
- **新增依赖**：引入 MCP 服务端 SDK 与模式校验库；两者均为该工程局部依赖，不影响既有 .NET 与 Rust 依赖树。
- **新增规范分类**：`openspec/specs/` 下新增分类目录 `mcp/`；该分类名需在 `openspec/config.yaml` 登记后，分类下的 capability 才可归档进主干规范。
- **新增全仓规则**：`openspec/config.yaml` 的 context 段新增一段「规范冻结粒度」，界定什么写进规范、什么归 design；该规则对全仓各分类一致适用，不追溯已归档的规范。
- **忽略规则**：`.gitignore` 需新增该工程的构建产物目录与覆盖率产物目录。
- **CI**：流水线需增加一个执行该工程构建与测试的作业。
- **文档**：`docs/TESTING.md` 需增补该工程的测试说明与实测用例数（单独记录，不并入既有合计口径）；`docs/BUILDING.md` 需在出现新的构建动作时更新。
- **不动**：C# 宿主工程、Rust workspace、既有规范文件均不改动；本刀不与既有日志引擎耦合。
