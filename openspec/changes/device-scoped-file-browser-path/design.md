# Design

## Context

动机见 proposal.md - Why。现状要点（本 design 的直接对象）：

- 文件浏览窗体由设备操作窗口按需创建（`DeviceOpsDialog.CreatePage`），是全项目唯一创建点。起始目录在窗体 `Load` 事件中通过 `NavigateTo(startPath)` 设定。
- 起始目录来源是单个全局字段（`AppSettings.LastRemotePath`，默认 `/sdcard`）。该字段在文件浏览窗体关闭时（`SaveLastPaths`）被写成当前面板所在目录。
- 切设备时设备操作窗口会关闭并重建设备相关页签（`OnDeviceChanged`）：先关闭旧页签（触发旧窗体的关闭流程 → 写全局字段），再重建新页签（读同一个全局字段）→ 上一台设备的目录成为新设备的起始目录。
- 目录列举失败时的错误处理在面板基类：加载异常统一交给「加载失败」钩子，钩子默认弹消息框；设备端钩子另有分支会在应用私有数据目录下失败时引导进入 run-as 模式。
- 面板基类是 WinForms 控件，但**现有单测已能构造它并替换其枚举行为**：`tests/logcat.Tests/FileBrowserTransferTests.cs` 实例化 `FileBrowserDialog`，并以 `StubDevicePane : DeviceFilePane` 覆盖 `ListAsync` 走无设备路径。
- 面板的当前目录在导航时**先提交后加载**（先写路径栏与状态，再异步列举），因此用户手动输入一个打不开的路径时，当前目录会停在这个失败路径上。

## Goals / Non-Goals

**Goals:**

- 起始目录按设备分别记忆，消除跨设备继承（spec「起始目录按设备分别记忆」）。
- 起始目录两级回落，且记忆目录失效时静默降级、不打断用户（spec「起始目录的回落顺序」「记忆目录失效时静默降级」）。
- 把「候选链构造」与「首个可用者选取」下沉为不依赖 WinForms 的可测逻辑。

**Non-Goals:**

- 不做每设备多条历史目录列表（需 UI 出口，属另一能力）。
- 不改收藏目录机制、run-as 包名记忆等其他记忆项。
- 本机侧目录记忆**不按设备拆分**（仍全局共享），但**写入值**改取「最后成功打开的目录」（见 D9，修同型缺陷）。
- 不引入新依赖，不改 csproj，不新增数据文件（沿用 `settings.json`）。
- 不给降级行为加任何用户可见提示（维护者已拍板：静默，不加状态栏文案、不加 i18n 键）。
- 不以新名字另起一个跨设备共享的目录字段（换了名字仍是全局单值，见 D2）。

## Decisions

### D1：记忆记录存 `AppSettings`，用列表而非字典

落点选 `AppSettings`（`settings.json`）而非 `FavoritesStore`（`favorites.json`）：前者承载「上次位置」这一族语义（设备端上次目录、本机端上次目录、run-as 中转目录），后者承载「收藏」语义（目录收藏、APK 路径、run-as 包名、最近打开文档）。「上次位置」与「收藏」是两类语义，混在一个文件里会让两个存储的职责边界变模糊。

注：原先承载设备端上次目录的单值字段 `LastRemotePath` 被移除（D2），设备端的「上次位置」改由本 change 新增的按设备集合承载，语义归属不变。

存储形状用「列表 + 最近在前」而非「字典 + 键为序列号」：字典虽查找快，但**淘汰策略无处安放**——设备序列号并不稳定（模拟器端口号 `emulator-5554`/`5556` 随启动顺序变化、网络设备地址随 IP 变化），记录会持续增殖，字典没有天然的「最久未用」概念。列表按「最近使用置首、超限从尾部淘汰」维护，与既有 `FavoritesStore.Add` 的插前范式同构，上限 16 条。

新增记录类型独立成模型（与 `FavoriteDir`、`FileEntry` 同处 `Models/`），字段为设备标识与目录路径。

### D2：全局单值字段整体移除，而非冻结保留

全局兜底目录字段（`AppSettings.LastRemotePath`）**从 `AppSettings` 中删除**，不再以任何形式存在。

先前的方案是「保留字段、冻结为不再被窗体改写的稳定兜底取值」。本轮决策改为删除，理由是这个字段本身就是串味机制的载体：

若保留（哪怕只读），它在「本设备无记忆记录」时仍会作为兜底候选进入回落链——而它的取值**必然来自某台设备**（唯一写入点是文件浏览窗体关闭时写入当前面板目录）。于是切到一台没访问过的设备时，兜底候选仍是**别的设备**的目录：串味只是从「每台设备都串」降级为「每台没访问过的设备串一次」，用户诉求并未真正满足。

删除后回落链只剩两级（本设备记忆 → `/sdcard`），**不存在任何跨设备共享的目录候选**，语义彻底干净。

删除的技术代价很低：

- 字段不再参与序列化 → 旧 `settings.json` 里的同名键在**下次保存时自然消失**，无需迁移代码、无需兼容读旧键。
- 反序列化时旧键被忽略（`System.Text.Json` 默认忽略未知成员），不抛异常，旧配置可直接加载。
- 既有测试里有两处断言引用该字段（`ModelTests.AppSettings默认值`、`StorePersistenceTests.AppSettings_文件不存在时返回默认值且不创建文件`），随字段删除一并移除。

**旧配置平滑的实际含义**：升级后用户的第一台设备起始目录是 `/sdcard` 而非旧配置里那个跨设备目录。这不是退化——那正是本次要修掉的行为。

### D3：静默降级不能复用「加载失败」钩子

静默降级要求失败时不弹框、也不触发设备端钩子里「引导进入 run-as」的分支——那条分支是为「用户主动导航到受限目录」设计的救济路径，在起始目录场景下弹出反而是打扰（用户没做任何操作就被问要不要进 run-as）。

因此「静默」必须是加载失败处理链上的一个显式模式：静默尝试失败时**不进入失败钩子**，仅返回失败结果给调用方。手动导航（用户输入路径、点击上级、双击目录等）维持现状——失败照旧报错，该提示是有价值的。

**静默是界面完全无痕，不只是不弹框**（维护者 2026-10-25 拍板）：面板加载失败路径上除失败钩子外，还会先写一次状态文案（「加载失败」，`Controls/FilePane.cs:382`），该文案落在面板状态标签（`LblStat`，位于按钮栏内）上，用户可见。静默尝试必须连它一起挡掉——否则降级虽不弹框，界面上仍留着一条「加载失败」痕迹，与 spec「不向用户弹出错误提示或提示信息」相悖。

### D4：起始目录解析由窗体层承担，序列号需留在窗体里

起始目录解析依赖设备序列号与「逐级尝试打开并观察成败」，两者都是窗体层的事：文件浏览窗体当前**虽在构造参数里接了序列号，但只用来拼标题、不留字段**——公开构造与 internal 测试构造均已带 `serial` 参数（`Forms/FileBrowserDialog.cs:34/43`），窗体拿得到却存不住，关闭时无法按设备归属写记忆。改造只需新增一个字段保存序列号，**不需要调整构造签名**。

起始目录解析放在文件浏览窗体而非设备操作窗口：降级需要「尝试打开并等结果」，而设备操作窗口是页签容器，跨窗口传递异步加载结果会让页签重建流程变复杂；文件浏览窗体本来就在 `Load` 事件里做起始目录导航，就地改造最自然。代价是窗体构造参数调整（起始目录参数不再由外部传入，见 D5）。

### D5：构造参数调整与「可写存储根目录」的处理

文件浏览窗体构造签名中「设备端起始目录」参数移除，改由窗体内部按设备解析；本机侧起始目录参数保留（其取值与设备无关）。设备可写存储根目录（`/sdcard`）作为回落链末位，在窗体内部取常量，不再由外部注入。

移除该参数的理由随 D2 一并简化：原先外部注入的旧值就是全局单值 `LastRemotePath` 的取值（语义为「上次目录」，与新语义不同，保留会误导调用方），该字段删除后**不再有可注入的旧值来源**，参数自然消失。唯一调用点 `DeviceOpsDialog.CreatePage` 相应改为只传本机侧起始目录。

### D6：尝试与提交分离

面板的当前目录是「正在显示的目录」这一 UI 状态，路径栏、传输按钮文案、收藏高亮都读它。逐级尝试若逐个改写当前目录再加载，失败时当前目录会短暂停在失败路径上（路径栏闪一下、按钮文案跳一下）。

因此**新增的「尝试打开指定目录」接口**须保证**成功才提交**：尝试某候选时先完成列举，成功则提交当前目录与列表并触发路径变更事件，失败则保持原状态，对调用方只返回一个失败结果。这样「提交」与「尝试」分离，降级过程对 UI 不可见。

失败时是否静默也由尝试接口按参数决定：起始目录解析用静默模式，手动导航用报错模式。

**与现有加载路径的关系（另起独立路径，不动 `LoadIntoAsync`）**：面板基类现有的加载入口 `LoadIntoAsync`（`Controls/FilePane.cs:361`）在 `await ListAsync` **之前**就执行了 `List.Items.Clear()` + 写「加载中…」+ 显示进度条，失败时再写「加载失败」并调失败钩子——它是「先清场、后加载」的形态，无法满足 D6「失败则保持原状态」。因此「尝试打开指定目录」**另起一条独立路径**：先列举，成功后一次性提交列表与状态，失败则原样返回、不触碰任何 UI 状态。现有 `LoadIntoAsync` 与手动导航语义**完全不动**（维护者 2026-10-25 拍板）。

**与手动导航的边界（本次范围）**：本 change 只改**起始目录解析**这条路径。手动导航（用户输入路径、双击目录、点上级）**保持现状的「先提交路径、后加载」语义**——失败仍照旧报错，且当前目录仍停在用户输入的失败路径上。

这不是遗漏，而是范围限定，理由有二：

1. 手动导航失败后当前目录停在失败路径，是**既有可见行为**（路径栏回显用户输入的路径，便于用户看清输错什么）。改掉它会变更手动导航的观感，超出本 change「修起始目录串味」的目标。
2. 手动导航路径**没有降级链**——失败就是失败，直接报错是正确反馈。若改成「成功后提交」，用户输入的路径会被静默丢弃（连同输入框回显），反而更困惑。

代价：面板需同时维护两条提交路径——起始目录解析走「尝试接口（成功后提交）」，手动导航走「现有 NavigateTo（先提交后加载）」。D9 的「最后成功打开的目录」字段正是为这二者并存而设。

### D7：候选链构造与「选中首个可用者」下沉为可测逻辑

把两段逻辑下沉到一处不依赖 WinForms 的组件：

- **候选链构造**：按「本设备记忆目录 → 设备可写存储根目录」产出有序去重的候选序列。纯数据逻辑。
- **首个可用者选取**：接受「尝试打开某路径并返回成败」的委托，依次尝试并返回首个成功者；全部失败返回「无」。委托由 UI 层提供，内部走 D3/D6 的静默尝试。

这样「顺序」「跳过失败项」「全失败」三条语义都有单测覆盖，且不依赖任何控件生命周期。

**关于可测性边界（修正早期判断）**：早期结论认为「仓库现有单测不构造任何 WinForms 控件，故降级行为若只写在窗体里就完全无法自动化验证」。代码核实后该前提**不成立**——`tests/logcat.Tests/FileBrowserTransferTests.cs` 已实例化 `FileBrowserDialog` 并以 `StubDevicePane : DeviceFilePane` 覆盖 `ListAsync`；面板基类的失败钩子 `OnLoadFailed` 是 `protected virtual`，`StubDevicePane` 同样可覆盖以断言「静默尝试不进钩子」。

结论方向不变，但理由换掉，且**覆盖面扩大**：面板层的关键行为可以自动化验证，不再依赖纯手工验收。纯逻辑下沉仍保留，理由从「否则无法验证」变为「面板层与逻辑层分离，各自可独立测试」，且逻辑层测试不需 STA 线程、不需构造窗体，跑得更稳更快。

### D8：记忆键为设备序列号，身份模式不参与

键取设备连接标识。身份模式（root / run-as / 普通）**不参与键**：同一台设备在不同身份下看到的目录树不同，但用户不会预期「切个 root 模式起始目录就变了」；且模式切换频繁，若纳入键会让记忆记录按模式翻倍、命中率下降。身份差异导致的目录不可见，由静默降级自然吸收。

**由此产生的体验落差（维护者已接受）**：用户在 root 身份下浏览过 `/data/local/tmp`（该目录被记入该设备的记忆记录），切回普通身份后该目录不可访问 → 起始目录静默降级为 `/sdcard`，**不弹权限提示、不作任何说明**。用户视角上表现为「刚才的目录不见了」，但这是身份模式的必然结果（普通身份本就看不到该目录），且静默降级符合 D3 的整体基调。spec 已单列 Scenario「身份模式变化导致记忆目录不可访问时静默降级」把该行为固化，避免实现阶段临场决定。

### D9：记忆记录的是「最后成功打开的目录」，不是「当前路径」

现状是「先提交路径、后加载」，用户手动输入一个打不开的路径时当前目录会停在失败路径上。若直接把当前路径写进记忆，下次打开就会先去试一个明知失败的目录——降级虽能兜住，但用户真实的工作目录被顶掉了。

故面板需单独维护「最后成功打开的目录」，仅在列举成功时更新；关闭时写入记忆的是它，而非当前路径。

**本机侧同源同修**：本机侧（`LastLocalPath`）存在**完全同型**的缺陷——手动输入无效本机路径 → 当前目录停在失败路径 → 关窗把该失败路径写入 `LastLocalPath` → 下次开页直接报错且无处可绕。面板基类既然已统一跟踪「最后成功打开的目录」，本机侧写入时**一并使用该值**，改动极小即消除该缺陷。

故写入规则统一为：设备侧写入本设备的记忆记录（本机侧与设备无关，仍写全局 `LastLocalPath`），两者都取「最后成功打开的目录」而非当前路径。

### D10：记录条数上限 16

上限 16 条：覆盖「常用几台设备 + 若干模拟器」的日常用量，JSON 体积在数 KB 量级。超限时从最久未用者开始淘汰。模拟器端口号变化造成的「同一台设备算作新设备」由此被自然吸收——旧记录沉到列表尾部后被淘汰，不需要额外的过期清理策略。

## 实施顺序约束

本 change **先于「拆分 logcat.exe + 安卓工具 exe」实施**（维护者 2026-10-25 就拆分探索笔记的 D8 拍板「甲」）。原因：两者要动的文件高度重叠——本 change 涉及的 `Services/AppSettings.cs`、`Forms/FileBrowserDialog.cs`、`Forms/DeviceOpsDialog.cs`、`Controls/FilePane.cs`、`Controls/DeviceFilePane.cs`，正是拆分要 `git mv` 搬走的那批。先做完本 change，拆分直接搬改完后的版本，基线稳定，本 change 的 design / tasks 一行都不用改写文件路径；若顺序反过来，本 change 的全部文件路径与 `file-browser` spec 的归属位置都要重写，实施前还得先 update 一次 change。

## Risks / Trade-offs

- **全局单值字段被删除**（D2）→ 旧配置里那个「上一台设备的目录」不再作为兜底候选，用户升级后第一台设备的起始目录是 `/sdcard` 而非旧值。取舍明确：那正是本次要修掉的串味行为，不是功能退化。技术代价低——旧键在下次保存时自然消失，无需迁移代码。
- **静默降级掩盖真实故障**（D3/D6）→ 用户不会知道起始目录为何变了。取舍明确：记忆目录失效是常态（应用被卸载、身份模式切换、目录被清理），弹框是常态性打扰；只有全部候选都打不开才报错，那时弹框才有信息量。身份模式切换导致的降级同样静默（见 D8，维护者已接受）。
- **模拟器序列号不稳定**（D1/D10）→ 模拟器重启后端口号变化会被视作新设备，旧记录沉底直至淘汰。可接受——上限 16 保证不会无限膨胀。
- **页面重建顺序依赖既有行为**→ 切设备时「先关闭旧页签（写旧设备记录）后重建新页签（读新设备记录）」的顺序由既有代码保证（`OnDeviceChanged` 先遍历关闭再逐个重建）。若两者顺序反转，会出现「用新设备记录写旧设备名」的错配。实现时需保持该顺序，并在 tasks 中列入核对项。
- **嵌入页签的关闭是否触发窗体关闭流程**→ 现有「写上次目录」正挂在这个流程上，其行为已被现网使用验证（用户可感知到目录被记住）；本次只是把写入目标从全局单值改为按设备，不改变触发机制。
- **本机侧起始目录仍为全局**→ 设备切换时本机侧不动。这是既有行为的延续（spec 场景已固化），不是遗漏。
