# Design：文件代理（fileproxy）

动机与范围见 proposal.md，行为契约见 specs/fileproxy/spec.md。本文只写实现层面的决策、理由与接入点。

## Context

现状关键事实（均已代码核实；行号为 2026-10-17 评审时点快照，随演进可能漂移，以符号名为准）：

- 装载入口只有一个：`frmMain.OpenFile` → `StartIndex`（frmMain.cs:938）→ `LogDocument.BuildAsync`。拖放（`OnDragDrop`，frmMain.cs:1576）、MRU（`RebuildRecentMenu`，frmMain.cs:860）、菜单「打开…」/Ctrl+O、手动输入路径（`OpenFileByInput`，frmMain.cs:923）全部汇入 `OpenFile`/`StartIndex`；产品代码中 `BuildAsync` 的另一处调用是 ADB 采集临时文件（frmMain.cs:1977），不碰本机文件打开。接入面收敛。
- 文档以路径为锚：`LogDocument.Path`（Services/LogDocument.cs:21）为唯一锚，索引构建期 `OpenMap`（:123，FileStream :129 + mmap :137）以内存映射随机访问，列索引按行号随机回读（`ScanRange` :282 经形参打开 :317）——这决定了「代理流」不能只支持顺序读，必须落成本地文件。
- 失败无分类：`StartIndex` 的 catch（frmMain.cs:990-993）一律弹同一个「建立索引失败：{ex.Message}」。
- 设置存储为 exe 同目录 JSON（`AppSettings`，Services/AppSettings.cs），缺字段走属性初始化器默认值——加字段对旧配置天然兼容。
- 实时采集链路读的是设备输出转临时文件（`LogcatStream`，Services/LogcatStream.cs），不碰本机文件打开，本设计零影响。
- 全仓无任何单实例逻辑：全仓 `*.cs` 检索 `Mutex` / `SingleInstance` / `GetProcessesByName` / `Process.GetProcesses` 零命中，`Program.cs`（Program.cs:9-26）启动即 `Application.Run(new frmMain())`，无实例互斥——用户当前可以多开对比多份日志（此能力将随本 change 移除，见决策 D13）。

## Goals / Non-Goals

**Goals：**

- 给「本机打不开的日志文件」一条经外部代理读入的通道，应用只认命名管道一种接口
- 全链路显示原路径，用户无感知临时文件
- 失败可分类、可指引；默认关闭，开启需用户显式选择
- 对既有装载链路最小侵入：拉取产物走既有索引构建，列索引 / 过滤 / 崩溃提取零改动

**Non-Goals：**

- 目录枚举（不进目录面板 / 时间线）；MCP 接入（白名单边界不松动）；DLT 触发联动（DLT 立项时另案）
- 管道随机读直替 mmap（模式 B）：`read` 的 `off` 参数为它留门，v1 不动文档的映射体系
- Reload 增量续拉：v1 全量重拉

## Decisions

### D1 传输用 Windows 命名管道（字节流模式）

不选 TCP localhost：免端口占用与防火墙提示，管道自带本机会话 ACL，安全边界由管道 ACL 承担，协议内无认证消息。默认管道名固定可配（撞车风险由「可配 + 握手自描述校验」缓解）。

### D2 代理是外部进程，应用只做客户端

代理 = 用户按 examples/ 例子自写的 node/python 脚本（或任何能写命名管道的程序）。应用不内置代理、不托管运行时。代价是用户要自己准备解释器；收益是「怎么读到这些字节」完全开放（换身份、调 EDR 放过接口、解密、远端拉都是脚本自己的事），应用不被任何特定读取手段绑定。

### D3 默认关闭（三条锚）

UI radio 默认「关闭」；单测断言反序列化缺该字段得 off；模式字符串解析失败一律回退 off（安全侧默认）。任何「默认开启」的改动都要显式推翻本条。

### D4 v1 消费形态 = spool 到本地临时文件

代理流不直接喂索引。根本原因见 Context 第二条：文档的 mmap 随机回读要求喂料源是本地文件。模式 B 列为后续候选。spool 本身是单线程顺序读（8MB 块），与大文件计划「单线程读」的既定方向哲学一致；spool 产物是普通本地文件，对后续大文件流水线透明。

### D5 spool 目录 = 应用所在目录下 temp 子目录，不提供配置项

不用系统临时目录：跟随应用所在盘，避开系统盘写满风险；exe 目录可写是既有前提（设置文件同在此目录）。磁盘写满不做特殊机制，I/O 错误原文透出，由用户处理——与「不兜底」哲学一致。

### D6 UI 全链路显示原路径

文档的显示路径 = 用户给的原始路径（标题栏、MRU、导出默认文件名）；内部源路径 = 临时文件。是否代理用一个布尔字段标记（而非运行时比较两路径是否不同），避免极端同路径巧合与语义漂移。

### D7 协议版本 v1，`hello` 握手协商

控制消息单行 JSON + 换行；读响应 = JSON 头行 + 紧跟的长度前缀裸块。`proto` 缺失或 ≠1 一律判连接失败，不做兼容降级（安全侧默认：连的是什么都不确定的代理，不给它读文件的机会）。保留 `off` 随机读参数是为模式 B 与 Reload 续拉留门，v1 客户端只发顺序偏移。

### D8 启动命令拆两个字段

「可执行文件」+「参数模板」两个独立配置，不做整行命令解析——免掉引号/转义地狱，UI 也好做。可执行文件 = 解释器或 exe 的完整路径，`UseShellExecute=false` 不依赖文件关联；脚本路径写在参数里。（2026-10-18 订正：参数字段不再承载 `{pipe}` 管道名模板——管道名收敛为服务层单一来源、组装时自动追加，占位符替换降级为旧配置兼容路径，见 D17。）

### D9 Reload 经代理时全量重拉

协议已支持按偏移续拉，但 v1 不做：全量重拉实现简单、语义无歧义；续拉优化（D-fp-03 类）留后续。

### D10 自动拉起与生命周期

连手动代理失败且配了启动命令才拉起（拉起与否只看命令是否配置，与模式无关）；轮询等待默认 5s 超时，错误消息附完整命令行。拉起进程驻留复用、退出双保险（主窗关闭流程 + 进程退出事件）杀进程树。`--once` / `--idle` 自杀是例子侧可选项，应用不依赖。

### D11 渠道状态区替代模态告知

auto 首次转代理不弹模态、不用一次性提示：状态栏常驻渠道状态区，三态互斥（直接读 / 代理读 / ADB 采集），当前显示哪个渠道的日志就显示哪个；无文档且无拉取时空文本占位不隐藏（隐藏会导致 StatusStrip 后续分区位移、开关文档时布局抖动）。ADB 在途优先于一切（采集期当前文档是采集临时文件，不能按文档属性反推渠道）。

### D12 spool 完整性以 open.size 为基准，增长不兜底

主流程不发 stat（避免 stat→open 之间文件变化的 TOCTOU）：完整性判据 = 实收字节 == open 响应的 size。源文件持续追加则追逐 EOF 直至取消或磁盘写满，不设「实收 ≥ size 即停」兜底（候选：以打开时刻大小为界的定量读取，协议零改动，仅客户端循环退出条件变化，留作后备，实际场景频发再启用）。

**追逐态的用户可观测性（2026-10-17 评审补充）**：实收超过 open.size 后百分比分母失效，进度条驻留 50% 不再推进；此时状态文案切换为「正在经文件代理读取（已接收 X MB，源文件持续增长）…」并随每个 8MB 块的接收刷新——字节数持续增长即存活信号，用户可区分「在追」与「卡死」，取消入口为既有取消管线。**禁止出现「静态文案 + 静止进度条」的组合**：追逐 EOF 是设计接受的正常状态（本 decision 上半段），不是异常，不能让它长得像卡死。文案键入 `LocTable.RuntimeMsg`，随语言切换重算。进度序列的派生（pct/msg 由 received 与 open.size 决定）抽为纯函数，进 `FileProxyLoopbackTests`。

### D13 启动清理依赖单实例（D-OPEN-1 已拍板：接受）

单实例前提下，暂存根目录残留必为崩溃/强杀的死亡目录，启动后台线程删全部（无 24h 阈值），删前跳过本进程活跃集合，删不掉只留痕。清理线程在启动守卫成功后、主界面启动前由入口程序起，不依赖 UI 层。

**D-OPEN-1 拍板记录（2026-10-17）**：维护者确认接受「应用不再允许多开」这一行为变更；备选（跨进程活跃登记表）不采用。多开是用户今天可用的能力，release note 必须显著声明。

**代价量化状态（2026-10-17 评审补充记录）**：「谁在用多开」**无数据可量化**：项目无任何遥测/使用统计（csproj 无分析类依赖，`StartupLog` 仅为本地文件留痕），也无用户反馈渠道的回流数据。决策路径因此不是「数据支撑」，而是：① 单实例是启动清理安全的技术必需项（多实例下两进程互删对方活跃暂存目录，跨进程活跃登记表方案已评估为复杂度显著更高，不采用）；② 守卫是增量式新增，发布后若收到真实反馈，回滚/放宽的成本低。**不单独做一轮用户沟通**——分发触达路径就是 GitHub/GitCode release 说明，把丧失的能力（不能再多窗口对比多份日志）写进 release note 显著声明即完成告知（见 tasks 7.4）。

### D14 超大文件预警：超 1GB 确认框阻断

on/auto 打开超大受限文件时 spool 会先整体复制再索引，可能默默写满磁盘。阈值 1GB 写死不进设置（spool 相关均不加设置字段），超阈值弹确认框，取消即中止。直接打开无此问题（mmap 原地零复制），这是 spool 模式新增的不对称成本，用一次轻量确认换掉「写满才失败」的最差体验。

### D15 测试连接复用完整拉起链路（2026-10-18 追加）

现状「测试连接」只对已运行代理发 hello（固定 2000 ms），不拉起——保存前无法验证启动命令正确性，实际排障中已造成误判（连不上时不知道该先手动跑脚本）。改为直接复用 `EnsureProxyAsync`：以对话框当前字段值构造 `FileProxySettings`（测的就是所配即所得，不需要先保存），快连 200 ms → 连不上且有启动命令则拉起 → 按超时字段轮询。拉起进程进 `_launched` 驻留复用、应用退出统一回收，与打开文件路径完全同一实现，不新增第二套拉起逻辑。错误消息原样透出（启动失败 / 超时 / 协议不匹配等分类文案不变）。

### D16 浏览按钮消除手敲路径的两类坑（2026-10-18 追加）

排障实录的两类配置错误——整行命令塞进可执行文件字段、中文输入法打出全角引号包路径——都源于手敲路径。两个字段各加「浏览…」：可执行文件选 exe（过滤 `*.exe`）；参数选脚本（过滤 `*.js;*.py`），选中后**智能替换**参数字段开头：开头已是路径 token（带引号的整段，或到首个空格为止且含 `\`/`/` 的首段）则整体替换为新路径，否则从头插入——首轮实现在光标处插入，用户在已有 `"path" --pipe {pipe}` 且光标在开头时再选一次，路径被拼接成两份（`path"path" --pipe {pipe}`），故改为替换语义。含空格才加半角引号（与 `QuoteIfNeeded` 同口径）。不做「自动补 `--pipe {pipe}`」之类魔法——保持行为可预测，默认参数模板本来就在字段里。（注：「不自动补 `--pipe {pipe}`」随后被 D17 推翻——参数字段改为只填其余参数，管道名由服务层统一追加。）

### D17 管道名自动追加 + 命令行预览（2026-10-18 追加）

管道名此前有两个来源（管道名字段 + 参数模板里的 `{pipe}` 占位符），漏写 `{pipe}` 的后果是代理起在别的管道名上、应用连不上超时——与 D15 排障实录同族。收敛为单一来源：`--pipe <管道名>` 由 `FileProxyService.BuildLaunchArgs` 在启动命令组装时统一追加（启动进程、测试连接、命令行预览、StartupLog 留痕共用同一串），参数字段只承载其余参数。兼容两道：模板含 `{pipe}` 的旧形态仍按替换语义（settings.json 里手改过的配置不断）；对话框载入时剥除尾部 `--pipe {pipe}` 模板展示（`NormalizeLegacyArgs`），保存即归一化。用命令行预览（随字段实时刷新）代替隐藏魔法——最终命令可见可复制，也能直接复制去手动跑代理。有意取舍：自动追加固定了 flag 名必须为 `--pipe`，第三方代理用其它写法（如 `--pipe-name`）无法配置；现阶段代理协议由本项目定义（示例脚本均为 `--pipe`），收益大于限制，记录备查。

## 架构

```
┌──────────────────────────── 本机 ────────────────────────────┐
│                                                              │
│  ┌──────────┐  JSON行+裸块   ┌─────────────────────┐          │
│  │  logcat  │◄─────────────►│  文件代理（外部进程） │          │
│  │ (客户端)  │  \\.\pipe\    │  node / python 脚本   │          │
│  │           │  <管道名>     │  （用户自写，任意手段  │          │
│  └────┬─────┘               │   读入受限文件）      │          │
│       │ spool 8MB/块        └──────────┬───────────┘          │
│       ▼                                 │ 任意读法            │
│  应用目录\temp\logcat-proxy\{guid}\app.log ▼                   │
│       │                            受限文件（权限/EDR/…）      │
│       ▼                                                        │
│  既有索引构建（临时文件, 显示路径=原路径）                       │
│       │                                                        │
│       ▼                                                        │
│  列索引 / 过滤 / 崩溃提取（零改动）                             │
└──────────────────────────────────────────────────────────────┘
```

代理只回答四个问题：`hello`（你是谁）、`open`（给我个句柄）、`read`（读一段）/`close`。协议不关心文件为什么受限。

## 协议实现要点

- 控制消息（双向）= 单行 JSON + `\n`，UTF-8，单行上限 64KB（路径超长直接报错，不分帧）。
- 读成功响应 = `{"id":N,"ok":true,"n":M}` 头行 + 紧跟 M 字节原始负载（无分隔符）；`n=0` 表示 EOF 无负载。
- `id` 从 1 单调递增，响应原样带回；`len` 上限 16MB，代理侧 clamp；句柄连接内有效，断线全部失效。
- 未知 op / 坏 JSON / 坏句柄一律回 `ok:false`，**不得断开连接**（长连接复用）。
- 路径为 JSON 字符串（UNC/中文/空格均可，UTF-8 转由 JSON 层处理）。
- **实现关键坑：管道上不能套文本读取器**——二进制帧会被读取器的缓冲吃掉。必须自写「行缓冲读 JSON + 按 n 收裸块」的双模读取器（ leftover buffer 模式，同 examples/ 两个例子的实现）。

一次 auto 模式失败转代理的完整时序：

```
应用（客户端）                              代理（服务端）
     │ ① 直接打开失败                            │
     │─────────────── hello ───────────────────►│
     │◄──────────── {ok,proxy,proto} ───────────│
     │─────────────── open path ───────────────►│
     │◄──────────── {ok,h,size} ────────────────│
     │─────────── read h off=0 len=8MB ────────►│
     │◄───── {ok,n} + 8MB 裸块 ─────────────────│   × size/8MB 次（进度 0→50%）
     │─────────────── close h ─────────────────►│
     │◄──────────── {ok} ───────────────────────│
     │ ② spool 完成，实收 == open 响应的 size     │
     │ ③ 既有索引构建（临时文件）→ 列索引（50→100%）│
     │ ④ UI 显示原路径；MRU 记原路径              │
```

## Risks / Trade-offs

- **`LogDocument` 显示/源路径分离的 7 处接入点改漏一处**（本 change 最高危接入点：打开映射、重载头部探测、增量回退、两处文件长度查询、两处扫描传参——清单见上方「改动」表）→ 漏改症状 = 代理文档仍按显示路径开文件：直接打开失败的用户原样复现失败；或部分路径走原路径：Reload/增量读到空或旧内容，且非代理文档零行为变化锚被破坏。验证：tasks 5.1 的逐一核对（按「改动」表 7 处逐处对照 checklist + 完成后 grep `LogDocument.cs` 文件触及残留为 0 作为完成判据）+ `LogDocumentProxiedTests` 覆盖每处语义（含非代理文档零行为变化锚）。
- **spool 双倍磁盘**（500MB 受限文件 → 应用盘再 500MB；盘满则失败）→ 目录不换、不加设置项，写满由用户处理；失败时报错明确（I/O 原文透出，无专用错误码）。
- **启动命令 = 用户自配置任意代码执行**（设置文件可被本地用户改）→ 文档显式声明「等同应用权限，勿配不受信任脚本」；不做额外沙箱（本来就是用户自己的机器）。
- **管道名撞车**（同机多用户/多应用）→ 可配 + `hello` 自描述校验，发现不是预期代理可拒绝。
- **代理读到一半断/短读**→ 完整性校验（实收 == open.size），不等即删报短读。
- **python 例子的 `_winapi` 是私有 API**（例子稳定性）→ 例子注明「十余年稳定，生产建议 pywin32，语义一致」；协议不依赖任何语言特性。
- **大文件读循环的管道缓冲往返**（默认缓冲 64KB × 8MB 块）→ 代理侧发送缓冲加大 + 客户端大 buffer 循环；本地回环预期不构成新瓶颈（索引耗时才是大头）。
- **auto 把正常二进制误送代理**→ v1 无二进制格式；DLT 立项时按其形态处理。
- **崩溃残留 + 拉起代理变孤儿**→ 单实例 + 启动清理全部残留 + 退出双保险杀进程树。
- **单实例是行为变更**（已拍板：接受不能再多开；启动清理安全性以此为前提，备选的跨进程活跃表方案不采用）。

## 与其他轨道的交叉

- **大文件计划**：spool 产物对其透明；共同改动点 = 文档打开处。本 change 按现状打开处实现，大文件的入口收敛 / 读取层 / 增量路径到来时，把本 change 留下的分流段与源路径打开处作为既有输入重接（登记为其协同改动点）。协议 / spool / UI / 测试用例零返工，返工范围 = 重接线，天级。
- **目录时间线**：面板只列枚举可见文件，代理文件不进面板（v1 预期行为，不补救）；对话框列不出时用手动输入入口。
- **MCP**：白名单根 + 只读边界不因本 change 松动，MCP v1 不接代理能力。
- **实时采集**：不碰本机 open，零改动。
