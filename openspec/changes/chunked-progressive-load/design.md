# Design

## Context

大文件加载现状为整份构建路径：一次读入、一次解析、一次上屏。分块所需原语均已在主工程落地并在实时采集路径跑通：区间扫描（`LogDocument.ScanRange`，跨块续行经 `ScanPart.CarryLines` / `EndPrevHead` / `EndJoined` 传递）、增量并入（`LogDocument.Append`，含 `_lens[_n-1]` carry 回写与 tag 重映射）、尾部追加（`LogListView.AppendRows`）、增量过滤（`FilterEngine.FilterTail`）、增量上屏编排（`frmMain.ApplyIncremental`）。全量 Message 过滤的块扫描（并行 SIMD）已由 change `filter-msgfilter-block-scan` 实现并归档（2026-10-30）于 master。探索结论与探针数据见 `openspec/notes/CHUNKED-PROGRESSIVE-LOAD.md`（D1–D12 决策记录），本设计不重复数据。

关键前提事实：

- 块扫描的扫描上界本就按「最后一条已登记记录的末尾」截断（`dataEnd = min(cap, Offs[n-1]+Lens[n-1])`），文档只含已发布前缀时上界自动收缩——「前缀语义」无需新造；
- 每个块的扫描体本身是区间语义（行首落在本块才计数、重叠区不重复计行）；
- 块扫描需要 mmap 基指针（`LogDocument.MessageSession` 持映射视图指针）。

## Goals / Non-Goals

**Goals:**

- 本地文件（含代理 spool 完成后的本地文件）统一走分块流式管线，达成 specs 的首屏、等价性、内存、取消验收线。
- 加载期 Message 关键词过滤走增量块扫描（C′），不发生「加载期比加载完成后更慢」的体感倒退。
- 加载期已发布前缀字节稳定，作为增量过滤正确性基础。

**Non-Goals:**

- 代理路径边 spool 边解析（D5=A，后续另行立项）。
- 流式加载的总时长优化（分块买首屏与内存；总时长验收线为不劣于现状 5%）。
- 修改 `message-filter` 的 spec 级行为（增量块扫描是内部路径扩展，既有「不同扫描路径结论一致」需求继续覆盖）。

## Decisions

1. **管线形态：区间扫描推进 + 增量并入 + 逐块发布**（D1/D8）。加载循环 = 读一块 → `ScanRange` 解析该区间 → `Append` 并入（消费 carry）→ 发布新完成记录。小文件单块即整份，无独立路径。理由：四个支柱全是既有原语，探针已证逐元素零差异；不发明新模式。

2. **块长：自适应两段式，首块 4 MB、稳态 32 MB**（D2）。理由：首块 4 MB 实测 212 ms 出首屏；D10 落地后视图拼接 O(n²) 解除，块长不再被 UI 拷贝绑架，稳态取较大块降块数与过滤轮次开销。32 MB 为可调参数（探针 16–64 MB 均等价），默认值以内存（≤1.0 GB）与首屏不回退为约束。备选 16 MB（更保守，块数翻倍）。

3. **末条发布：滞后一条**（D3=A）。每块解析后判 `LastAppendCarried`：carry 置位意味着刚并入的末条会被下一块续行延长，不发布；EOF 无条件补发。理由：这是等价性硬约束（块首续行必须并入上批末条），同时正好保证「已发布前缀字节不再变」，是 C′ 的正确性前提。备选「允许末行刷新」（B）需新增单行刷新能力且与 Message 过滤语义冲突，否决。

4. **加载期 Message 过滤：C′ 增量块扫描**（D9）。把 `MsgFilterBlockScan` 的「全文档一轮」拆为三个阶段：
   - **会话**：按当前 RowCount 分配（或复用）`counts` / `nonAscii` 累计数组；
   - **区间轮**：给定字节区间 `[from, to)`，只扫该区间（`from` = 上轮 `dataEnd`，`to` = 本轮末条记录末尾，扫描起点前移 `overlap = 最长词 - 1` 防跨轮边界漏配）；归属逻辑复用现有扫描体（只计行首落在新区间的记录）；
   - **行段判定**：`VerdictPass` 只对本轮新增候选行跑，产出本批命中行号供 `FilterTail` 现有增量上屏路径消费。
   调度：每发布一块跑一轮（块内 SIMD 对稳态块长为毫秒级/词）。加载中途修改过滤条件：对已发布前缀走既有全量路径（`BlockScanEligible` 满足即块扫描），随后继续增量轮。
   不可扫形态（非 ASCII 词、超词数上限、小文档）沿用既有三条件分派，回退逐条增量（`FilterTail` 现状），行为仍正确。
   理由：分派逻辑已在 master，C′ 落点是该函数的形状拆分；备选 B（逐条 + 完成后重过滤）的重过滤语义冗余（两路径结论一致，重过滤无消费方）且逐条总量 ≈ 19 s 摊在加载期仍是最慢段，降级为兜底；A（加载期不支持 Message 过滤）牺牲可过滤性，仅作 raw 视图依赖不可行时的回退。

5. **raw 视图：加载期保持整文件映射**（D9 硬前提的落法）。分块管线不改变文档映射的生命周期——映射在加载期即存在，`OpenMessageSession` 照常提供基指针，块扫描增量轮直接复用；不为块扫描新造「自有缓冲区」形态。理由：优先复用既有模式；**需先核实**现状文档的映射是否在解析开始前就绪（见风险 1），若不成立再评估加载期建映射的成本。

6. **视图行号数组：分段可增量追加结构**（D10=B）。`_rows` 从「整表替换数组」改为分段块数组 + 段索引，覆盖 `SetRows` / `AppendRows` / `CaptureAnchor` / `PinAnchor` / `ModelRowOf` / `DocRow` 全部访问点。理由：4 MB 块长下整表拷贝已占 9%、1 MB 达 26%，为迁就不改 UI 而被迫用大块会把首屏从 212 ms 劣化到 539 ms，不划算；O(n²) 实测成立，必须根治。

7. **取消：整份清空**（D4=B）。沿用既有 worker 换代取消机制（`StopWorker` / `_workerGen`），分块管线在任意块边界检查取消；清空文档与视图回到空状态。理由：部分保留会引入「半份文档」的一致性问题（tag 重映射、崩溃事件、统计），清空语义最简单且可验证。

8. **加载期 UI**（D6=A / D11=A）：过滤器与时间过滤随发布增量生效；导出与崩溃面板置灰至完成；进度状态记录「已发布到第几块」。视图跟随沿用既有开关，不改语义。发布上屏按时间片节流（约 100 ms 聚合一批），避免高频 UI 抖动——块耗时 p95 在 16 MB 块下达 254 ms，逐块上屏会造成锯齿。

9. **存量私有设计处置**（D7=A）：以公开探索笔记为事实基座，不读、不引私有文档。

## Risks / Trade-offs

- [文档映射在加载期是否已就绪未核实——若现状是解析完成后才建映射，C′ 无指针可用] → 实施首任务先写探针/测试核实映射生命周期；不成立则评估加载期提前建映射（文件已打开，成本低），仍不可行则按决策 4 的回退链降级（增量逐条 → A）。
- [总时长持平略慢 2–5%，验收线 ≤1.05× 在边界] → 稳态 32 MB 降低块边界与 AlignEnd 回扫占比；探针口径 1.02–1.05，实施后以同口径复测，超线则调块长。
- [滞后一条发布使可见行数短暂少 1 条] → 用户不可感知（EOF 补发）；等价性测试覆盖「末条不滞留」场景。
- [分段行号结构改 6 个访问点，回归面大] → 虚拟列表行为有既有测试；为分段结构补等价性用例（`ModelRowOf` / `DocRow` 双向往返），UI 回归按 96 DPI 口径 + 用户实机验证。

## Migration Plan

- apply 在 change 专属 worktree（`wt/chunked-progressive-load`）实施，主树保持干净。
- 旧整份构建路径保留为内部等价性基准（等价性不变量测试依赖它比对），不作运行时开关；回滚 = git revert 整个 change。
- 测试口径按 AGENTS §一.4：dotnet test 优先，口径数字进 docs/TESTING.md。

## Open Questions

- 稳态块长默认值（32 MB）与发布节流时长（100 ms）为可调参数，实施期按探针复测微调，不影响 spec 与任务拆分。
