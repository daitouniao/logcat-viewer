# Design

## Context

本仓库当前的 MCP 资产只有一样：`mcp/` 下的 `logcat-mcp` 服务端（Node + TypeScript，stdio 传输，工具面仅 `info`，契约已归档于 `openspec/specs/mcp/server-shell/spec.md`）。本刀要加的是**另一个进程**——代理，与 `logcat-mcp` 并列而非复用它。

工程规范约束（来自 AGENTS.md 与 `openspec/config.yaml`）：产物用简体中文；规范只写行为契约（需求 + GIVEN/WHEN/THEN），实现细节归本文件；规范按实现代际分层，能力落 `openspec/specs/<分类>/<capability>/spec.md`，`mcp` 分类已于 2026-11-26 登记，故本刀落 `mcp/proxy`；新能力须走 OpenSpec 变更流程，评审通过后才编码；编码在变更专属独立 worktree 实施；测试用例数以 `docs/TESTING.md` 为唯一权威源。

工具链现状（实测，2026-11-27）：Node v26.8.1 / npm 11.19.0；npm registry 指向 npmmirror 镜像且可达（`registry.npmjs.org` HEAD 200）；`mcp/` 已装 `@modelcontextprotocol/server@2.4.0` 与 `zod@4.6.7`，TypeScript 5.9.3；**SDK v2 已拆包，仓库现只有 `server` 与 `core` 两个包，没有客户端包**——代理要用客户端侧能力必须新增 `@modelcontextprotocol/client` 依赖。

CI 现状（实测）：`.github/workflows/ci.yml` 已有 `mcp` 作业（windows-latest，node 版本矩阵 `['26','22']`，`npm ci` → `npm run build` → `npm test`）。代理工程按同一口径单开作业。

## Goals / Non-Goals

**Goals:**

- 产出可被真实 MCP 客户端拉起的代理：一次握手后，Agent 能看到全部上游工具并调用其中任意一个。
- 上游的增删改、启停、重启、状态查看有明确入口：页面给人类，工具给 Agent。
- 把「代理」的行为契约写成可测试的规范条款：配置、生命周期、命名空间、路由、错误、访问控制、退出纪律。
- 上游失败可归因：状态页与错误结果都要能指明是哪个上游、什么原因。

**Non-Goals:**

- 不接日志数据能力，不定义业务工具面（`MCP-FUNCTIONALITY.md` 的 D5 口径仍待拍板，与本刀无关）。
- 不做 http / sse 上游，不做上游认证与凭据保管。
- 不发布、不占公共包名、不进版本号同步点。
- 不改写、不裁剪上游工具的产出——聚合只做命名空间包装与路由。
- 不做代理的多实例、负载均衡、跨机部署。

## Decisions

### D1：代理是独立进程，不复用 `mcp/` 工程

**理由**：`logcat-mcp` 是一个日志服务端（未来会长出日志业务工具），代理是一个通用连接器（聚合别人的工具）。两者生命周期、依赖面、发布节奏都不同：代理依赖客户端 SDK + 服务端 SDK，日志服务端只要服务端 SDK；代理要常驻并管理子进程，日志服务端是被客户端拉起的短命子进程。塞进一个 npm 包会让「谁该装谁」的边界糊掉，也会让 CI 的构建与测试粒度跟着变粗。

**代价**：仓库多一套 Node 工程（第二份 lock 文件、第二套 node_modules）。

**缓解**：两工程目录相邻（`mcp/` 与 `mcp/proxy/`），共享同一 SDK 版本线与同一 TS 版本线；CI 两个作业口径完全一致。

### D2：SDK 选 v2 的 client + server 双包，沿用既有版本线

**理由**：v2（`@modelcontextprotocol/client` 2.4.0 / `@modelcontextprotocol/server` 2.4.0）是 MCP 当前的稳定线，与仓库既有的 `server@2.4.0` 同版本线，不引入第二套 SDK 世代；v1 单包会把 HTTP 与鉴权依赖拖进来，而本刀上下游都只用 stdio。

**代价**：v2 客户端包社区示例少于 v1；缓解方式同 `mcp-node-shell` 那刀——只依赖极小的 API 面（连接、列举工具、调用工具），且全链路测试兜底。

### D3：一个进程两副面孔

**理由**：下游对 Agent 是 MCP 服务端（stdio 传输），上游对各 MCP 是客户端（stdio 子进程）。同进程实现的理由有三：

1. 配置与进程一一对应：代理进程即配置实例，配置文件路径由启动参数决定，不存在「配置文件与运行实例不匹配」的两难；
2. 状态天然一致：页面看到的上游状态与 Agent 看到的是同一批连接，不存在两套状态要同步；
3. 退出纪律单一：一次退出即终止全部上游子进程，不需要额外的守护进程对账。

**代价**：代理崩溃会带走全部上游；stdio 上游本就是子进程，代理挂了就都断了，这个代价可接受。

### D4：管理页面用 Node 内置 `http`，单页 HTML，不引 Web 框架

**理由**：页面只做「看状态、增删改、启停、重启」六件事，一个 JSON API + 一张静态页足够；引入 express / hono 会带来 v1 明确排除的 HTTP 与鉴权依赖（与 `mcp-node-shell` D1 的裁剪口径一致）。Node 内置 `http` 足以支撑。

**页面形态**：单页 HTML（原生 JS，无构建步骤），通过 JSON API 轮询状态。理由：页面要能被本地文件与 http 两种方式打开都不现实，因此直接由代理自己 serve，端口可配。

**代价**：没有前端框架，页面代码要手写；但本刀页面交互面很窄，这个代价可控。

**端口与启动参数**：管理端口**默认取随机空闲端口**（理由见 D16），可用 `--port <端口>` 显式指定；另一个启动参数 `--config <路径>` 指定配置文件。参数口径固定在两个，避免引入子命令解析这层复杂度。

### D5：管理面只绑回环地址 + 启动随机令牌 + 校验 Host

**理由**：管理面能改配置、能启停进程，等于本机控制面。绑回环地址可挡住局域网访问；但**只绑回环并不足以防 DNS rebinding**（恶意网页可让浏览器把请求发向 `127.0.0.1`），故：

1. 启动时生成随机令牌，写入 **stderr**（stdout 是协议通道，绝不可污染）；
2. 页面 URL 带令牌，首次访问后由页面持有并以请求头回传；
3. HTTP 服务校验 `Host` 头为本机地址，拒绝指向别的 host 的请求。

**令牌的交付方式**：代理启动时把带令牌的页面地址写到 **stderr**，形如 `管理页面：http://127.0.0.1:<随机端口>/?token=<令牌>`。stdout 是协议通道，令牌绝不进 stdout。

**代价**：用户每次启动要拿到令牌（从 stderr 读，或让代理在启动时打开默认浏览器——本刀不做自动开浏览器，只在 stderr 打印带令牌的地址）。

### D6：配置文件在用户配置目录，仓库内只留示例

**理由**：配置文件里可能有环境变量形式的凭据（API key 等），写进仓库等于泄密。默认路径取用户配置目录（Windows `%APPDATA%\logcat\mcp-proxy\config.json`，其他平台 `~/.config/logcat/mcp-proxy/config.json`），可用 `--config` 覆盖；仓库内只提交 `config.example.json` 说明默认形状。

**代价**：首次使用需复制示例或由页面新建；页面支持「新增上游」时会自动创建配置文件目录与文件。

### D7：上游条目形状与 id 约束

**理由**：条目字段取最少必要集：

```
{ "id": "fs", "command": "node", "args": ["..."], "env": {}, "cwd": null, "enabled": true }
```

- `id` 是命名空间前缀，必须唯一，限定 `^[a-z0-9][a-z0-9_-]*$` **且不得含连续下划线 `__`**：工具名会拼进下游工具名，双下划线既会与分隔符混淆（`id=a__b, tool=c` 拼出 `a__b__c`，视觉上像三段），也会让「按分隔符切分反解」这种做法产生歧义（故路由改走对应表，见 D8）；
- `command` / `args` 描述 stdio 上游怎么起；
- `env` 透传给上游子进程（凭据的落盘处）；值取 `"env:VAR"` 形式时，表示**从代理进程的环境变量 `VAR` 读取、不落盘**（见 D17）；
- `cwd` 可选，默认继承代理进程工作目录；
- `enabled` 控制是否在启动时拉起。

**为什么不用 URL 形态**：v0 只支持 stdio（D9），字段里放 URL 会诱使后续实现「顺手支持 http」——这正是 `mcp-node-shell` D15 明确禁止的形状漂移。

### D8：工具名 `server__tool`，内置管理工具用 `proxy_` 前缀

**理由**：多个上游必有同名工具（几乎所有 MCP 都有 `search`、`read_file`）。前缀命名空间是唯一能让 Agent 无歧义选择、也让代理能路由的形态。两个下划线作分隔符，是因为 MCP 工具名惯例本身用下划线，单下划线会导致 `a_b` 与 `a__b` 歧义。

**路由走对应表，不做字符串反解**（2026-11-27 评审定）：代理在聚合期持有「下游工具名 → (上游 id, 上游工具名)」的对应表，调用时按表查上游，**不从工具名里切分隔符反推 id**。理由：分隔符在 id 与工具名两侧都可能出现（`id=a__b, tool=c` 与 `id=a, tool=b__c` 都拼出 `a__b__c`），字符串反解不可靠；对应表是注册期事实，无歧义。配套收紧：`id` 禁含 `__`（D7）；上游工具名不设门槛，但经 D18 规范化后落到下游名里的连续双划线会被压平，故下游名中至多出现一处分隔符。

**冲突处置**：若两个不同上游的工具拼出同一个下游工具名（注册期即撞名），先注册者保留，后注册的上游被标记为不可用并记录冲突原因，不静默覆盖。

**内置管理工具**：`proxy_servers`（列出上游状态、工具数、最后错误）与 `proxy_restart`（重启指定上游）。它们用 `proxy_` 前缀，不参与命名空间（2026-11-27 评审定：保持扁平名，不改成 `proxy__servers`）。与上游命名空间不冲突——分隔符是双下划线，`proxy_servers` 永远匹配不上 `id__tool` 的形状；且 `id` 禁含 `__`，故不存在 `id=proxy` 造成的视觉混淆。**保留这一取舍的代价**：下游工具名有两种形状（`fs__read_file` 与 `proxy_servers`），换来的是内置工具名不被上游撞名——上游极可能自带 `list_upstreams` 这类名字，若内置工具也走扁平名，撞名会在注册期把某个上游判死，代价不对称。

**代价**：Agent 看到的工具名比上游长（`fs__read_file`）。这是命名空间化的固有代价，换来的是无歧义。

**下游可执行入口**：代理工程在工程清单中提供 `bin` 字段，可执行名取 **`logcat-mcp-proxy`**。理由：MCP 客户端只认「命令 + 参数」，给出一个稳定可执行名后，各 Agent 的客户端配置只需一行（`logcat-mcp-proxy`）即可直连代理——这正是「各 Agent 直接连这个代理」的落地形态。名字一旦对外就难改，故与 `logcat-mcp` 同风格取名但不同名，避免两者在客户端配置里混淆。

### D9：上游连接模型——每上游一个常驻子进程，代理内共享

**理由**：stdio 上游是子进程，天然单例。代理为每个 `enabled` 上游维护一个子进程与一条客户端会话，**所有下游客户端共享**这些会话。

**为什么共享而非每客户端独立**：独立会让上游进程数随下游连接数放大（N 个 Agent × M 个上游 = N×M 个进程），且重启语义会变得模糊（重启一个上游要重启 N 份）。共享的代价是上游会话的状态（如订阅型能力）跨客户端共享——但 stdio 上游在 v0 没有有状态资源能力，这个代价在本刀不显现。

**限制声明（2026-11-27 评审定）**：v0 **不做**按下游 Agent 隔离上游会话。因此若两个 Agent 需要同一上游的**不同凭据**或不同订阅状态，v0 无法满足——这类需求需另起切片（把凭据与状态下沉到「同一上游多实例」形态）。此限制写明在此，避免后续把「共享」误读为「已支持多租户」。

**上游重启**：销毁子进程与会话，重新拉起，重新列举工具，随后工具集合刷新。重启期间该上游的工具从下游列举结果中消失（不是返回错误条目），避免 Agent 调到死工具。

### D10：错误语义与错误码

**理由**：Agent 面对失败要能分清「我调用方式错了」与「上游坏了」——两者的纠正动作完全不同（改参数 vs 换上游/稍后重试）。故错误码分族：

| 错误码 | 含义 | 纠正方向 |
|---|---|---|
| `TOOL_NOT_FOUND` | 工具名不存在（含前缀无对应上游、或上游未提供该工具） | 换工具名 |
| `TOOL_FAILED` | 入参不符合工具输入模式（沿用 `server-shell` 码族） | 改参数 |
| `UPSTREAM_UNAVAILABLE` | 上游未运行 / 拉起失败 / 连接断开 | 换上游或稍后重试 |
| `UPSTREAM_TOOL_FAILED` | 上游工具自身处理失败 | 换用法或换上游 |

**理由沿用 server-shell 的 `TOOL_` 族**：代理与 `logcat-mcp` 是两套进程，但错误码族对 Agent 是一致的更友好；`UPSTREAM_` 是新增的第二个族，只描述代理特有的失败。

**代价**：错误码从一个族变两个族，客户端若按前缀通配需注意。

### D11：上游诊断输出留尾部，供页面查看

**理由**：上游起不来时，最有价值的信息在它的 stderr。代理把每个上游的 stderr 收进环形缓冲（默认保留最后 200 行），页面可看。代理自身的诊断一律走 stderr。

**为什么上游 stdout 不能碰**：上游 stdout 是它的协议通道，代理只做 JSON-RPC 帧的读取与转发，不得写入或混入。

### D12：代理退出时终止全部上游子进程

**理由**：与 `server-shell` 的孤儿进程纪律同源。代理作为客户端拉起子进程，若代理先退，上游会残留成孤儿继续占端口与内存。

**代价**：代理被强杀（SIGKILL）时来不及清理上游——这是操作系统层面的普遍问题，本刀不追求绝对兜底（可后话：上游进程用进程组 + `detached: false` 并在代理退出时统一 kill）。

### D13：本刀不做的事（明确的边界清单）

- 不做 http / sse 上游、不做上游认证与凭据保管；
- 不做 **HTTP 下游传输**（见 D16）——本刀下游只有标准输入输出；
- 不做按下游 Agent 隔离上游会话（见 D9 的限制声明）；
- 不做工具级的暴露开关（上游工具全量聚合；页面只能整体停用某个上游）；
- 不做代理自身的 MCP 资源（resources）与提示（prompts）能力——只暴露工具；
- 不做工具结果的改写、裁剪、限流与审计；
- 不做多代理实例、负载均衡、跨机部署；
- 不做上游工具的按需加载（全部上游工具一次性聚合暴露）；
- 不发布。

### D14：配置写入的原子性

**理由**：页面改配置 → 代理落盘。若写到一半进程被杀，配置文件会损坏，用户下次启动全部上游都起不来。故写入走「临时文件 + rename」，rename 在同一文件系统内是原子的。

### D15：TypeScript 锁 5.9.x

**理由**：与既有 `mcp/` 工程同版本线（5.9.3），不引入第二个 TS 版本面。

### D16：下游传输限定为标准输入输出；管理端口默认随机

**理由**：下游只用标准输入输出承载协议，与 `server-shell` 的传输纪律同源；管理端口**默认取随机空闲端口**——代理是本机工具，多实例并存是常态，固定端口必然撞，随机端口把「端口冲突」这类失败模式整个消掉，且页面地址本来就要写到 stderr（令牌同处）。`--port` 可显式指定。

**代价（须写明，不可含糊）**：只支持 HTTP / SSE 的 MCP 客户端**连不上**代理——本刀的兑现面是「能以子进程方式拉起 stdio 服务端的客户端」。HTTP 下游列为下一个切片的候选（要自带鉴权与会话管理，工作量约等于再加半个管理面）。

**为什么必须写明**：本刀的目标是「各 Agent 可直接连这个代理」。若不显式限定，受众会以为任何客户端都能接，HTTP-only 客户端的失败会表现为「连不上」，极难归因到「v0 不做 HTTP 下游」这条设计取舍。

### D17：凭据可从外部环境变量引用，不落盘

**理由**：`env` 值取 `"env:VAR"` 形式时，表示从代理进程的环境变量 `VAR` 读取、不写入配置文件。这给不愿明文落盘的用户一条成本极低的出路（代价只是启动时多设一个环境变量）。明文直写仍被允许，但页面一律掩码显示、写回不覆盖原值。

**代价**：多一种取值形态，配置校验与页面掩码逻辑要多处理一种情况。

**排除项**：系统钥匙串（keychain / credential manager）跨平台成本高、维护面大，本刀不做，留待后续。

### D18：校验对象是「代理对外暴露的下游名」，上游名不设门槛（**2026-11-27 定**）

**事实（实测）**：MCP SDK v2 的 `ToolSchema` 继承 `BaseMetadataSchema`，其中 `name: z.string()` —— **无正则、无长度上限**（`node_modules/@modelcontextprotocol/core/dist/schemas-*.mjs`）；协议 2025-11-25 线同样只把工具名定义为普通字符串。故「按 MCP 规范校验上游名」本就没有可执行的判据。

**定案（维护者拍板）**：**这次是代理、且有对应表**——路由由注册期对应表决定，不依赖名字切分。故**上游（stdio）的工具名可以随意**，合规性由**代理对外暴露的下游名**承担：代理保证自己吐给下游的名字合规，原始名不合规时由代理规范化。

**规则**：

1. 下游名 = `<id>__<上游名>`；
2. **下游名的合规口径**：`^[a-zA-Z0-9_-]+$`、总长 ≤ 64、不含 `__`、不与内置工具名（`proxy_servers` / `proxy_restart`）撞名；
3. 上游名不满足第 2 条时，代理做**受控规范化**：非法字符替换为 `_`；上游名中的连续双下划线压为单下划线；超长时按「id 段完整保留、工具名段截断」处理；
4. **规范化只影响寻址与展示**：调用仍路由到该上游的**原始**工具（由对应表保证，不会调错），**原始名写入工具描述**，让 Agent 与人仍能识别它；
5. 规范化后仍与其他工具撞名 → 沿用 D8 的处置（先注册者保留，后注册者判不可用并记冲突原因）；
6. **另一件事，别混**：上游返回的工具**定义**（名称、描述、输入模式的形状）须符合 MCP 协议，由 SDK 校验；不合规的上游响应按协议失败处置，该上游不可用——这与命名口径无关。

**代价**：Agent 看到的工具名可能与上游原名不完全一致（规范化痕迹），靠工具描述补回可读性。**收益**：stdio 上游可以随意命名工具，不会因名字怪癖整个上游不可用——这是「代理」相对「直连上游」的核心价值之一。

**与 D8 的关系**：D8 的「对应表消歧」是**路由**层的防线（不切分名字）；本条是**展示与寻址**层的防线（名字合规）。两层独立，叠加后下游名既无歧义又合规。

### D19：与 `mcp/` 既有 `npm run harness` 分工

**理由**：仓库已有一个「把 stdio 服务端桥成 HTTP」的网页调试台（`mcp/dev/web-harness.mjs`，`npm --prefix mcp run harness`），与本刀的管理页面在形态上都是 HTTP + 网页。若不写明分工，两个 HTTP 桥并存会让人误以为是同一个东西。

**分工**：harness 是**开发期调试单服务端**的工具（看工具清单、调工具、看原始 JSON-RPC 流量，服务于 `logcat-mcp` 自身开发）；代理是**运行期聚合多上游**的管理与路由层（面向使用者配置与运维）。两者不互相替代，也不共享代码。

**落地**：在 `docs/BUILDING.md` 的代理章节与本 change 的 tasks 9.2 同时写明这一区分。

## Risks / Trade-offs

- **v2 客户端 SDK 较新、API 形态可能与预期有出入** → 只依赖极小的客户端 API 面（连接 / 列举 / 调用 / 关闭），并用「拉起真实上游子进程」的端到端测试兜底；仓库内已有 `logcat-mcp` 可作真实上游，减少造桩成本。
- **上游工具名可能不符合下游可用性要求**（部分实现含 `:` `/` 等字符）→ 代理对外暴露的名字由代理保证合规（D18）：非法字符替换、连续双下划线压平、超长截断；原始名写入工具描述，调用仍路由到原始工具。
- **下游只有 stdio，HTTP-only 客户端接不上** → 属 v0 的显式边界（D16），须在 proposal 范围外、design 与构建文档中同时写明，避免失败被误判为缺陷。
- **上游拉起失败拖慢启动** → 上游拉起并发执行，单个上游失败不阻塞代理进入可服务状态（该上游工具缺席即可）。
- **管理页面的 XSS** → 页面渲染上游名与工具名时按文本转义，不拼 innerHTML。
- **配置里含凭据** → 页面不回显 env 明文（统一掩码），写回时掩码值保留原值不被覆盖。
- **代理常驻占资源** → v0 无内存上限要求；但上游 stderr 环形缓冲有行数上限（200 行）。
- **第二套 Node 工程抬高维护成本** → 与 `mcp/` 共用 SDK 版本线与 TS 版本线；CI 两个作业口径一致；若后续证明 Node 路线成本过高，可整体换语言而不动已冻结的契约。

## Migration Plan

不涉及迁移：新增独立工程，既有 `mcp/` 服务端、Rust workspace、C# 宿主与既有规范均不改动，无数据迁移、无既有行为变更。回滚即删除 `mcp/proxy/` 目录与 `openspec/specs/mcp/proxy/` 目录，并从 CI 移除作业。
