# Proposal

## Why

每次修改 message 过滤条件，`ApplyFilter` 都要全量重跑。1 GB 日志（1582 万行）上，用户改一次过滤条件要等 3.0–3.3 s（实测 6069–6564 ms）——其中绝大部分时间花在「每行 `new byte[]` + `ReadArray` 拷贝」上，与用户真正关心的「哪几行命中」无关。

改造后同一操作降到 1.1–1.3 s（实测 2160–2426 ms，段 2 口径；完整 ApplyFilter 口径为 3100–3368 ms），过滤结果**逐行完全一致**（14 组过滤规格 × 1582 万行实测验证，`MsgOp` 显式指定，含真 or 模式）。

## What Changes

- **message 过滤改为零拷贝读取**：不再为每条候选记录分配临时字节数组并拷贝，直接在内存映射的文件内容上定位与比较。
- **显式实现大小写不敏感的字节级比较**：纯 ASCII 行走「字节级忽略大小写」快路径；含非 ASCII 字符的行仍走 Unicode 小写化路径，两条路径的命中结论与改造前逐行一致。
- **匹配算法用候选首字节定位**替代逐位置朴素比较：先按首字节（大小写两种形态）定位候选位置，再逐字节验证后续字符。实测该形态比朴素逐位置比较快约 2 倍，且不改变命中集合。
- **message 过滤的读取契约收敛到文档层**：文档对外提供只读正文读取会话（**会话对象 + 回调取正文**，正文 span 只在回调期间有效、不允许逸出），过滤引擎不再自行拼装偏移量与拷贝缓冲。

### 非目标（out of scope）

- **不改列布局**：文档的定长列数组与公开列视图 API 保持不变（`SIDECAR-CACHE-INDEX.md` 依赖此前提）。
- **不做落盘缓存**：属 `SIDECAR-CACHE-INDEX.md` 的范围。
- **不做 SIMD 块扫描 / 全文顺序扫描**：属 `UTF8-BYTE-SIMD-SEARCH.md` 的后续路线。本次只在「按行取正文」这一层做零拷贝，不引入块级扫描与并行分块。
- **不做结构体重排（AoS）**：实测段 1 预筛只占全量过滤的 4–9%，收益上限 9%，而内存流量会恶化 32 倍，不划算。
- **不改用户可见的过滤语义**：命中集合、and/or 组合、空过滤词、排除语义、大小写等价规则全部保持不变；本 change 不引入任何新的用户可见行为。

## Capabilities

### New Capabilities

- `message-filter`: message 正文过滤的判定契约 —— 匹配作用域、大小写等价规则、多关键词组合语义、排除语义、增量与全量路径的一致性。本 change 不改变这些行为（改造前后命中集合逐行一致，已实测），但既有 message 过滤语义此前只由单元测试钉住、没有规范承载；本次正好重写了大小写比较的实现路径（从「拷贝后折叠」改为「字节级比较」），是把这批易错语义固化为规范契约的时机。

### Modified Capabilities

（无）—— `time-column` 等既有能力的过滤维度（分钟 / 级别 / tag）均不受本 change 影响。

## Impact

- **代码**：
  - `Services/LogDocument.cs`：新增只读正文读取会话（会话对象 + 回调取正文），供过滤引擎零拷贝消费；会话**复用文档已有的 `_view`**（其容量随 `Append` 重映射，越界读会导致进程段错误，故不可自持独立映射）。现有 `MessageBytes` / `LineBytes` / `HeaderBytes` 等公开读取接口保持不变，外部调用方（列表渲染、崩溃时间、导出、查找）不受影响。
  - `Services/FilterEngine.cs`：message 过滤路径改为零拷贝读取 + 字节级比较；and/or 组合、空过滤词、排除语义、大小写处理规则保持原有结论。
- **测试**：`tests/logcat.Tests/FilterEngineTests.cs` 现有 message 相关用例全部继续有效（语义不变）；新增回归用例锁定「改造前后命中集合逐行一致」与新读取路径的正确性。回归对照须**显式指定 `MsgOp`**（`FilterSpec.MsgOp` 默认值为 `"and"`，不显式指定则 or 规格实际跑的是 and 语义 —— 探索阶段的 11 组规格即因此未真正覆盖 or 模式）；中文 needle 须选样本中真实出现的串（本样本「连接」「中文」出现 0 次，用之对照为空转，「加载」出现 250,156 次）。
- **性能**：1 GB / 1582 万行实测，同会话三轮取区间。忽略大小写（UI 默认模式）：完整 ApplyFilter 由 7668–7809 ms 降至 3100–3368 ms（2.28–2.49×），段 2 单独由 6069–6564 ms 降至 2381–2426 ms；大小写敏感模式：完整 ApplyFilter 由 2173–2451 ms 降至 1082–1221 ms（**1.93–2.18×**）。300 MB 样本同向（CI 2.36–2.57×、CS 1.97–2.42×）。**验收线按 CI ≥ 2×、CS ≥ 1.9× 分档** —— CS 本身是现状最快的一条（无需折叠），按 2× 硬卡会迫使实现引入与收益不成比例的复杂度。实时采集的增量过滤走同一条路径，同样受益。
- **无新增依赖**；主工程 csproj 需加 `AllowUnsafeBlocks`（零拷贝指针所需，`unsafe` 上下文），无 API 破坏性变更（新增接口为追加）。
