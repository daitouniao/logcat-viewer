## 背景

新壳日志视图的列宽是自绘画布内的固定常量。用户反馈 Tag 列过宽内容压到 Message 列（叠字），且表头与实际列错位。已按 A 方案修复：按列裁剪、Tag 列 154 → 200、表头位置改为与列起点同源。

A 方案只解决「不叠字、不错位」；**列宽仍不可调整**。本卡登记 B 方案：允许用户拖拽调列宽。

## 现状事实（2026-11-26）

- 列起点是 `LogCanvas.ColumnStarts = { 0, 62, 190, 258, 326, 356, 556 }`，宽度依次为 62 / 128 / 68 / 68 / 30 / 200 / 剩余。
- 表头是 XAML 里的 7 个 `TextBlock`，启动时按同一份常量定位（`MainWindow.LayoutHeader`）。
- 画面自绘在 `LogCanvas.Render`：只画视口行，文本按列裁剪（`DrawCell` → `PushClip`）。
- 滚动由上层 `ScrollViewer` 驱动，画布本身 `IsHitTestVisible="False"`；表头所在区域当前不可交互。
- 设置层（`avalonia-app-storage`）已具备带版本号的设置文件与单一写入入口，可承载列宽持久化。

## B 方案范围

- 表头列分隔线可拖拽；拖拽时实时重绘（自绘只需改常量并 Invalidate）。
- 双击分隔线：按该列内容宽度自适应（需要能看到当前页文本宽度，可能只按可见页估算）。
- 最小列宽（建议 24 px），且总和超出窗口时允许横向滚动或压缩 Message 列。
- 列宽持久化到设置文件（新增键，带默认值；旧设置文件无该键时使用默认宽度）。

## 需要维护者决策

1. **交互形态**：只做拖拽，还是同时做双击自适应？（双击需要定义「按哪一页的内容算宽」）
2. **持久化粒度**：只存用户改过的列，还是存整组宽度？列数将来变化时如何降级？（建议存整组 + 数量不匹配则回默认）
3. **窗口变窄时**：压缩 Message 列、保底最小宽度，还是出现横向滚动条？（建议后者，避免 Message 被挤到不可读）
4. **与语言的关系**：列名（Time / PID / Tag）是域常量不本地化，列宽不应随语言变化——确认是否维持。
5. **是否复用设置层**：列宽进入 `next-settings.json`（需新 change 扩展 schema 到 v2 或新增键并保持 v1 兼容读取）。
6. **归属**：单独 change（`avalonia-log-columns`）还是并入下一次 UI 迭代？建议单独，因涉及设置 schema 演进与交互验收。

## 风险与实现注意

- 表头在 XAML、数据在自绘画布：两处必须共用同一份列常量，否则会再次错位（A 方案已建立该约束）。
- 拖拽态需要在表头放一层可命中测试的覆盖物；注意不要拦截菜单/滚动条的事件。
- 自绘裁剪已存在，列宽变窄时超长文本会截断而非溢出——符合预期，但需要确认「截断 vs 省略号」的表现（建议先截断，不引入省略号测量开销）。
- 列宽写入设置文件会触发「外部修改不热加载」的既有约定：拖拽后应立即生效并落盘，重启后保持。
