## 基础需求

**用户画像（维护者口述，2026-10-13）**：日常日志 300–500 MB、多在 SMB、**一个目录多文件是高频场景**、文件按时间前后关系成序列、多 bug 调查会反复打开同一个 log、最疼的是「找时间点在哪个文件里面」。

**用户故事**：报障说「10 月 12 日下午 3 点左右崩了」，我有一个按天/按次导出的日志目录——

1. **哪个文件覆盖那个时间？** 不想逐个打开 300 MB 文件试。
2. 打开后**跳到那个时刻**，不想手动滚十分钟。
3. 查第二个 bug 时**切回同一个文件**，过滤条件、标记、位置还在。

**范围**：

| 做 | 不做 |
| --- | --- |
| 时间覆盖扫描（不加载文件即知其时间范围） | 并排双文档对比（内存否决） |
| 目录列表面板（目录内按时间排序） | 跨文件聚合搜索（跨文档架构，另立需求） |
| 快速切换器（目录内 LRU + Ctrl+Tab） | 目录拖放展开（v1 范围外） |
| 每文件轻量状态持久化（过滤/标记/位置） | 文件名时间兜底（不可信） |
| 跳转到时间 | 旁车索引缓存（属性能轨道，另议） |

**两条硬约束（需求成立的前提）**：

1. **内存**：列索引 ≈ 0.75 × 文件体积；500 MB 单文档索引 ≈ 0.4 GB，两份同时开着 ≈ 0.8 GB+，顶到单文档 ≤ 2 GB 目标 → **并排对比否决，切换必须「卸载旧的再开新的」**。
2. **`YearTables` 无锁静态可变缓存**：原设计把「跳转到时间会让 UI 线程成为第二个写入方」列为跳转功能的硬前置。**现状已变**：该表随 change `2026-10-24-minute-byte-column`（已归档）删除，重启时须按分钟列重新评估线程安全前置是否仍然成立（不假设结论）。

**状态持久化口径**：每文件状态必须走「立即落盘」先例（`FavoritesStore` 模式：`Changed` 事件 + 单测设施），不能沿用 `AppSettings` 关窗才落盘（崩溃即丢）。切换文件 = 关闭当前文档 + 打开目标，与既有取消语义（Esc = 回退清空）同构，不需要新状态机。
