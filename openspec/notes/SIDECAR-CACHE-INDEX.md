## 1. 目标与范围

**问题**：重开一个 1 GB 日志文件，`LogDocument.Build` 需 14.8–18.5 s（解析 + 九列物化 + 终算），期间界面无内容。

**本 change 做什么**：把建好的列索引落盘成 sidecar 文件，重开同一文件时直接加载索引、跳过解析。

**本 change 不做什么**：
- 不做过滤加速（属 `FILTER-ACCEL-ZERO-COPY.md`）
- 不做流式加载 / 首屏快（属 `STREAMING-FILE-LOAD.md`，D1–D4 已拍板、D5–D11 仍待定）
- **不改列布局**（见 §3 结论 1：sidecar 沿用现状 SoA 9 段）

## 2. 现状（代码事实）

`LogDocument.DoBuild` → `ScanRange`（单遍扫全文件 → `ParseLine` → 写 9 个 List → tag 字典）→ `Assemble`（`FinalizeTs` 终算 → `ToArray` 物化 → `SetColumns`）。

1 GB 文件实测分解（`STREAMING-FILE-LOAD.md` 探针口径）：逐行 `ParseLine` 6–9 s + 九列物化 4–7 s + 终算/组装 2–4 s；本地 SSD 冷读仅 2.5 s。→ **纯 CPU 瓶颈，可被缓存跳过**。

## 3. 实测基线（2026-10-25）

样本：`testdata/big_test.log`，1.02 GB，15,823,120 行，145 tag，热缓存。

### sidecar 落盘与加载

| 环节 | SoA 9 段布局 | AoS 定长记录 |
| --- | --- | --- |
| 写 sidecar | 1435 ms | 989 ms |
| sidecar 体积 | **0.457 GB** | 0.472 GB |
| **加载 sidecar（= 缓存命中的重开）** | **459 ms** | 509 ms |
| 相对首次 Build（14.8 s） | **32× 提速** | 29× 提速 |

- 加载后立即做零拷贝过滤：915 ms → 验证 sidecar 命中后仍走零拷贝路径可行。
- sidecar 命中的重开**仍需 mmap 源文件**（文本本体不在 sidecar 里），页读按需发生。

**结论 1 · sidecar 落盘应沿用现状 SoA 9 段，不改 AoS**

原文建议「B 的落盘格式可直接采用 A 的结构体（AoS 定长记录）」。**实测推翻**：

| | SoA 9 段（现状布局） | AoS 定长记录 |
| --- | --- | --- |
| sidecar 体积 | **0.457 GB** | 0.472 GB |
| **加载（缓存命中的重开）** | **459 ms** | 509 ms |
| 加载后内存布局 | **与现状完全相同** | 变成 AoS，需重建成结构体数组 |
| 与过滤加速 change 的关系 | **无冲突** | **冲突**：内存布局变了，段 1 预筛要重写 |

- SoA 加载更快（459 vs 509 ms）且体积更小：SoA 读回后**直接就是内存里那 9 个数组**（零转换）；AoS 还要把连续记录重建成结构体数组（多一次 0.47 GB 拷贝）。
- **关键收益是解耦**：内存布局不变 → 与过滤加速 change **互不牵制**，可独立实施、独立验证、独立回滚。
- 代价：sidecar 是「9 段变长段」而非「定长记录流」，失去「流式追加友好」。但 sidecar 是**一次性整体写、整体读**的离线文件，不需要流式追加 → 该代价不成立。
- 原文「AoS 是 B 的价值所在」随之作废：AoS 唯一还站得住的场景是**流式加载时的逐块发布**（`STREAMING-FILE-LOAD.md` 摩擦点 1、2），与 sidecar 无关。

### sidecar 需落盘的数据量与体积要素

1 GB 文件实测：

| 要素 | 数量 | 体积占比 |
| --- | --- | --- |
| 行记录（9 列 SoA） | 15,823,120 | **0.457 GB（源文件的 47.2%）** |
| tag 字典 | 145 项 | 可忽略 |
| 异常类型字典 | 13 项 | 可忽略 |
| 包名字典 | 17 项 | 可忽略 |
| 崩溃事件（稀疏） | 592 项 | 可忽略 |

**结论 2 · sidecar 必须连带记录 join 模式**：崩溃事件用「文档行号 + 字典 id」定位，而 join=true/false 的行号语义不同（join=true 会把续行合并进上一条记录）→ 同一源文件在两种 join 下的索引不可混用。

## 4. 已定：落点 = exe 同级

- **结论（2026-10-25，维护者）**：sidecar 缓存放 **exe 同级**。
- **与现有惯例一致**：exe 同级已有 `settings.json`、`commands.json`、`favorites.json`、`Log/startup.log`、`temp/logcat-proxy/`；`SpoolPaths` 文档明写「exe 目录可写是既有前提」。
- **实测支撑**：SMB 实测 7 MB/s → 缓存若放共享目录，读回 0.457 GB ≈ **71 s**；而 SMB 冷读原文件 1 GB ≈ 146 s + 解析 13–18 s ≈ 161 s。**「亚秒级重开」只在缓存落本地盘（exe 同级）时成立** → 落点决策与收益承诺绑定，不可分开。
- **写失败降级**：exe 目录不可写（权限 / 只读部署 / U 盘写保护）时须静默降级为「无缓存、走原路径」，不得影响打开流程。`AppSettings.SaveTo` 与 `StartupLog.Write` 已有同类先例：异常被吞 + 留痕。

## 5. 待决策项

### D5 · 缓存的键与失效判定

- **为什么需要澄清**：落点定了（exe 同级），但**一个 exe 目录要服务多个日志文件**（维护者画像：单目录多文件高频）→ 缓存文件必须能唯一定位到「源文件的哪一份索引」，且源文件一变必须失效重建。
- **选项**：
  - A **按源文件路径派生名 + 文件身份校验**（size + mtime + 首尾哈希，任一失效即重建）。**← 倾向**
  - B 按内容哈希命名：读全文件算哈希 → 与「打开要快」的目标自相矛盾，排除。
  - C 只按 size + mtime：同大小同修改时间的替换文件会命中错误缓存 → 需补首尾哈希兜底。
- **需要维护者回答**：命名规则取哪种？（建议：路径哈希 + 可读前缀 + size/mtime 摘要，既能区分同目录不同文件，又不在文件名里暴露本机绝对路径 —— AGENTS.md §一.2）
- **衍生**：缓存文件名不得包含本机绝对路径明文。

### D6 · 体积上限与清理策略

- **为什么需要澄清**：实测 sidecar = 源文件的 **47.2%**（1 GB → 0.457 GB）。exe 同级目录若无限增长会撑爆磁盘（便携工具常放 U 盘 / 系统盘）。
- **选项**：
  - A **总量上限 + LRU 淘汰**：缓存总量不超过 N MB，超限按最近使用时间淘汰。**← 倾向**
  - B 单文件上限：只限制单个 sidecar 大小 → 拦不住多文件累积，排除。
  - C 不限 + 手工清理：与「不加手动清理按钮」的既有偏好（`RESTART-BACKLOG.md` C1 已拍板）冲突，且长期占盘。
- **需要维护者回答**：**总量上限取多少？**（1 GB 文件占 0.457 GB → 上限 2 GB 约容 4 个大文件；5 GB 则约 10 个）
- **衍生**：淘汰时不得删除正在使用的缓存（需与打开中的文档互斥，参照 `SpoolDir` 活性锁机制）。

### D7 · 与「文件被追加 / 实时采集」的交互

- **为什么需要澄清**：`LogDocument` 有增量路径（`Reload` / `Append`），实时 adb 采集的文件**持续增长**。源文件在增长 → sidecar 必然过期。
- **选项**：
  - A **增长中的文件不写 sidecar**：只对静态文件（size 稳定）落缓存；采集文件每次重建索引。**← 倾向**
  - B 支持增量更新 sidecar：复杂度高（追加写 + 处理续行合并的 carry 状态），且采集路径本身不慢（增量扫描），收益低。
- **衍生**：写入时机判定 —— 「本次 Build 完成且文件 size 在构建期间未变」才落盘；否则跳过并留痕。

## 6. 实施要点（design 参考）

- **落盘格式**：9 段变长段（offs / lens / moff / pid / tid / tagId / min / lvl / flags），段内为定长原始类型字节，段间连续。加载时**直接读进现成的 9 个数组**（零转换）。需带版本号以便格式演进。
- **字典**：tag / 异常类型 / 包名三个字典随 sidecar 落盘（数量小，可忽略体积）。
- **崩溃事件**：按「行号 + 字典 id」落盘（592 项，可忽略体积）；**必须连 join 模式一起记录**（结论 2）。
- **身份校验**：size + mtime + 首尾哈希，任一失效即重建（D5 待定命名规则）。
- **接入点**：`LogDocument.Build` 之后判定是否落盘；加载路径在 `DoBuild` 之前分流（命中则跳过 `ScanRange` + `Assemble`，直接 `SetColumns` + 恢复字典与崩溃事件）。
- **与流式加载的关系**：sidecar 命中时流式解析被绕过；两者目标不同（重开全量就绪 vs 首屏快）但同属「打开加速」，design 需说明先后与互斥点。

## 7. 验收线（建议）

- **正确性**：sidecar 命中路径产出的文档与「从零 Build」路径**完全等价** —— 行数、9 列内容、tag 字典、崩溃事件、join 语义全部一致（需专项对比测试）。
- **性能**（1 GB 文件）：sidecar 加载 ≤ 600 ms（实测 459 ms）；首次 Build 不劣于现状（≤ 18.5 s × 1.05）。
- **降级**：exe 目录不可写时静默走原路径，打开流程不受影响。
- **失效**：源文件被修改（size / mtime / 首尾哈希任一变化）后必须重建，不得命中过期缓存。
- **体积**：sidecar 总量不超 D6 定的上限；淘汰不误删使用中的缓存。
