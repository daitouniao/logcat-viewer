# 探索结论：边加载、边解析、边显示（IO / CPU 卡点探针）

- 状态：探索完成，**待维护者决策**（未建 OpenSpec change，未改动仓库代码）
- 日期：2026-10-24
- 关联提交：无（探针为临时工程 `.tmp-test/BenchLog`，已被 `.gitignore` 忽略，不入库）
- 验收结论：不适用

## 结论摘要

1. **卡点不是单一答案，取决于文件所在路径**：
   - 本地 SSD：**CPU 主导**。1 GB 文件 `Build` 17.6 s，其中冷读 IO 仅 2.5 s（14%），其余 15.1 s 是解析、列物化、终算与组装。
   - 网络 SMB：**IO 主导**。176 MB 冷读 25.6 s（7 MB/s），同份数据的 CPU 解析 + 列物化仅 3.7 s（约 10%）。
2. **流式化对两类路径的价值不同**：本地盘不缩短总时长，买到的是首屏（4 MB 块首块 25–46 ms）与内存（当前 1 GB 文件峰值工作集 4.6 GB）；网络盘的重点是把传输与解析重叠，但当前代理路径是「先整份 spool、再 Build」，要吃到这部分收益需改跨进程边界。
3. **可复用的原语已经存在**（`LogDocument.Append` / `FilterEngine.FilterTail` / `LogListView.AppendRows`），不是从零造管线；但有三个代码事实会直接卡住「逐块发布」，见「摩擦点」。
4. 现有全量管线是「一次 `new byte[rangeSize]` 读全文件 → 单遍扫描 → 建完才显示」，首屏时间 = 全量耗时。

## 探针口径

- 探针工程：`.tmp-test/BenchLog`（`dotnet run -c Release --project .tmp-test/BenchLog -- iocpu <file>`；`chunks` 子命令跳过 `Build`）。**不入库**，克隆者无此脚本；本笔记记录口径与结果，供后续复现时重建。
- 探针进程可见逻辑 CPU：8 个（`Environment.ProcessorCount`；机器本体为 36 核 / 72 逻辑处理器，`Build` 单线程，不影响墙钟对比）。
- 本地样本：`testdata/big_test.log`，1024 MB，15,823,120 行 / 15,823,120 条记录，145 tag，592 崩溃（与既有基线一致）。
- 网络样本：真实 SMB 共享上的 176 MB 日志，3,063,986 行 / 2,719,107 条记录。
- 口径说明：冷/热 = 同一进程内首次 / 第二次顺读同一文件；「折算全文件」= 256 MB 取样测量值按字节线性外推；解析是内存内测量，不碰磁盘。

## 现状管线与卡点判读

```
 打开文件（frmMain.StartIndex）
        │
        ▼
 BuildAsync ──► ScanRange：new byte[rangeSize] 一次读全文件（1 GB LOH）
        │         └─ 单遍：切行 → ParseLine → 写 10 个 List → tag 字典
        │         └─ 进度条只报百分比，列表区为空
        ▼
 Assemble ──► FinalizeTs 终算 → ToArray 物化 → 建立 _ts 等列数组
        │
        ▼
 SetDocument + ApplyFilter（默认筛选，全量） ──► 首屏可见
```

- 首屏 = 全量构建完成，**没有任何增量发布**（`frmMain.cs` L1004–L1027）。
- 本地卡点：CPU（解析 6–9 s + 列物化 4–7 s + 终算/组装约 2–4 s），IO 冷读仅 2.5 s。
- 网络卡点：IO（7 MB/s 冷读），CPU 只占约 10%。
- 现有 `Append` 已经实现「增量并入」：carry 续行、tag 复用重映射、增量 `FinalizeTs`（支持 prev 状态）、崩溃并入、`OpenMap` 重映射。实时 adb 抓取走的正是它 + `FilterTail` + `AppendRows`。

## 摩擦点（代码事实，需在设计中正面处理）

1. `LogDocument.Append` 每批末尾都调用 `OpenMap()`（`Services/LogDocument.cs` L1031 附近）——静态文件加载没必要每块重映射，250 块就是 250 次映射/退场。
2. `LogListView.AppendRows` 每次 `new int[oldLen + newLen]` 整表复制（`Controls/LogListView.cs` L94–L103）——adb 每批 500 行无感，全量 1583 万行分 250 块发布是 O(n²) 量级拷贝，应改为预留容量或分块追加结构。
3. `Join=true` 时末条记录会被下一块的 carry 拉长，而 `ApplyIncremental` 遇 `LastAppendCarried` 直接回退全量过滤（`frmMain.cs` L1253 附近）——与「逐块发布」天然冲突，必须定发布时机（见 D3）。
4. `ScanRange` 的单块 `byte[]`（`Services/LogDocument.cs` L393–L402）既是 4.6 GB 峰值内存的主因，也决定流式化必须先拆掉「整份读入」这个形态。

## 待决策项

### D1 首批目标范围 —— 已定：C

- 结论（2026-10-24，维护者）：**C 两者一期覆盖**。本地文件与代理文件都是单进程读取、且不读动态增长的文件，可共用一条流式管线。
- 影响：需同时覆盖 `BuildAsync(本地 path)` 与 `BuildAsync(spool 后的本地文件)` 两个入口；代理仍按现状先落本地 spool，再走同一条流式管线（「边 spool 边解析」见 D5）。

### D2 发布块长 —— 已定：自适应

- 结论（2026-10-24，维护者）：**自适应**，不复用固定块长。
- 待 design 定：首块阈值与稳定期阈值（探针锚点：4 MB 首块 25–46 ms、8 MB 首块 78 ms、16 MB 首块 113 ms）；是否采用「首屏优先 → 吞吐优先」两段式，以及块长上限。

### D3 加载期 join 语义与末条发布 —— 已定：A

- 结论（2026-10-24，维护者）：**A 滞后一条发布**。块末那条记录压到下一块，确认没有续行后再发布。
- 为什么：`join=true` 时一条记录可由多行组成（崩溃堆栈），列表里显示为一行。块边界处最后一条记录是否还有续行，要读到下一块才知道；若此时已发布，它的内容会变长。
- 举例（一个 4 MB 块恰好断在第 3 行之前）：
  ```
  12-24 10:00:01.123 E AndroidRuntime: FATAL EXCEPTION: main           <- 记录头行（已发布）
  12-24 10:00:01.124 E AndroidRuntime: java.lang.IllegalStateException  <- 续行（下一块）
  12-24 10:00:01.125 E AndroidRuntime:   at com.demo.Main(X.java:12)    <- 续行（下一块）
  ```
- 选项：
  - A **滞后一条发布**：只发布已确定结束的记录，块末那条压到下一块再发。首屏只少一条，延迟约一块（25–46 ms），用户无感。
  - B **允许末行刷新**：照发，下一块到达时刷新该行。当前 `ApplyIncremental` 遇 `LastAppendCarried` 会退化为全量过滤（`frmMain.cs` L1253 附近），选 B 需新增单行/末段失效能力。
  - C **加载期关 join**：续行各自成行，加载完成后按 join 设置重排（等于再扫一遍），加载中崩溃识别不完整、视图会跳变。
- 偏向：**A**。
- 影响：选 A 不需要新增「单行刷新」能力，`Append` 现有的 carry 语义正好承载「压一条」；EOF 时必须无条件 flush 最后一条。

### D4 取消语义 —— 已定：B

- 结论（2026-10-24，维护者）：**B 整份清空**，沿用现状，不保留已加载前缀。
- 影响：取消路径与现有行为一致，无需新增 specs 场景；但加载中取消必须能干净回退已发布的行。

### D5 代理（网络）路径是否「边 spool 边解析」 —— 待定

- 为什么：网络卡点是 IO，只有重叠传输与解析才能缩短总时长；但解析需要跨进程数据通道与完整性判据。
- 选项：A 本期不做（代理仍先 spool 后 Build）；B 做（spool 写入端与解析端流水）。
- 偏向：**A**。与 D1=C 不冲突：代理文件仍走同一条流式管线，只是不在传输层做重叠；跨进程重叠另立 change。

### D6 加载中功能可用性 —— 待定

- 为什么：过滤器、导出、崩溃面板在「只有前缀」时语义不同；全部禁用体验差，全部放开需要保证前缀一致。
- 选项：A 过滤器/时间过滤可随发布增量生效，导出与崩溃面板置灰到完成；B 全部置灰到完成；C 全部放开（前缀语义自担）。
- 偏向：**A**。

### D7 存量私有设计处置 —— 待定

- 为什么：同一命题存在一份私有待评审设计（重启卡 B1，见 `BACKLOG-BIGFILE-LOAD-PERF.md`；私有目录内容按项目规则不作依据，本文不引用其内容）。
- 选项：A 以本笔记为事实基座，吸收私有设计中仍成立的结论；B 私有设计整体废弃，重写；C 两案并行评审。
- 偏向：**A**，但需维护者确认哪些结论仍成立。

### D8 小文件是否走同一条流式管线 —— 待定

- 为什么：流式与整读两条路径并存会多一套分支与测试面；但小文件整读本来就只有几十毫秒。
- 选项：A 所有文件统一流式（含代理 spool 后的本地文件）；B 保留阈值以下（如 ≤ 8 MB）的整读快路径。
- 偏向：**A**。探针 4 MB 块首块 25–46 ms，小文件总耗时差异在几十毫秒量级；单一管线减少分叉。

### D9 进度与行数显示口径 —— 待定

- 为什么：流式下总字节已知（静态文件），但总行数只有加载完才知道；进度条与状态栏文案需要定口径。
- 选项：A 进度条继续按已读字节百分比（现状），状态栏显示「已加载 N 行」；B 只显示行数；C 只保留进度条。
- 偏向：**A**。

### D10 加载期视图跟随 —— 待定

- 为什么：逐块发布持续向列表追加行；现有「跟随尾部」开关默认关闭。
- 选项：A 严格按「跟随尾部」开关（默认关 → 视图停在顶部）；B 加载期总是跟随最新行；C 加载期强制不跟随，完成后再恢复用户设置。
- 偏向：**A**，不改现有开关语义。

### D11 验收线 —— 待定

- 为什么：没有量化指标就无法判定「通过」。
- 建议值（写进 specs 场景）：
  - 首屏：本地 1 GB、冷缓存下 ≤ 0.5 s 出现首批行（探针首块 25–46 ms，余量给冷读与 UI）。
  - 总时长：不差于现状（≤ 17.6 s × 1.05）。
  - 内存：峰值 ≤ 1.2–1.5 GB（现状 4.6 GB；具体值在 design 按列宽核算后收敛）。
  - 取消：整份清空并回到空文档状态（与 D4=B 一致）；加载中途 IO 失败按同口径处理，除非另有指示。
