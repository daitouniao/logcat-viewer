## 1. 结论先行

> **2026-10-25 复核结论：建议搁置。** 本探索的收益 100% 来自「感知延迟」，**不减少任何总工作量**；而总工作量正是另一条线（过滤加速零拷贝 / 块扫描 SIMD）的主战场。复核确认典型规模（300–500 MB）下全量过滤现状已是几百毫秒量级，A 落地后约 200 ms —— **本探索要解决的「等太久」在典型规模上不复存在**。完整判据与重启条件见 §7。

以下是 2026-10-24 首版的原始分析（保留作为搁置依据），结论以 §7 复核为准。

想法拆开是三件事：**锚点分段的并行扫描**（成立且贴合现有结构）、**边扫边上屏**（技术上成立，改动最重的部分）、**从当前位置开始**（只改善感知延迟，不减少总工作量）。

实现路线倾向：快速预筛保持一次性全量跑完（本来就快），只把耗时大头 `MsgFilter` 在候选数组里按锚点拆成前后两段并行，命中分批合并上屏。语义零变化，结果集与现状逐字节一致。

本质限制需要先确认接受：双向扫描不减少总工作量，只改变命中出现的顺序。总完成时间与现状相同（还多付 UI 合并开销），收益全部来自「锚点附近的命中几十毫秒内上屏」的感知延迟。

## 2. 现状（代码事实）

- 过滤入口 `frmMain.ApplyFilter`：全量扫完 → 一次性 `SetRows(rows)` 上屏。扫描期间屏幕显示旧过滤结果 + 进度条，首屏延迟 = 全量扫描时间。
- 两段流水：
  1. 快速预筛（Level/PID/TID/分钟/Tag/MarkedOnly）——纯列访问，O(N) 但极快；
  2. `FilterEngine.MsgFilter`——逐候选行 `MessageBytes` + 大小写折叠 + `IndexOf`，真正的耗时大头。
- `LogListView._rows` 为升序文档行号数组；`SetRows` 整体替换、`AppendRows` 尾部追加（实时采集增量在用）；`PinAnchor` 用二分把文档行号映射回视口，锚点固定机制现成。
- 取消/换代机制现成：`_workerGen` + `_ctsWorker`，中途改条件自动取消重扫。
- 实时采集走 `FilterTail` + `ApplyIncremental`，只扫尾部增量，与本探索不冲突。

## 3. 目标形态

```text
                 锚点 = 当前视口位置
                        |
        +---------------+---------------+
        v                               v
   向后扫 [anchor, N)              向前扫 [0, anchor)
   升序命中 → 分批追加尾部         降序命中 → 分批反转后插头部
        |                               |
        +------- 定节流合并（如 40ms）----+
                        |
                        v
          front(升序) ++ back(升序) → SetRows → PinAnchor 重钉
```

候选数组升序且锚点可二分定位，front / back 各自升序，合并是 O(1) 拼接，无需排序。锚点天然把工作切成两段，比通用 K 段划分更贴合「附近命中先看见」的语义；将来可推广为 K 段。

## 4. 关键难点

1. **虚拟列表语义从「完整」变「部分」**：扫描中统计数字、滚动条比例需要表达「扫描中」状态；`UpdateStat` 口径要定。
2. **向前插入顶动视口**：头部每插一批，用户所见内容整体下移，必须每批重钉锚点（机制已有，交互行为要定义）。
3. **扫描中的操作边界**：滚屏应允许；改条件走现有取消重扫；导出/汇总建议等完成后再触发。
4. **UI 合并开销**：每批合并重建数组 + `SetRows`，需节流（按时间或行数），避免高频整表拷贝。

## 5. 与既有探索的关系

`UTF8-BYTE-SIMD-SEARCH.md` 攻同一瓶颈（逐行 ReadArray + 每行分配），方向是块扫描降低**总时间**；本探索做「渐进显示的壳」，改善**感知延迟**。

## 6. 待澄清（2026-10-24 首版原文；Q4 已答，Q1–Q3 的「偏向」为搁置前的记录）

- 为什么需要澄清：决定这个 change 是否值得做——若诉求其实是总时长下降，对症的是 SIMD 块扫描那条线，本探索方向不解决问题。
- 方案：A 接受总时长不变，只做「附近命中先看见」；B 要总时长下降，转 SIMD 线；C 两者都要（分两个 change）。
- 偏向：**A**，本 change 只做感知延迟；总时长另立。

### Q2 扫描中的屏幕语义

- 为什么需要澄清：决定 UI 改动面与交互契约，是改动最重的部分。
- 方案：A 列表显示部分结果 + 状态栏「已显示 X 行 / 扫描中」，完成后补全；B 维持现状——扫完才切换，不做渐进显示（本探索作废）。
- 偏向：**A**，这是想法的初衷。

### Q3 渐进范围

- 为什么需要澄清：快速预筛本就是毫秒级列访问，拆它没有收益，只增加复杂度。
- 方案：A 仅 MsgFilter 渐进（预筛一次性跑完、在候选数组上二分锚点分段）；B 预筛也双向。
- 偏向：**A**。

### Q4 事实缺口：全量过滤基线耗时 —— **2026-10-25 已答（推算，非 SMB 实测）**

- 为什么需要澄清：决定这个 change 是否值得做——若实际只要几百毫秒，渐进显示可能不值得。
- 方案：跑探针取实测数字（可复用 `.tmp-test` 探针工程模式）。
- **复核答案**：按《过滤加速·零拷贝》探索笔记的实测基线折算，现状已落在「几百毫秒」区间 → 按本节自己设的判据，**不值得**。

| 项 | 300 MB 本地热缓存（实测基线） | 176 MB SMB（按行数折算，推算） |
| --- | --- | --- |
| 行数 | 4,635,207 | 3,063,986 |
| 段 1 预筛 | 40 ms | ≈ 26 ms |
| 段 2 现状 case-insensitive | 733 ms | ≈ 484 ms |
| 段 2 零拷贝 + 字节级忽略大小写 | 267 ms | ≈ 176 ms |
| **全量过滤合计（现状 CI）** | **773 ms** | **≈ 510 ms** |
| **全量过滤合计（A 落地后 CI）** | **307 ms** | **≈ 200 ms** |

- 折算方法：按行数线性折算（176 MB 文件行数 ÷ 300 MB 样本行数 = 0.661）。SMB 文件在仓库里先落本地 spool 再过滤，故可比本地盘；**冷缓存不可比**（176 MB 冷读 25.6 s @ 7 MB/s，见 `openspec/notes/archive/2026-10-30-STREAMING-FILE-LOAD.md`）。
- **顺带纠正原文一处量级笔误**：原文「2.7 万行量级」实为 **272 万条记录 / 306 万行**（差 100 倍）。该数字只出现在「为什么要澄清」的说明里，不影响结论方向，但引用时勿沿用。
- **仍缺**：176 MB SMB 上的**直接实测**（未跑）。本节结论基于折算，标注为推算而非实测。

## 7. 2026-10-25 复核：建议搁置

### 7.1 三条硬判据

1. **C 不减少总工作量，A / B 减少。** C 的收益全部来自感知延迟，总耗时一分不省，还要多付并行调度 + 分批合并整表重建的开销。A 落地后段 2 从 2.3–2.9 s 降到 0.5–1.3 s（1 GB / CI），300–500 MB 典型规模降到 200–300 ms —— C 想省的「等待」在典型规模上已经不存在。
2. **C 要造的 UI，流式加载也要造。** §4 难点 1「虚拟列表语义从完整变部分」与 `openspec/notes/archive/2026-10-30-STREAMING-FILE-LOAD.md` 的「逐块发布」是同一套前提（列表显示部分结果 + 扫描中状态 + 分批追加 + 锚点重钉）。先做 C 再做流式加载 → 这套契约、状态栏口径、统计数字要设计两遍；反过来可只造一遍。
3. **C 的验收判据客观不可测。** 原文验收前提里的「扫描中每批上屏后视口锚点不跳动」（已保留在 §7.5）在虚拟列表里没有客观判据，且与用户滚动意图耦合。A 的判定标准（行号集合完全一致）可自动断言 —— 实测 362,871 个命中数逐个对齐。

### 7.2 没有「便宜的 C 子集」

能想到的降级版都已被既有机制覆盖：

- 进度反馈 —— `_pbar` + `ShowStatusRaw` 已有；
- 取消干净 —— `_workerGen` + `_ctsWorker` 换代已有；
- 「先上屏已扫部分」—— 这就是 C 本身（部分结果语义 + 锚点重钉），无法再简化。

→ 没有「只做 10% 拿 80% 收益」的切法，也不存在低风险试水版本。

### 7.3 重启判据（不废弃，改为条件触发）

本笔记不删除。若**同时**满足以下条件，再回来评估：

1. A（`filter-msgfilter-zero-copy`）与 B（块扫描 SIMD）均已落地；
