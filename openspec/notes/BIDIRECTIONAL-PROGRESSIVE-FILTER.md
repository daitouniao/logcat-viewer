# 过滤双向渐进显示：从当前位置双线程向前/向后过滤

## 1. 结论先行

想法拆开是三件事：**锚点分段的并行扫描**（成立且贴合现有结构）、**边扫边上屏**（技术上成立，改动最重的部分）、**从当前位置开始**（只改善感知延迟，不减少总工作量）。

实现路线倾向：快速预筛保持一次性全量跑完（本来就快），只把耗时大头 `MsgFilter` 在候选数组里按锚点拆成前后两段并行，命中分批合并上屏。语义零变化，结果集与现状逐字节一致。

本质限制需要先确认接受：双向扫描不减少总工作量，只改变命中出现的顺序。总完成时间与现状相同（还多付 UI 合并开销），收益全部来自「锚点附近的命中几十毫秒内上屏」的感知延迟。

## 2. 现状（代码事实）

- 过滤入口 `frmMain.ApplyFilter`：全量扫完 → 一次性 `SetRows(rows)` 上屏。扫描期间屏幕显示旧过滤结果 + 进度条，首屏延迟 = 全量扫描时间。
- 两段流水：
  1. 快速预筛（Level/PID/TID/分钟/Tag/MarkedOnly）——纯列访问，O(N) 但极快；
  2. `FilterEngine.MsgFilter`——逐候选行 `MessageBytes` + 大小写折叠 + `IndexOf`，真正的耗时大头。
- `LogListView._rows` 为升序文档行号数组；`SetRows` 整体替换、`AppendRows` 尾部追加（实时采集增量在用）；`PinAnchor` 用二分把文档行号映射回视口，锚点固定机制现成。
- 取消/换代机制现成：`_workerGen` + `_ctsWorker`，中途改条件自动取消重扫。
- 实时采集走 `FilterTail` + `ApplyIncremental`，只扫尾部增量，与本探索不冲突。

## 3. 目标形态

```text
                 锚点 = 当前视口位置
                        |
        +---------------+---------------+
        v                               v
   向后扫 [anchor, N)              向前扫 [0, anchor)
   升序命中 → 分批追加尾部         降序命中 → 分批反转后插头部
        |                               |
        +------- 定节流合并（如 40ms）----+
                        |
                        v
          front(升序) ++ back(升序) → SetRows → PinAnchor 重钉
```

候选数组升序且锚点可二分定位，front / back 各自升序，合并是 O(1) 拼接，无需排序。锚点天然把工作切成两段，比通用 K 段划分更贴合「附近命中先看见」的语义；将来可推广为 K 段。

## 4. 关键难点

1. **虚拟列表语义从「完整」变「部分」**：扫描中统计数字、滚动条比例需要表达「扫描中」状态；`UpdateStat` 口径要定。
2. **向前插入顶动视口**：头部每插一批，用户所见内容整体下移，必须每批重钉锚点（机制已有，交互行为要定义）。
3. **扫描中的操作边界**：滚屏应允许；改条件走现有取消重扫；导出/汇总建议等完成后再触发。
4. **UI 合并开销**：每批合并重建数组 + `SetRows`，需节流（按时间或行数），避免高频整表拷贝。

## 5. 与既有探索的关系

`UTF8-BYTE-SIMD-SEARCH.md` 攻同一瓶颈（逐行 ReadArray + 每行分配），方向是块扫描降低**总时间**；本探索做「渐进显示的壳」，改善**感知延迟**。两者正交、可叠加：先落渐进壳，将来把 MsgFilter 引擎换成块扫描。

### Q2 扫描中的屏幕语义

- 为什么需要澄清：决定 UI 改动面与交互契约，是改动最重的部分。

### Q3 渐进范围

- 为什么需要澄清：快速预筛本就是毫秒级列访问，拆它没有收益，只增加复杂度。
- 方案：A 仅 MsgFilter 渐进（预筛一次性跑完、在候选数组上二分锚点分段）；B 预筛也双向。

### Q4 事实缺口：全量过滤基线耗时

- 为什么需要澄清：2.7 万行量级（如 176MB SMB 测试文件）上现有全量过滤实测耗时决定收益大小；若实际只要几百毫秒，渐进显示可能不值得。
- 方案：跑探针取实测数字（可复用 `.tmp-test` 探针工程模式）。
- 偏向：动手前先取这个数。
