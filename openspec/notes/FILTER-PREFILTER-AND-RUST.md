# 过滤初筛策略与 Rust 落点

- 状态：**探索完成**（不建 change；切片侧 C18 已于 2026-11-15 定甲）
- 日期：2026-11-15
- 关联提交：无（纯探索）
- 验收结论：不适用

## 1. 结论先行

- 现有过滤链路已具备常见初筛形态：结构化字段预筛在前、字节级 SIMD 块扫描居中、行段判定收尾。「按选择性排序」与「多级过滤管道」不是待补项。
- 唯一真缺口是**多关键词 message 过滤每词一轮全量扫描**（`O(k × 数据量)`）：`BLOCK_SCAN_MAX_KEYS = 8` 是兜底阀而非能力上限，超限整体退回逐行。
- MCP 正则确定由 Rust core 执行，方言以 **Rust `regex`** 为准（2026-11-15 拍板）：线性时间、无灾难性回溯、不支持反向引用与环视；原「200 ms 匹配超时」安全模型作废，改为编译期拒绝不支持的语法。
- 契约已收敛（2026-11-15）：一份 `FilterExpr` + 两个执行档（物化行 / 流式统计）+ 导航面 + 单一导出原语；UI 的条件字段是它的子集；`markedOnly` 与标记集合归 core（见 §7.4 / §9）。
- Trigram / Bloom 索引当前不引入，收益模型与触发条件见 §5。

## 4. 唯一真缺口：多关键词单遍

现状成本随词数线性增长，根因是每个关键词独立一轮全量扫描：

```
k = 1 : 1 轮 —— 已贴内存带宽地板，单遍多模式不会更快
k = 3 : 3 轮 —— 理论 3×，净收益受多模式引擎每字节开销更高影响
k = 8 : 8 轮 —— 上界；再往上整体退回逐行，是全表最差一档
k > 8 : 逐行匹配（BLOCK_SCAN_MAX_KEYS 兜底阀触发）
```

Rust 侧的落点：

- 子串多关键词：`aho-corasick`（SIMD Teddy 预筛），一遍扫描报出所有模式命中。
- 正则多模式：`regex-automata` 的 `RegexSet` / 元引擎，必含字面量预筛内建，同样是统一编译、一次扫描。
- 两者共用同一份候选行/块扫描骨架，`BLOCK_SCAN_MAX_KEYS` 的前提消失，随刀3 重估。

移植时必须保住的语义：

1. **非 ASCII 回退**：字节级多模式只接管「可扫词」；非 ASCII needle 与含 ≥0x80 的行仍走 Unicode 折叠回退（`ß/ẞ`、`İ/ı` 只在折叠路径成立）。
2. **and 计数**：and 语义按「该行命中词数 = 可扫词数」判定，多模式引擎必须逐词报出命中，不能只报「有命中」。
3. **跨块重叠**：沿用现有 `overlap = 最长词长 - 1`，防跨块漏配。
4. **逐位一致**：子串路径与 C# 现有块扫描在 k = 1/3/8/20、CS/CI、ASCII/非 ASCII 混合语料上给出完全相同的行号集合。正则无 C# 对拍基线（新能力），验收用固定语料 + 预期行号黄金集。

## 5. 索引类策略：当前不引入

- **Trigram**：只服务正则，MCP 正则落地后语义上成立；但构建成本 ≈ 一次全量扫描，另加常驻内存、append/reload/采集追加的增量维护与失效逻辑。
- **Bloom 跳块**：4 MB 块的 trigram 集可达十万级，1% 位图预算下占用率轻松过 80%，假阳性高到跳不掉几块；需要更大的位图或更小的块才有效，成本随之上升。
- **触发条件**（同时满足才重估）：单文档 > 1 GB、用户工作流对同一文档反复换条件查询 ≥ 3 次、查询延迟成为可感知瓶颈。届时作为独立的数据模型 change（属 sidecar 家族），不并入过滤切片。
- 红线：任何预筛/索引都必须「不漏」——只用无假阴性的结构（bloom、trigram 位图、多模式自动机），并配一批已知命中的回归语料。

## 6. 正则引入后的现行规则

- **执行方**：Rust core（GUI 与 MCP 共用同一 dll）；GUI 首版不暴露正则入口。
- **方言**：Rust `regex`。线性时间、无灾难性回溯；不支持反向引用与环视；不支持的语法在编译期拒绝并返回明确错误，不做静默降级。
- **安全模型**：不需要匹配超时。「超时按不命中处理」整条删除，防拖死的责任由引擎的线性时间保证承担。
- **作用面**：正则只匹配 message 体（既有倾向），整行匹配等实际需求再加。
- **大小写**：`(?i)` 走 Rust regex 的 Unicode 大小写折叠，与 GUI 子串路径的「ASCII 折叠 + 非 ASCII 整行回退」是两套模式，不要求逐位一致。

## 7. 契约面：一份条件模型 + 两个执行档 + 导航面 + 导出（2026-11-15 定）

### 7.1 分层

| 层 | 内容 | 归属 |
| --- | --- | --- |
| 条件 | `FilterExpr`：level / tag{values, match: substring\|exact, op, case, exclude} / pid / tid / minute / timeRange / msg{mode: substring\|regex, op, case, exclude} / markedOnly | UI 提交子集（无正则；tag 固定 substring），MCP 提交超集 |
| 结果 | `open(FilterExpr) -> queryId`，升序行号表 | core 持有，宿主不持有；刀2 的临时 `set_result(ids)` 由刀3 删除（C16 定甲） |
| 执行档 | `MaterializeRows`（分页取行、计数、导出）；`StreamStats`（不物化，只返回计数/分布/首末时间） | 同一扫描骨架，两种消费面 |
| 导航 | `resolve` / `page` / `context` / `next_match` / `prev_match` / `close` | UI 与 MCP 共用 |
| 导出 | `export(queryId, path, overwrite)` | core 执行，UI 与 MCP 共用 |

- 正则作为 `FilterExpr` 的一等 `mode`，GUI 首版不暴露；随刀3 一并实现（§10）。
- 子串与正则是两条匹配引擎，共用扫描骨架；**禁止把子串编译成正则实现**（改变 ß/İ 等语义，且退掉字节级向量化路径）。
- `tagMatch` 由调用方显式指定：UI 固定 `substring`（与现状一致），MCP 推荐 `exact`；GUI 首版不暴露 exact。
- exact 用 tag 字典 id 比较（`case=false` 时先把值折叠后映射到 id 集合）；`TagOp=and` 在 exact 下按集合交集定义，单 tag 行上多个不同 exact 值即空集，不做特判。
- 宿主专属件不进条件模型：采集增量 tail、`Loc` 文案、视口槽位；MCP 的英文错误码、返回上限。标记不是宿主件：集合与 `markedOnly` 均在 core。
- MCP 的两套工具面草案（检索原语 / 分析接口）仍未合并，属 MCP 自身命名问题，不影响本分层。

### 7.2 导航规则

- 锚点 = `(文档行号, 视口偏移)`：有选中取选中行，无选中取视口顶行（偏移 0）。
- `resolve` 在升序结果表上二分：命中即返回；不命中取前后两条，平局取**前一条**；越界取首条/末条。规则与现有 `NearestModelRow` 一致。
- 结果集升序、只追加：采集新增只影响尾部，已有序号前缀稳定；重载换映射后锚点失效，需重新锚定。
- `page` 返回的每行带 pid / tid / level / tag / 时间，供"同 pid 附近"这类谓词组合直接取值。

### 7.3 导出面（写盘策略 2026-11-15 定：甲）

- 单一原语，不复活旧分析草案的逐工具 `save_to`。
- 路径：任意绝对路径；默认**不覆盖**已存在文件，覆盖须显式 `overwrite`；目标等于源文件时拒绝。
- 写盘：流式写、临时文件 + 改名（原子），失败不留半个文件。
- 快照：取调用时刻的结果集长度快照，采集期间新追加的行不混入。
- 内容：与 UI 现有导出一致——每条记录原文一行、行尾 `\n`、UTF-8 无 BOM。
- 上限：不受内联返回的 500 行 / 2 MB 限制；设总大小预警，防一次导出几十 GB。

### 7.4 标记与持久化（2026-11-15 定）

- 归属：core 持有 markset，暴露 `mark(row)` / `unmark(row)` / `clear_marks` / `list_marks`；`markedOnly` 在扫描阶段生效，UI 不再事后过滤。
- 持久化：独立文件 `.lcm`，与 `.lcs` 同目录、同 `derive_name` 键；启动维护只扫 `.lcs`，`.lcm` 不参与容量回收与自动删除（缓存可删、用户数据不可删）。
- 格式：`magic "LCMM"` + 版本 + identity（size / mtime / 头尾哈希）+ 文档行数 + 标记条目 `(row, offs, len)`。独立版本号，`.lcs` v1 字节不变（C6 维持甲）。
- 存活规则乙：忽略 mtime；头哈希相同且文件未变短时，逐条用 `(offs, len)` 复验，不匹配的单条丢弃；其余情况不加载。采集源 `identity=null`，标记仅会话内。
- 写入：变更防抖约 500 ms + 关闭 / 切文档 flush；临时文件 + 改名原子写；失败保留内存态并报错，不阻塞交互。
- 查询：标记变更**不**使已打开查询失效；只有 `markedOnly` 选项变化时重建结果集。「跳到标记 / 导出标记行」读实时 markset。
- MCP 不暴露标记；`markedOnly` 不进 MCP 的对外参数。

## 8. 邻近语义（2026-11-15 定：甲）

- "附近几行" = 原始行窗口：`context(row, before, after)` 取文档全部行（含未命中行）。
- 窗口内的谓词（如同 pid、同 tag）由 MCP 层对返回的小窗口本地过滤，**不进 `FilterExpr`，不加 `rowRange`**。
- 需要"最近的 K 条满足谓词的行"时用组合表达：`open(谓词)` + `resolve(q, row)` + `page(q, ord±k)`。
- 重启条件：若窗口内谓词需要计数或分页，再评估给 `FilterExpr` 增加 `rowRange`。

## 9. 标记与 `markedOnly`（2026-11-15 定）

- 结论：取甲——core 维护 markset，UI 不再事后过滤（分页总数、滚动条、翻页位置一致）。
- 持久化取独立 `.lcm` 文件，理由与格式见 §7.4：塞进 `.lcs` 会触发格式升版、缓存回收误删用户数据、每次标记重写整份索引三笔账。
- 标记变更不影响已打开查询；只有 `markedOnly` 选项变化时才重建结果集（等同现状：`ToggleMark` 只重绘、不重滤）。
- 连带修正：C17 原「标记变更纳入查询世代失效」作废；查询失效只由条件表达式变化触发。

## 10. 正则交付刀次（2026-11-15 定：甲）

- 结论：**随刀3 一并实现**，不另立 core change，也不推迟到 MCP。
- 内容：Rust `regex` 编译 + message 体匹配 + `(?i)` Unicode 折叠；不支持的语法编译期拒绝（`REGEX_INVALID`）；无超时。
- 验收：黄金集回归（已知命中/不命中行逐条对拍）；子串与正则是两条引擎，互不实现。
