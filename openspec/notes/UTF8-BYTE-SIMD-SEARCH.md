## 1. 结论先行

方向成立：在 mmap 原始字节上做关键词预筛、只对命中行解码，比现状「逐行 ReadArray + 每行分配」更有性能上限。

但给出的草案有 4 处与 .NET 实际 API / 本仓库过滤语义不符，直接照抄会得到错误结果（不是慢，是**误报/漏报**）。落地前必须按 §4 校正。

**2026-10-25 修订**：§4.2 原推荐的「预筛用 needle 小写形式即可覆盖所有大小写命中」经实测**证伪**（`Exception` 漏 99.97%），该节的推荐方案与论据已重写；§6 Q2 的推荐随之作废。

## 2. 现状（代码事实）

- 文档模型：`MemoryMappedFile` + `CreateViewAccessor(0, 0)`，文本本体留在磁盘，内存只有定长列（`offs` / `lens` / `moff` / `lvl` / ...）。
- Message 过滤（`FilterEngine.MsgFilter`）逐候选行执行：
  1. `doc.MessageBytes(row)` → **每行 new byte[]** + 一次 `_view.ReadArray`（小随机读）；
  2. 区分大小写时直接匹配；忽略大小写时先复制到 scratch 就地折叠 ASCII；
  3. 含非 ASCII 时回退 `GetString → ToLowerInvariant → GetBytes`（每行 3 次分配）；
  4. `MatchAny` 对每个关键词跑 `hay.IndexOf(needle)`（`Span<byte>.IndexOf` 在 .NET 8+ 已是向量化实现）。
- 即：**现状不是全量解码**，只有含非 ASCII 的行才走编码往返。瓶颈候选是「逐行小随机读 + 每行数组分配」，不是字符级匹配本身。

```text
现状（每候选行）
  offs/lens/moff --+
                   v
        [view.ReadArray 小读] --> new byte[] --> 折叠/回退编码 --> IndexOf(needle)

目标（块扫描）
  mmap 指针 --+
              v
   [Parallel 块 + 字节 IndexOf] --命中--> 行归属/复核 --> 仅对命中行 Decode
```

| 实现 | 耗时 |

## 3. 草案中成立、可直接采纳的部分

1. UTF-8 自同步：ASCII 字节不会出现在多字节序列的续字节（续字节恒为 0x80–0xBF），所以英文关键词（ERROR/WARN）绝不会在汉字内部误匹配。
2. 中文关键词转 UTF-8 字节后直接搜索，在**合法 UTF-8** 中不会误报也不会漏报（首字节决定长度 + 续字节区间 + 禁止超长编码）。
3. `0x0A` 不可能出现在多字节序列内部 → 按字节找换行零解码；CRLF 亦然（`0x0D` 同理）。
4. 分块并行需要重叠 `最长关键词字节数 - 1`，否则跨块关键词漏匹配。
5. 只对命中行调用一次 `Encoding.UTF8.GetString` 用于展示。
6. `ptr + accessor.PointerOffset` 才是数据起点、`Capacity` 才是有效长度 —— 与仓库既有 `LineIndexProbe` 的 `AcquirePointer` 用法一致。
7. 全文件块扫描顺带修复逐行小随机读，与待办 C1（网络路径过滤慢、嫌疑跨页率）方向一致。

## 4. 必须校正的 4 点

### 4.1 多模式字节 `SearchValues` 重载不存在

草案里 `SearchValues.Create(patterns.Span)`（`ReadOnlyMemory<byte>[]`）没有对应重载；`SearchValues.Create(ReadOnlySpan<byte>)` 的语义是「**任意一个字节值**」，把多个关键词的字节拼平成数组会退化成单字节 any-of → 大面积误报。多子串 SIMD 匹配只有 .NET 9+ 的 `SearchValues<string>`（`char` 域）提供，**不适用于字节域**。

置信度：高（依据 .NET 8/9/10 API 面），但按探索规范仍需探针确认，见 §7。

替代方案（按推荐排序）：
- 多关键词：并发/循环跑 N 次 `span.IndexOf(needle)`，每次本身即 SIMD；关键词通常个位数，代价可控。
- 单关键词：`IndexOf` 就是最优路径，不需要 `SearchValues`。
- 关键词多到几十个时：先 `IndexOfAny(首字节集合)` 定位候选，再逐点校验完整模式（候选少时更快）。

### 4.2 忽略大小写与原始字节扫描冲突 —— **2026-10-25 修订：原推荐已证伪**

现状 `MsgCase=false` 是**折叠 haystack 后用小写 needle**。扫描原始文件时无法折叠 haystack。

**原文的推荐（已作废）**：预筛只用于「排除」，命中行再按现有折叠逻辑做一次确认匹配 —— 并称「预筛用 needle 小写形式，任何大小写命中都必然经此路径」，故「预筛漏不掉」。

**实测证伪**（1 GB 文件，原始字节上搜 message 段内）：

| needle | 正确忽略大小写命中 | 预筛（小写 needle） | 预筛（原样 needle） |
| --- | --- | --- | --- |
| `error` | 362,895 | 362,871（漏 24） | 362,871 |
| `Error` | 362,895 | 362,871（漏 24） | 24 |
| `Exception` | 120,545 | **36（漏 120,509 / 99.97%）** | 120,343 |

原因：原始字节里是 `Exception`（首字母大写），小写 needle 的字节串**根本不在文件里**。「小写 needle 覆盖所有大小写命中」不成立 —— 除非 needle 本身全小写且文件里恰好也全小写，这不可依赖。

**修订后的可行路径**（按推荐排序）：
- **A（推荐）· 显式的大小写不敏感字节搜索**：预筛阶段直接用大小写不敏感的比较（比较时两侧 OR 0x20 后逐字节比对，或 SIMD 向量化）。这等价于现状「折叠 haystack」的语义，但不需要物化折叠后的副本。实测朴素版（逐字节 OR 0x20）为 945–1270 ms，已优于现状 CI 2284–2945 ms；SIMD 化后仍有空间。
- **B · needle 大小写变体展开**：k 个字母 → 2^k 个模式，模式数爆炸，不可行。
- **C · 双模式（仅大写 + 仅小写）**：漏混合大小写（`eRRor`）→ **与现状语义不符，不可接受**。
- **D · 命中后复核**：只有当预筛本身大小写不敏感时，「命中即候选、复核确认」才成立；即 D 必须建立在 A 之上，**不能单独用小写 needle 预筛**。

非 ASCII 行的 Unicode 折叠回退（`ß/ẞ`、`İ/ı` 等长宽变化规则）在 A 方案下**仍须保留** —— 不能因为做了 ASCII 折叠就丢掉这条路径。

### 4.3 Message 语义与整行扫描不一致

现过滤只匹配 message 段（`moff` 之后），整文件字节扫描会把 tag / pid / 时间戳也算进去 → 行为变化（false positive）。
处理：命中 offset 后按行核验是否落在 `[offs[row] + moff[row], offs[row] + lens[row])`；`offset → row` 用 `offs` 二分。命中点通常远少于总行数，代价可忽略。

### 4.4 重叠区重复命中与行归属

朴素「每块覆盖 `[offset, offset+len+overlap)` 并各自报命中」会让落在重叠区的命中被相邻两块各报一次；行归属也必须唯一。
采用仓库已有范式（`LineIndexProbe.ScanChunk`）：**行首落在本块 `[rawStart, rawEnd)` 的行才归本块**，重叠只用于跨块把整行读完；结果按行去重。

## 5. 其他风险

- mmap 冷缓存下顺序扫描受磁盘带宽限制；200MB 的「几十~几百毫秒」是热缓存量级，冷缓存不可比。需要大小文件阈值（小文件走现状，避免固定开销）。
- 非法 UTF-8 字节可能造出假命中；作为显示型工具可接受，但复核路径会自然消解（复核基于 `Decode` 后的文本或现有字节匹配）。
- 中文关键词的大小写折叠是 no-op，可跳过折叠分支（纯优化）。
- **与「零拷贝逐行」路线的关系**（《过滤加速·零拷贝》探索笔记，已归档；其 D1 已定「过滤 + 缓存」两项都做）：本路线天花板高于零拷贝逐行，但实现复杂度与语义风险更高。零拷贝已于 2026-10-28 落地（`filter-msgfilter-zero-copy`）；**2026-10-29 排序更新：本路线（SIMD 块扫描）紧随其后立即做，sidecar 缓存再往后**（用户拍板，原「先 sidecar 后 SIMD」顺序作废）；两条线共用同一套实测基线数字。
- **D2 已定并已落地（2026-10-28）**：「显式大小写不敏感字节搜索」（本笔记 §4.2 方案 A），实现 = 候选定位 + 逐字节验证（`FilterEngine.ContainsAsciiInsensitive`）。块扫描预筛直接复用 —— 块扫描同样不能折叠 haystack。
- **与「双向渐进显示」方向的关系（2026-10-25 复核）**：该方向**已搁置**（`BIDIRECTIONAL-PROGRESSIVE-FILTER.md` §7）—— 它只改命中出现的顺序、**不减少总工作量**，而本路线把总时间降 13×。顺序结论：**先降总时间（A → B），感知延迟类方案按 `BIDIRECTIONAL-PROGRESSIVE-FILTER.md` §7.3 判据条件重启**，不先落渐进壳。

## 6.1 决策日志（2026-10-29，已转 change `filter-msgfilter-block-scan` 后评审拍板）

- CS 并行仅 ~3.5×（138 → 39 ms，72 核远未吃满）→ 顺序扫描受**内存带宽墙**限制；CI 的逐候选验证可并行摊薄，反而补齐到地板量级。
- CI-Par 不含行归属复核 / message 段边界判定（§4.3、§4.4 的代价另计），设计时按「复核命中点数量」评估追加成本。
- 局限：中文关键词用例在样本上为 0 命中（只验证了正确性交叉一致，未覆盖有命中的中文场景）；轮间存在机器负载噪声，数字取区间。

### 7.3 剩余步骤

1. 基准（可与 change 的 tasks 合并，不阻塞 propose）：造 200 MB 含中文日志，A/B 对比「现状 MsgFilter」vs「块扫描预筛 + 命中复核」；记录冷/热缓存与网络路径（联动 C1）。
2. **转 `/opsx:propose`**：范围限定 Message 过滤（Q1=A / Q3=A 已拍板），specs delta 只写行为契约（结果集不变）。

## 8. 判定标准（验收前提）

- 对同一输入与同一 FilterSpec，新旧路径输出**行号集合完全一致**（含空 needle、and/or、忽略大小写、中文、混合中英）。
  - **2026-10-25 补充**：忽略大小写场景要达成此标准，实现**必须**包含显式的大小写不敏感字节搜索（§4.2 方案 A）；依赖「needle 小写化」的预筛会漏（实测 `Exception` 漏 99.97%），该路径不满足本条判定标准。
- 200MB 热缓存纯 Message 关键词过滤较现状有可测量的下降；冷缓存不劣化。
- 参考基线（1 GB / 1582 万行，热缓存）——**2026-10-29 刷新（零拷贝落地后）**：现状 case-sensitive 453–692 ms、case-insensitive 945–1270 ms（零拷贝逐行口径，即变体 G / G'）；全文顺序扫地板 149–160 ms；**探针目标形态（并行 + SIMD CI）133–151 ms（§7.2，未含行归属复核）**。旧现状（每行分配+拷贝）CS 1791–2089 ms、CI 2284–2945 ms 仅作历史参考。
