## 背景与目标

仓库已有 MCP 服务端壳 `mcp/`（`logcat-mcp`，stdio，工具面仅 `info`），是**单服务端形态**。真实场景里一个 Agent 常要用多个 MCP，且多数 MCP 客户端只支持配一个 stdio 命令——故需要一层代理：对下游是 MCP 服务端，对上游拉起并管理多个 MCP 服务端，聚合其工具暴露给 Agent，配套本机管理页面。

## 代码事实核对（2026-11-27 实测）

1. **SDK v2 已拆包，仓库只有服务端侧**：`mcp/node_modules/@modelcontextprotocol/` 下只有 `core` 与 `server` 两个包，**没有 `client` 包**。代理要用客户端侧能力必须新增 `@modelcontextprotocol/client` 依赖（npm registry 可达，HEAD 200；镜像源为 npmmirror）。
2. **既有服务端 SDK 版本线**：`@modelcontextprotocol/server@2.4.0` + `zod@4.6.7`，TypeScript 5.9.3，Node 引擎要求 ≥ 22.6（测试运行器的 glob 支持）。代理工程沿用同版本线，避免第二个 SDK 世代。
3. **`mcp/` 的服务端实现已自带可复用的契约口径**：结果信封（文本块 + 结构化内容同源）、错误码族（`TOOL_FAILED` / `TOOL_NOT_FOUND`，前缀 `TOOL_`）、stdout 只走协议 / 诊断走 stderr、退出即终止。代理作为**另一个进程**存在，不复用该工程代码，但沿用其契约口径。
4. **CI 现状**：`.github/workflows/ci.yml` 已有 `mcp` 作业（windows-latest，node 矩阵 `['26','22']`，`npm ci` → `npm run build` → `npm test`）。代理工程按同一口径单开作业。
5. **规范分类**：`mcp` 分类已于 2026-11-26 在 `openspec/config.yaml` 登记（首个 capability 为 `server-shell`），故新能力落 `mcp/proxy`，无需新增分类。
6. **可作真实上游的现成件**：仓库内的 `logcat-mcp` 本身就是一个 stdio MCP 服务端，可直接作为代理的端到端测试上游，减少造桩成本。

## 定稿口径（本 change 已实现为条款）

| 维度 | 定稿 |
| --- | --- |
| 形态 | 独立 Node 工程 `mcp/proxy/`；一个进程两副面孔（下游 MCP 服务端 / 上游 MCP 客户端） |
| 下游入口 | 可执行名 `logcat-mcp-proxy`（MCP 客户端一行命令即可接入）；启动参数 `--config <路径>` / `--port <端口>`，管理端口**默认随机空闲端口**；带令牌的页面地址写 stderr |
| 下游传输 | **仅标准输入输出**；HTTP 下游列为下一切片候选（HTTP-only 客户端 v0 接不上） |
| 命名空间 | 下游工具名 `<id>__<tool>`；路由走「下游工具名 → (id, 工具名)」**对应表**，不按分隔符切分反解；`id` 禁含 `__`；上游工具名**不设门槛**，由代理规范化出合规的下游名（非法字符→`_`、连续双划线压平、超长截断），原始名写入描述、调用仍路由到原始工具；拼出同名时先注册者保留、后注册者判不可用；内置管理工具 `proxy_servers` / `proxy_restart` 不参与命名空间 |
| 凭据 | `env` 明文可写但页面掩码；另支持 `"env:VAR"` 引用外部环境变量、**不落盘**；系统钥匙串后置 |
| 依赖 | `@modelcontextprotocol/client@2.4.0` + `@modelcontextprotocol/server@2.4.0` + `zod@4.6.7`；TS 5.9.3 |
| 上游形态 | v0 **仅 stdio 子进程**；条目 `{ id, command, args[], env{}, cwd?, enabled }` |
| 生命周期 | 每上游一个常驻子进程与一条会话，代理内共享（**v0 不做按 Agent 隔离**——同上游不同凭据/订阅态的需求需另起切片）；支持启停与重启；重启后重新列举工具 |
| 多 Agent 形态 | **一个代理实例同时只服务一个下游客户端**（stdio 形态的必然结果）；多 Agent = 各起一个代理实例，共享同一份配置文件路径，上游进程各拉各的、页面启停各管各的；共享留给 HTTP 下游 / 守护进程那一切片 |
| 时限 | 上游调用默认 **60 秒**（超时按 `UPSTREAM_UNAVAILABLE` 返回、描述标明超时）；上游就绪默认 **10 秒**；客户端取消时中止转发、不转给上游 |
| 错误族 | `TOOL_NOT_FOUND` / `TOOL_FAILED`（沿用既有族）+ `UPSTREAM_UNAVAILABLE` / `UPSTREAM_TOOL_FAILED`（新增族）；四个码值为对外契约，锁进规范；错误**码归一、原文保留**（描述带上游返回的原始错误文本） |
| 管理面 | Node 内置 `http`，仅绑回环地址 + 启动随机令牌（写 stderr）+ 校验 `Host` 头；单页 HTML，原生 JS，每 2 秒轮询刷新 |
| 配置 | 用户配置目录（Windows `%APPDATA%`，其他 `~/.config`），`--config` 可覆盖；写入「临时文件 + rename」；仓库内只留示例 |
| 退出纪律 | 代理退出即终止全部上游子进程，不留孤儿 |

## 明确不做（v0 边界）

http / sse 上游；**http 下游传输**（HTTP-only 的 MCP 客户端 v0 接不上，列为下一切片候选）；**多下游客户端共享同一代理**（v0 一实例对一下游客户端）；上游认证与凭据保管；按下游 Agent 隔离上游会话；工具级暴露开关（只能整体停用某上游）；业务工具面与日志数据能力（与 `MCP-FUNCTIONALITY.md` 的 D5 口径无关，仍待拍板）；工具结果改写与限流；多实例与跨机部署；发布与版本号同步点。

## 已否决的选项与理由

- **把代理塞进 `mcp/` 单一 npm 包** → 代理是通用连接器、`logcat-mcp` 是日志服务端，生命周期与依赖面不同；混住会让边界与 CI 粒度变粗。
- **用 express / hono 写管理面** → v1 SDK 的 HTTP 依赖面在 stdio-only 场景是纯负担；页面交互面窄，`node:http` 足够。
- **工具名原样透传 + 撞名报错** → 多上游必有同名工具（`search` / `read_file`），透传等于让 Agent 只能用一个上游；前缀命名空间是唯一无歧义且可定位路由的形态。
- **按分隔符切分工具名反解上游** → 分隔符在 id 与工具名两侧都可能出现（`id=a__b, tool=c` 与 `id=a, tool=b__c` 都拼出 `a__b__c`），字符串反解不可靠；改走注册期对应表。
- **用严格口径卡上游工具名（不合规即整个上游不可用）** → stdio 上游可以随意命名工具，因代理有对应表，合规性由代理对外暴露的名字承担更合理：不合规则规范化而非拒用整个上游。
- **内置工具也走 `proxy__servers` 形状** → 形状统一了，但内置工具名仍是全局名，与上游扁平命名空间混在一处反而更易撞名；保持 `proxy_servers` / `proxy_restart` 扁平名，靠「内置工具不参与命名空间」隔离。
- **内置工具用 `list_upstreams` / `restart_upstream` 这类通用名** → 上游极可能自带同名工具，撞名会在注册期把某个上游判死，代价不对称。
- **管理端口用固定值** → 代理是本机工具、多实例并存是常态，固定端口必然撞；默认随机空闲端口，把「端口冲突」这类失败整个消掉。
- **凭据一律明文落盘** → 不给不愿明文落盘的用户留路；加 `"env:VAR"` 引用形式成本极低。系统钥匙串方案跨平台成本高，后置。
- **不设调用时限、信任上游** → 上游卡死不返回会把下游那一轮对话挂死；设默认 60 秒时限，超时按上游不可用族返回。
- **上游错误只归一码、丢掉原文** → 「401 unauthorized for repo X」这类线索一丢就只剩一个码，排障成本极高；码归一、原文保留，两者不冲突。
- **代理自述工具（第三个内置工具）** → 上游清单已由 `proxy_servers` 覆盖，版本信息写 stderr 与文档即可，不必再加一个占 Agent 上下文的工具。
- **支持 http / sse 上游** → 引入鉴权、部署与端口占用整套负担；且形状一旦进配置字段就容易「顺手支持」，与既有「传输形态限定」的纪律相悖。
- **上游每下游客户端独立拉起** → 进程数随连接数放大，重启语义模糊；stdio 上游本就是单例子进程，共享更贴合语义。
- **配置放仓库内** → 条目 `env` 可能含凭据，写进仓库等于泄密。

## 实施结果（2026-11-27）

- 工程落在 `mcp/proxy/`（Node + TypeScript，`@modelcontextprotocol/client@2.4.0` + `server@2.4.0` + `zod@4.6.7`，TS 5.9.3），可执行名 `logcat-mcp-proxy`。
- 实现的模块：`config.ts`（校验 / 原子落盘 / `env:VAR` 引用）、`naming.ts` + `registry.ts`（命名空间与对应表）、
  `upstream.ts`（生命周期 / 时限 / 诊断尾部 / 进程树清理）、`server.ts`（下游服务端）、`management.ts` + `page.ts`（管理面）、
  `builtins.ts`（`proxy_servers` / `proxy_restart`）、`cli.ts` + `index.ts`（入口）。
- 测试 **74 条全部通过**（`npm --prefix mcp/proxy test`），覆盖配置、聚合、路由与错误码、时限与取消、
  上游生命周期、内置工具、管理面访问控制、下游服务端纪律，以及以仓库内 `logcat-mcp` 为真实上游的端到端四条。
- 实施中修正了两处与设计初稿的偏差：① 停止的上游其工具**保留在对应表里但标记为不活跃**——
  这样调用被停上游的工具报「上游不可用」而不是「工具不存在」（规范场景要求前者）；
  ② 上游自己返回的失败结果在管理器层就归一为 `UPSTREAM_TOOL_FAILED` 并保留原文，错误语义只有一处判定。
