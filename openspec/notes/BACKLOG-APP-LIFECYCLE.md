## B-APP-01 关窗时加载 worker 与文档关闭的并发竞态（风险：中，可能导致进程崩溃）

**事实（代码为据）**：

- 主窗体关闭流程只对加载 worker 做取消（`StopWorker()` 的取消 + 代际递增），随后立即关闭文档映射，不等待 worker 真正退出。
- 分块加载全程不持文档互斥：加载编排（`frmMain.Load.cs` 的 `RunChunkedLoadAsync` / `OnChunkPublished`）没有参与 `_docBusy` 的加锁协议，只有 UI 侧的过滤/重载路径在用它。

**后果**：worker 可能在映射被释放后继续按块读取 → `AccessViolationException`（不可捕获，进程直接终止）；或在文档关闭后抛出对象已释放异常，落到异步入口的兜底分支。

**修法候选**（择一或组合）：

1. 关窗前「取消 + 有上限等待」worker 退出，再关文档（把最坏等待挪到关窗，与 B-APP-02 合并设计）。
2. 把文档关闭推迟到 worker 结束之后（后台收尾），窗口先销毁。
3. 文档加「使用中」引用计数，最后持有者负责关闭。

**触发场景**：打开大文件后，加载尚未完成时关闭主窗口（用户实际遇过多次，但尚未观测到崩溃）。

## B-APP-02 关窗路径的「UI 线程同步等待 async」（风险：低—中，固定多等 2~4 秒）

**事实（代码为据）**：

- 关窗流程有两处同步等待：等采集任务停止（上限 2 秒）、等文档互斥（上限 2 秒）。
- 被等待的异步方法内部 `await` 没有脱离 UI 上下文；UI 线程此时正阻塞在等待上，续体无法回到 UI 线程 → 只能等满超时。等价于「每次关窗固定多花 2 秒」的定时器。

**后果**（推断，待实测）：有 ADB 采集在跑、或有在途筛选时，关窗稳定多 2~4 秒，且与视图行数无关。此现象与 `fix-close-dispose-slow` 修复的「按行数线性变慢」是两个独立成因，勿混为一条。

**修法候选**：

1. 关窗只取消、不等待；清理挪到后台或进程退出时完成。
2. 被等待链路统一脱离 UI 上下文，UI 线程不做阻塞等待。
3. 关窗时先放行单实例守卫，再后台收尾（与 B-APP-01 的方案 2 同源）。

## B-APP-03 单实例/退出类需求在 capability 中的归口（整理项，无功能改动）

**事实**：`openspec/specs/old/fileproxy/spec.md` 当前挂着「单实例守卫（BREAKING，已拍板）」需求；`fileproxy` 的主题是设备侧文件代理与暂存目录，单实例属应用生命周期。本次新增的 `app-shutdown` 只覆盖关窗耗时与关闭后重启，与该需求语义相邻但未合并。

**待办**：后续用一个只含 spec delta 的 change，把启动/退出类的应用级需求（单实例守卫、关闭后重启、将来的启动清理语义）收拢到 `app-shutdown`（或另立 `app-lifecycle`），`fileproxy` 只保留代理与暂存相关内容。纯文档整理，不改代码行为。
