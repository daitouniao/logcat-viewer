## 结论摘要

用户诉求：打开网络驱动器（网上邻居）上的日志文件后，**每次**修改 message 过滤关键字都要 ~1.7 s（176 MB / 140 万行）；加 tag 过滤则很快、命中数相同。问是否最近改动引起。

最终结论（三点；第 2 点的成本分解含反算，见「复核算术」）：

1. **用户感知的速度不是回归，但缺陷形状来自一次优化提交**。`scratch` + `FoldLowerAsciiInPlace` 由 2026-10-03 的 `1ba0270`（「过滤引擎消除 message 逐行重复编码，零行为变化」）引入；在那之前每行都走 `GetString→ToLowerInvariant→GetBytes`，只会更慢。所以对「是否最近改动引起」的准确回答是：慢的代码形状确实来自那次改动，但速度没有变差，是那次优化没覆盖到的路径。
2. **与网络完全无关**。真凶是 `MsgFilter` 的一个 CPU 侧 bug，**两层叠加**：
   - **主因**：`FoldLowerAsciiInPlace(scratch)` 遍历**整个缓冲容量**（8 KB，与当前行长度无关），每行 O(容量) 逐字节扫描，实测折算约 1 GB/s；
   - **次因**：同一处的残留字节污染让 ASCII 判定误判，把 Unicode 回退率从数据下限 10.8% 抬到 27.4%。
   瓶颈是纯 CPU，本地文件同样会慢。
3. **修复面极小**：`FoldLowerAsciiInPlace` 增加 `Span<byte>` 重载，调用点改为按 `msgBuf.Length` 切片折叠 —— 一条改动同时消掉主因（扫描量回落到行内字节）与次因（回退率回到下限）。实测同环境 17.4 s → 0.5 s（约 34 倍），命中数不变。

「tag 过滤快」的解释：`TagIds` 只读内存字典、不碰 message 字节，从而完全不进入这条出错路径；加了 tag 条件还会缩小候选集，扫描行数随之减少。

## 根因机制

```
MsgFilter（Services/FilterEngine.cs，大小写不敏感路径）
├─ scratch = new byte[1024]              <- 只增不减，容量按 2 的幂翻倍
├─ 每行: Array.Copy(msgBuf -> scratch)    <- 只覆盖前 msgBuf.Length 字节
├─ FoldLowerAsciiInPlace(scratch)        <- 缺陷①：遍历 scratch.Length（整个容量）
|    · 纯 ASCII 行：要把 8 KB 扫完才返回 true
|      -> 每行 O(容量)、与行长度无关（主因）
|    · 残留区留有之前中文行的字节 >= 0x80
|      -> 本行哪怕纯 ASCII 也返回 false，走
|        GetString->ToLowerInvariant->GetBytes 回退（次因）
└─ 扩容公式 new byte[Math.Max(len, cap*2)]
      -> 只能 1024->2048->4096->8192...，不会出现 5.6 KB 这类非 2 的幂
```

- 文件真实含非 ASCII 行占比 10.8%（292,737 / 2,719,107），本应只有这些行走回退；
- 污染后实际回退 744,922 行（27.4%），且每次过滤都复现（与缓存冷热无关）；
- 用户环境 1.2 μs/行 与复现环境 6.4 μs/行 的 5 倍差同样由容量解释：若用户文件最长消息 ≤ 1024 B，容量停在 1 KB，1.4M × 1 KB ≈ 1.4 GB ≈ 1.4~1.7 s，与实测 1732 ms 吻合（推断，未直接测容量）。

### 复核算术（未新增实验，拿上表数据反算）

| 成本项 | 量 | 折算 |
| --- | --- | --- |
| 全容量扫描（`scratch.Length` = 8 KB） | 1,974,185 行 × 8 KB ≈ 16.2 GB | @ ~1 GB/s ≈ **16 s** |
| Unicode 回退 | 744,922 行 × 0.34 μs（实验 D 实测） | ≈ **0.25 s** |
| 修复形态 H | 0.18 GB 扫描 + 292,737 次回退 + IO ~0.15 s | ≈ **0.5 s** ✅ |

扫速 ~1 GB/s 由 A/B 反算：B 330 ms − A 114~183 ms ≈ 0.15~0.22 s 完成 176 MB 折叠。

结论：G 的 17.4 s 与「8 KB × 行数」吻合，与「回退行数」相差约 70 倍 → **主因是每行按容量扫描，回退率放大是次因**。主因/次因的直接拆分实验已定稿为 G′（见「待澄清项定稿」Q1）。

## 已排除的假设

| 假设 | 排除依据 |
| --- | --- |
| 「mmap 绕过 SMB 客户端缓存」 | 独立 mmap 读 80 MB 仅 108 ms，与 FileStream 同速 |
| 「只有第一次过滤慢」 | 用户确认每次都慢；复现 1/2/3/4 趟均慢 |
| 「IO 带宽饱和」 | 缓存热态下顺序读全文件 51 ms，过滤仍 16.8 s |
| 「客户端缓存没生效」 | 顺序读二次 0.19 s（908 MB/s），缓存生效 |
| 「真实 moff 跨页率放大页故障」 | 实测跨 4 KB 页率仅 1.1%（30,623 / 2,719,107）；真实 moff 与近似 moff 逐行读耗时无差异（240 / 164 / 176 ms） |
| 「网络路径本身的读放大」 | F（case 敏感）同文件全量读字节仅 0.24 s |
| 「回退行数就是耗时主因」 | 744,922 × 0.34 μs ≈ 0.25 s，与 17.4 s 相差约 70 倍；只有「8 KB × 行数 ≈ 16.2 GB」与实测吻合（见「复核算术」） |

## 修复方案（定稿，2026-10-23 维护者拍板 Q3 = 方案 1）

**修复本体（最小切片）**：
- `FoldLowerAsciiInPlace` 增加 `Span<byte>` 重载（现 `byte[]` 版本按 `buf.Length` 全量扫描）；
- 调用点改为 `FoldLowerAsciiInPlace(scratch.AsSpan(0, msgBuf.Length))`，匹配切片同步用 `msgBuf.Length`；
- 一条改动同时消掉主因（扫描量从「容量」回落到「行内字节」）与次因（回退率回到数据下限 10.8%）。

**备选形态处置**：方案 2（删 scratch、对 `msgBuf` 原地折叠）已核查无破坏面、结构更净（省每趟 ~176 MB 拷贝 ≈ 20 ms），但本次不做，**记为可选后续优化另议**。

**行为不变**：命中数在全部对照实验中全等；修复只改变「扫描了多少字节」与「回退触发率」，正确性路径（含 ßẞ、İı 等长宽变化规则的 Unicode 回退）保持原样。

**性能预期**：复现环境 17 s → ~0.5 s（实测 H = 516 ms）；用户环境 1.7 s → 0.1~0.2 s 量级（按其 1.4M 行 × 行内字节折算），剩余成本是 mmap 页读与每行分配。

**不需要的防护**：修复后单行成本与缓冲区容量无关，故不必给 scratch 设容量上限，也不必为「出现超长行」加特殊处理。

**连锁作废**（方向性结论）：
- 「网络文件本地缓存」整套方向作废——瓶颈从来不是传输；
- 「块读」重评作废——跨页率仅 1.1%，读路径无问题；
- `FilterEngine` 现状逻辑（BATCH 分批、进度上报、取消检查）实测均不是瓶颈，无需改动。

## 环境备忘（可复用）

- **回环 SMB 不能用于独立进程的 SMB 测试**：`\\127.0.0.1\share` 与 `\\本机名\share` 能列目录，但 `CreateFileW` 返回 `win32=65`（ERROR_NETWORK_ACCESS_DENIED）、`WNetAddConnection2` 返回 `rc=5`；同一 PowerShell 宿主内读文件却成功——差异在进程凭据上下文。真实远程共享无此问题。
- **子进程传 UNC 路径会被 shell 反斜杠转义吃掉** → 探针类工具应把路径写死在代码里或用开关选择。
- **`Add-Type` 被安全策略拦**（运行时编译 .NET 代码）；`.ps1` 脚本被执行策略拦 → 「在 PowerShell 宿主内跑 C# 探针」走不通。
- **仓库自带真实日志** `testdata/big_test.log`（1.07 GB / 1783 万行，真实 threadtime 格式，含中文）→ 截取前 N MB 即可造出同构测试文件。
- **探针工程 csproj 用 `EnableDefaultCompileItems=false` 显式枚举源文件** → 新增 .cs 文件须手动加 `<Compile Include>`，否则静默跑旧二进制。
- **scratch 容量只按 2 的幂翻倍**（`new byte[Math.Max(len, cap*2)]`）→ 讨论「缓冲区多大」时不要用非 2 的幂估计。
- **折叠循环吞吐 ≈ 1 GB/s**（由 A/B 反算）→ 估算「按容量扫描」的成本时可直接用这个数，不必实测。
- 探针（`.tmp-test/realprobe/`）不入库；本笔记结论的数据可由探针复跑。
