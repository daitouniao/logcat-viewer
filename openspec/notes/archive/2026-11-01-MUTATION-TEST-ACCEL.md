# 变异测试加速探索（MUTATION-TEST-ACCEL）

> 状态：探索中（A+B 方向已定，待立项；未动代码）
> 日期：2026-10-31
> 关联：`scripts/mutation-test.py`、`docs/UT-AUDIT.md`、`docs/TESTING.md`

## 1. 问题

变异测试全程 ~35 分钟（105 个变异点），慢在哪、能否加速。方向已定为 **A（两级测试选择）+ B（失败即停）**。

## 2. 现状结构（事实）

`scripts/mutation-test.py` 串行执行 105 个变异点（TEXT 95 + LINE 10），每个变异：

```
改写 Services/*.cs 源文件（原地，内存备份 → 跑完写回）
  → dotnet run -c Release --no-restore（%TEMP%/tstrun）
      = MSBuild 增量编译（主工程 → Tests → tstrun 三工程链式重编）
      + 全量测试（tstrun 口径 ~750 条）
  → 写回原文件
```

## 3. 实测耗时拆分（事实，2026-10-31 本机，Release）

| 环节 | 实测 | 占比 |
|---|---|---|
| `dotnet build` 无变化空转（CLI 启动 + 3 工程 MSBuild 评估） | 2.8s | ~15% |
| 有源码变更时 3 工程链式重编 | ~2s（推算，见 §6） | ~10% |
| **纯测试运行（`--no-build`）** | **14.7s** | **~75%** |

- 单轮变异 ≈ 19~20s，105 点全程 ≈ **35 分钟**。
- 交叉印证：UT-AUDIT 记录 10-05 那轮 15 分钟，当时用例数 ~370；现 ~750 条，时间翻倍，量级吻合。
- **大头 = 每个变异都跑全量测试（~75%），编译开销合计仅 ~25%。**

## 4. 探针结果（事实，2026-10-31，均 `--no-build` 不触发编译）

**探针 1：类名过滤的子集运行耗时**（方案 A 第一级成本的实测）：

| 子集 | 耗时 |
|---|---|
| `FilterEngineTests` | 1.6s |
| `LogDocument*`（3 个类） | 2.0s |
| `LogParser*` | 1.5s |

结论：第一级子集单轮 **~2s**（含 ~1s CLI/MSBuild 空转），对比全量 14.7s，方案 A 的核心假设成立。

**探针 2（未做，需授权）**：真实变异触发的 3 工程重编耗时。需临时改动一个 Services 源文件（与变异脚本同机制，跑完写回），预算影响 ±3s/轮，价值低，建议不跑。

## 5. 方案 A+B 设计（待评审）

### 5.1 流程

```
每个变异：
  按映射取 tier-1 测试类子集，跑（~2s）
    ├─ 有失败 → KILLED（失败即证明咬住；B：首败即停，不跑完子集）
    └─ 全过   → 回退跑全量（~15s）
          ├─ 有失败 → KILLED（杀手在映射外的类里，映射要补）
          └─ 全过   → SURVIVED（全量口径，可信）
```

### 5.2 正确性约束（不可妥协）

- **KILLED 判定只会提前、不会失真**：子集失败 = 有用例咬住，语义与全量等价。
- **SURVIVED 必须全量确认**：子集全过不能直接判存活，否则引入假 SURVIVED。
- tier-1 无映射或映射的类不存在（漂移/改名）→ **安全失败，直接全量**，不猜。

### 5.3 预算（估）

固定 ~5s/轮（CLI + 编译）+ tier-1 ~2s；KILLED 在子集命中时 ~7s/轮，映射外回退 ~22s/轮。
按历史 KILLED 率 ~97%、90% 在子集内命中估：全程 35 → **~15 分钟**。B 再压缩其中失败较晚的部分。

### 5.4 依据（事实）

- UT-AUDIT：每个变异通常只被 1~3 条用例抓住，历史 KILLED 率 ~97%（103 点 102 KILLED）。
- tstrun 原生支持类名过滤参数（`dotnet run <类名子串>`），探针 1 已验证耗时。
- 测试类命名规整（`<X>Tests` / `<X>*Tests`），映射可推导。

### 5.5 B（失败即停）的具体形态

runner 循环里首个失败后停止调用后续用例，输出保持 `passed: X failed: Y skipped: Z` 同一行格式（只提前退出），脚本解析逻辑不变。**启用方式已定：环境变量开关（`TSTRUN_FAIL_FAST=1`），默认行为不变**（change design D2）。runner 位于 `.tmp-test/tstrun`（git-ignored），其源码模板记录在 TESTING.md §3.1——**改 runner 必须同步更新该模板**，否则 runner 重建后改动丢失；改后必做 756 条交叉验证（TESTING.md §3.2 坑 3）。

### 5.6 不做的

- 方案 C（多 worker 并行）：worktree 上 runner 指错仓库会全报假 SURVIVED，工程量大，A+B 后预计已够用，留作后续。
- `dotnet run` → 直调 `tstrun.exe`：省 ~1s/轮，不值得。

## 6. 猜测（显式标注）

- 「3 工程链式重编 ~2s」是从 build 实编（4.8s，可能含重编）与空转（2.8s）的差值推算，**未单独实测**（探针 2，见 §4）。
- 「90% KILLED 在子集内命中」是按 M1~M9 等历史记录的推断，**未实测**；实际比例影响预算在 ±5 分钟内，落地时脚本输出各级占比即可事后校准。
