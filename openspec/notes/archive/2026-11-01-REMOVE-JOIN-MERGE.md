## 1. 要做什么

现在的索引里，一条「记录」是一个**逻辑事件**：一条日志后面若跟着若干缩进续行（最常见的是崩溃堆栈），这些行会被折叠进同一条记录，列表里看到的是一条。

要改成按**自然行**建索引：文件里每一行（空行与横幅行除外）各自成为一条记录，各占一行，不再合并。

```
现在（join=true）                改后（join=false）
─────────────────────────       ─────────────────────────
[行1] 崩溃头                     [行1] 崩溃头
[行2]   at Foo.bar    ← 折叠      [行2]   at Foo.bar
[行3]   at Foo.baz    ← 折叠      [行3]   at Foo.baz
─────────────────────────       ─────────────────────────
1 条记录，3 行物理行              3 条记录，3 行物理行
```

「自然行」的准确口径：**除空行与横幅行（`----- beginning of main` 之类）外的每一行**。空行与横幅行仍然不索引 —— 这跟 join 无关，是它们本身的性质。

## 2. 好处

1. **少一整套机制**。合并、跨块续行、末条滞后发布、跨块等价性，这一整套规则及其配套的坑全部消失，预计净减约 200 行代码、9 个变异测试锚点。
2. **在途的 `chunked-progressive-load` 大幅简化**。该 change 目前 0/13 未开工，它的 carry 语义、末条滞后发布、跨块等价性陷阱全部建立在 join 上。此刻动手最便宜。
3. **行号语义稳定**。join 开关一开一关，同一份文件的行号完全不同；删掉后行号只由文件内容决定。

## 3. 代价（三条，都要认）

### 3.1 记录数涨 11.3%，sidecar 与内存跟着涨

样本 `testdata/big_test.log` 实测：

| 口径 | 数值 |
| --- | --- |
| 物理行（LF 计数） | 17,832,235 |
| 空行 / 横幅行（不索引） | 22 / 0 |
| 现在的记录数（join=true） | 15,823,120 |
| **被合并掉的行** | **2,009,093（物理行的 11.27%）** |

真实 SMB 日志同比例：3,063,986 物理行 → 2,719,107 条记录 → 合并 344,879 行 = 11.26%。**任何含无头续行的日志都会涨约 11%**，不是样本的特例。

由此：

| 形态 | 行数 | 段宽 | sidecar 体积 | 相对现状 |
| --- | --- | --- | --- | --- |
| 现状（join=true，9 段） | 15,823,120 | 31 B | 0.4568 GiB | — |
| 删 join，9 段 | 17,832,213 | 31 B | 0.5148 GiB | **+12.7%** |
| 删 join，8 段（见 R1） | 17,832,213 | 30 B | 0.4982 GiB | **+9.1%** |

内存同理（列数组宽度同 sidecar）：490 MB → 535 MB（8 段，+45 MB）或 553 MB（9 段，+62 MB）；chunked 基线峰值 663 MB → 约 708 MB，仍在 1.0 GB 预算内。

sidecar 1 GiB 上限对应口径：现状「约 34.6 M 记录」→ 改后「约 35.8 M 自然行」。

> 注：上表「9 段 / 31 B」一行已作废 —— R1=A（一次清掉，含 flags 列）+ §9①=B（信号位不预留）定为 **8 段 / 30 B**，以「8 段」一行为准；sidecar 尚未实现（§5.1.1），此处只是未来列定义与体积公式的口径。

### 3.2 约 11% 的行在「元数据类过滤」下不命中（**原句偏重，真实命中口径以 §3.2.1 为准**）

那 2,009,093 行今天被并进父记录，没有自己的身份。删 join 后它们各自成记录，但解析不出元数据：`Lvl=0`、`Pid=-1`、`Tid=-1`、`Minute=255`（哨兵）、`TagId=-1`。

于是 **level / pid / tid / minute / tag 五类过滤全部不命中它们**（`FilterEngine` 的级别集合取自 `LogParser.ALL_LEVELS={1..7}`，不含 0；分钟哨兵 255 永远不在 0–59 内）。只有「不加元数据过滤」或「排除模式」能看到它们。

按 message 关键词过滤不受影响 —— 它们的正文照常参与匹配。

### 3.2.1 复核订正（2026-10-31）：元数据过滤的真实命中口径

原文「level / pid / tid / minute / tag 五类过滤全部不命中」偏重。以现码为准逐条核对（`Services/FilterEngine.cs:785-833` 全量路径、`:856-893` 增量路径）：

| 类别 | 哨兵 | 实际匹配 | 对无元数据行的结论 |
| --- | --- | --- | --- |
| level | `Lvl=0`（`LogParser.LVL_UNKNOWN`） | `filterLevels` 只在「勾选级别集合 ≠ 全部 7 级」时才成立（`FilterEngine.cs:792`/`:862`）；UI 默认全选 V/D/I/W/E/F/A（`frmMain.cs:459`、`:1282`、`:1303`） | **默认可见**；只有用户取消勾选某些级别时才被丢弃 |
| pid | `-1` | `hit = pidSet.Contains(-1)`，包含模式丢弃 / 排除模式**保留**（`:805-809`） | 启用 pid 过滤时才不命中；排除模式下反而保留 |
| tid | `-1` | 同 pid（`:811-816`） | 同 pid |
| minute | `255`（`LogDocument.MINUTE_NONE`） | 分钟值取自**时间戳文本的 mm 字段**（`LogParser.cs:264`/`:299` → `ParseResult.Minute` → `LogDocument.cs:609`），哨兵 255 不可能是分钟集合成员 | 启用分钟过滤时天然不命中 |
| tag | `-1` | `tagIds.Contains(-1)`，且 tag 需先在 tag 字典里命中（`:829-833`、`TagIds` `:104-130`） | 启用 tag 过滤时天然不命中 |

两点必须纠正的旧认知：

1. **不是「(ts/60000)%60」**。分钟来自时间戳文本的 mm 字段；`within`（毫秒时间戳）只用于 `HeaderBytes` 与显示。`docs/private/notes/LEAP-SECOND-MINUTE-FILTER-EDGE.md:14` 的旧描述与现码不符，不作依据。
2. **默认状态下这 11% 的行照常可见**。只有在用户主动启用 pid / tid / 分钟 / tag 过滤时它们才被丢弃；level 只在用户取消勾选某些级别时才被丢弃。

**结论**：D2「接受约 11% 的行在元数据类过滤下不可见」的**决策不变**（接受本身没问题），但**影响面比原描述小得多**，spec 措辞与验收基线必须按本节口径写，不能沿用 §3.2 原句。

### 3.3 「多行正文整体参与匹配」的能力消失

主规范 `openspec/specs/message-filter/spec.md:12` 现在写的是「多行记录 SHALL 以合并后的完整正文参与匹配」。删 join 后不存在「跨行的那条记录」，续行内容只属于它自己那一条。

范围要说准，比「能力消失」轻：

```
threadtime（主流格式）：堆栈行自带时间戳 + 级别 + tag
  → 删 join 后堆栈行是独立记录，元数据完整
  → 按级别 / tag / 关键词过滤堆栈【仍然找得到】
  → 命中的不再是「崩溃头那条记录」，而是「堆栈行那条记录」

无头续行（brief / long 的堆栈行、样本里的 resize 737x737 一类）：
  → 无元数据，上一条 3.2 的规则适用
```

**崩溃堆栈在详情里不可见**：这条不是新增回退。threadtime 的崩溃块里 `Process:` / 异常类型 / `at …` 每一行都自带时间戳头，今天就是各自独立的记录，「查看完整记录」今天也只返回崩溃头那一行。真正受影响的只有**无头续行**形态。

### 3.4 复核订正（2026-10-31 第三轮）：崩溃提取（a 轨）**不受**删 join 影响

原稿与第一轮复核都说过「『崩溃头缩进并入父记录』这一形态的崩溃事件在删 join 后不再产生（c 轨补扫整段变死代码）」——**这个说法过重，是错的**。查证过程：

- a 轨的文本来源是 `LogDocument.ExtractCrashAt(data, lineOff, lineLen, msgOff, lookFrom)`（`Services/LogDocument.cs:729-760`）：本行 msg + **最多 3 次前瞻**，前瞻读的是**文件缓冲区里的后续物理行**（`Array.IndexOf(data, '\n', q)` 逐行推进），**不是合并记录内部的字节**。
- 调用点传的是 `pos`（`LogDocument.cs:638`），而 `pos` 在该处仍是**当前物理行的起点**（`pos = nl + 1` 要到 `:659` 才推进）⇒ 前瞻窗口实际覆盖「本行 + 其后 2 个物理行」，`TryJava` 在 `head+1..head+3` 里找 `Process: ` 行（`Services/CrashExtractor.cs:86-95`）恰好够用。
- 结论：**join 开关不参与崩溃提取**，删 join 后 a 轨读到的字节完全相同 → 崩溃事件的识别、异常类型、包名、PID/TID **一律不变**。

「崩溃头缩进并入父记录」这一形态（崩溃头本身是上一条记录的缩进续行）今天是这样被捞出来的：a 轨在扫描时该行走 join 分支 `continue` 了、根本进不了「新记录」分支 → 只能靠 c 轨批末补扫（`LogDocument.cs:683-706`，依赖 `FLAG_MULTILINE`）从合并文本里再提一次。删 join 后该行成为**独立记录** → a 轨直接命中 → **事件照常产生**，且不再依赖 c 轨兜底；c 轨整段可删。

所以准确的口径是：

| 事项 | 删 join 后 |
| --- | --- |
| 崩溃事件**识别**（类型 / 包名 / PID / TID / 崩溃头行号） | **不变**（a 轨不看 join） |
| 「崩溃头缩进」形态的事件 | **照常产生**（由 c 轨兜底改为 a 轨直取），不再是「不再产生」 |
| 崩溃块的**续行内容归属** | 变：不再并入崩溃头记录（详情里只剩崩溃头一行）—— 这才是决策 ① 接受的回退 |
| `CrashEvent.Row` | 恒为崩溃头所在行（今天的「父行」在缩进形态下本来就是崩溃头行，语义等价） |
| 崩溃汇总的 group 行范围 | 恒为崩溃头行（`CrashAggregator` 不读 `LineCount`，不受影响） |

### 3.5 复核订正（2026-10-31 第四轮）：规范面已有的「无元数据行」契约只有 minute 一条

- `openspec/specs/time-column/spec.md:10` 早就写着：「行首无有效时间戳的记录…SHALL 存储一个不可能是分钟值的标记，**分钟过滤激活时视为不命中**」，并配了 Scenario「无时间戳记录不命中」。
  → **minute 类的「无元数据行不命中」契约已经在规范里**，本次新增需求不必复述它。
- level / pid / tid / tag 四类过滤在 `openspec/specs/` 下**一条规范都没有**：7 个 capability 里只有 `message-filter` 讲过滤且只讲 message，`time-column` 顺带覆盖 minute。
- 删 join 后「无时间戳记录」的**构成显著变大**：今天被并进父记录的那 200 万条无头续行里，只有**父记录**算「无时间戳记录」；删 join 后它们各自成为独立记录 ⇒ **每一条都是「无时间戳记录」**。
  → time-column 的**规则一个字都没变**（仍是「无时间戳 ⇒ 分钟过滤不命中」），只是适用集合从约 0.6% 变成约 11% ⇒ **time-column 不需要改**，但 design 里必须写清这一点。
- 一处措辞陷阱：`message-filter` 现有 Requirement「message 的排除语义」写的是「**缺失正文**的记录 SHALL 一律视为未命中并被保留」——「缺失正文」与「无元数据」是**两回事**（无头续行有正文，只是没有头部元数据）。新需求的措辞**不能用「缺失正文」来表达**，否则与现有 requirement 打架。

**② 「索引耗时 ≤ 现状 × 1.15」里的「现状」基线怎么取？**

- 倾向：**A** —— 跨探针跨条件的秒数不可比；同机同探针现测才能把「扫描量 +12.7%」和「代码变慢」区分开。

**③ 在途 `chunked-progressive-load` 要不要留一行「前提已变」的标记？**

**① 已失效的行号型变异锚点怎么办？（原「行号漂移」问题 + 第六轮核对的既有事实）**

`scripts/mutation-test.py` 有两类变异：文本替换型（按「旧文本」精确匹配）与**行号型**（`LINE_MUTATIONS`，按「行号 + 该行内容」双重校验）。行号型漂移后内容校验不符即 `SKIP` —— 静默跳过、不报错，等于该测试点没在跑。第六轮逐条核对（2026-10-31）：
