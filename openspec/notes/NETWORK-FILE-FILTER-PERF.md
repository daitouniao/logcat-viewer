# 探索结论：网络路径文件过滤慢 —— 根因定稿：MsgFilter scratch 缓冲污染（与网络无关）

- 状态：**根因定位完成，方案方向定稿：纯 bug 修复，走 OpenSpec change**（2026-10-23）
- 日期：2026-10-22 探索；2026-10-23 根因闭环
- 关联提交：无（探索阶段，未改动仓库代码）
- 验收结论：待定

## 结论摘要

用户诉求：打开网络驱动器（网上邻居）上的日志文件后，**每次**修改 message 过滤关键字都要 ~1.7 s（176 MB / 140 万行）；加 tag 过滤则很快、命中数相同。问是否最近改动引起。

最终结论（三点，均有实测支撑）：

1. **不是回归**。过滤热路径（`MsgFilter` / `MessageBytes` / mmap 打开）自首次提交起未变；期间对过滤的改动都是加速（消除逐行编解码、移除用户正则）。
2. **与网络完全无关**。真凶是 `MsgFilter` 的一个 CPU 侧 bug：大小写不敏感过滤时，ASCII 折叠判定**扫的是整个 scratch 缓冲（含历史残留字节）而非当前行**，导致含中文日志文件的大量行走上昂贵的 Unicode 折叠回退。瓶颈是纯 CPU，本地文件同样会慢。
3. **修复面极小**：`FoldLowerAsciiInPlace` 增加 `Span<byte>` 重载，调用点改为按 `msgBuf.Length` 切片折叠。实测同环境 17.4 s → 0.5 s（约 34 倍），命中数不变。

「tag 过滤快」的解释：`TagIds` 只读内存字典、不碰 message 字节，从而完全不进入这条出错路径；加了 tag 条件还会缩小候选集，进一步减少回退行数。

## 根因机制

```
MsgFilter（Services/FilterEngine.cs，大小写不敏感路径）
├─ scratch = new byte[1024]              ← 只增不减
├─ 每行: Array.Copy(msgBuf → scratch)    ← 只覆盖前 msgBuf.Length 字节
├─ FoldLowerAsciiInPlace(scratch)        ← 缺陷：遍历 scratch.Length（整个缓冲）
│    残留区留有之前中文行的字节 ≥ 0x80 → 返回 false
│    → 本行（哪怕纯 ASCII）走 GetString→ToLowerInvariant→GetBytes 回退（~4.5 μs/行）
└─ 一旦出现 >1024 B 的长行，scratch 扩容至 ~5.6 KB
     残留区几乎长期含非 ASCII → 回退率被放大数倍
```

- 文件真实含非 ASCII 行占比 10.8%（292,737 / 2,719,107），本应只有这些行走回退；
- 污染后实际回退 744,922 行（27.4%），且每次过滤都复现（与缓存冷热无关）；
- 回退本体 ~4.5 μs/行 × 数十万至百万行 → 用户环境的 1.7 s 与复现环境的 13~19 s 同源。

## 方案定稿

**修复**（预期一处调用点 + 一个重载）：
- `FoldLowerAsciiInPlace` 增加 `Span<byte>` 重载（现 `byte[]` 版本按 `buf.Length` 全量扫描）；
- 调用点改为 `FoldLowerAsciiInPlace(scratch.AsSpan(0, msgBuf.Length))`，匹配切片同步用 `msgBuf.Length`。

**行为不变**：命中数在全部对照实验中全等；修复只改变回退触发率，正确性路径（含 ßẞ、İı 等长宽变化规则的 Unicode 回退）保持原样。

**性能预期**：复现环境 17 s → ~0.5 s；用户环境 1.7 s → ~0.1 s 量级（网络剩余成本仅为 mmap 页读）。

**连锁作废**（方向性结论，随根因定稿一并失效）：
- 「网络文件本地缓存」整套方向作废——瓶颈从来不是传输。2026-10-22 拍板的缓存目录 / 关闭即清 / 默认走缓存等 5 条决策随之失去对象，不再执行；
- 「块读」重评作废——跨页率仅 1.1%，读路径无问题；
- `FilterEngine` 现状逻辑（BATCH 分批、进度上报、取消检查）实测均不是瓶颈，无需改动。

## 环境备忘（可复用）

- **回环 SMB 不能用于独立进程的 SMB 测试**：`\\127.0.0.1\share` 与 `\\本机名\share` 能列目录，但 `CreateFileW` 返回 `win32=65`（ERROR_NETWORK_ACCESS_DENIED）、`WNetAddConnection2` 返回 `rc=5`；同一 PowerShell 宿主内读文件却成功——差异在进程凭据上下文。真实远程共享无此问题。
- **子进程传 UNC 路径会被 shell 反斜杠转义吃掉** → 探针类工具应把路径写死在代码里或用开关选择。
- **`Add-Type` 被安全策略拦**（运行时编译 .NET 代码）；`.ps1` 脚本被执行策略拦 → 「在 PowerShell 宿主内跑 C# 探针」走不通。
- **仓库自带真实日志** `testdata/big_test.log`（1.07 GB / 1783 万行，真实 threadtime 格式，含中文）→ 截取前 N MB 即可造出同构测试文件。
- **探针工程 csproj 用 `EnableDefaultCompileItems=false` 显式枚举源文件** → 新增 .cs 文件须手动加 `<Compile Include>`，否则静默跑旧二进制（本次踩过：exe 输出与源码不符）。
- 探针（`.tmp-test/realprobe/`）不入库；本次结论的数据可由探针复跑。
