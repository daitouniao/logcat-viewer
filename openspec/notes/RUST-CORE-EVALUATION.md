## 0. 一句话结论

技术上可行，边界收敛后成本可接受；**但它买到的不是「过滤更快」**——过滤已贴内存带宽地板。真实收益是内存峰值可控、并行建索引更容易、Core 与 UI 的边界被语言强制切开、以及 MCP 侧可获得无运行时的小二进制。决策前置是一次 1 GB 对拍探针。

## 1. 诉求与定位

维护者提出三条诉求，按优先级：

1. **性能**：打开大文件与过滤仍不够快；
2. **逻辑与显示混合**：引擎代码与 UI 同处一个工程，职责不清；
3. **MCP 反正要重建 core，不如一起**。

关键定位：`logcat.Core` **尚不存在**（MCP 卡 D1 已定其为独立工程、TFM 目标 `net10.0`，但工程未建；阶段 0 `logcat.UiCore` 已由拆分卡落地）。因此本轮不是「把已存在的 C# Core 换成 Rust」，而是**在零迁移成本窗口内为尚未创建的 Core 选语言**。

范围进一步收敛为维护者明确的**两件事**：

- **建索引**（含连带项，见 §4）
- **过滤并给出结果**（行索引）

## 3. 现状性能基线（历史实测记录，本轮未复测）

> 下列数字来自已归档的探索笔记与现存规范：归档笔记已冻结、按 AGENTS §3.2 不作引用依据，此处仅作量级参照；**阶段 0 必须重新采集同一口径**，不得直接以本表作为判据。

| 项 | 数字 | 来源 |
| --- | --- | --- |
| 过滤 case-sensitive | 453–692 ms | `UTF8-BYTE-SIMD-SEARCH` 探针（零拷贝落地后刷新） |
| 过滤 case-insensitive | 945–1270 ms | 同上 |
| 全文顺序扫地板（不可再低） | 149–160 ms | 同上 |
| 块扫描并行 + SIMD（探针目标形态） | 133–151 ms | 同上 |
| sidecar 重开 | 459 ms（验收线 600 ms） | `sidecar-index-cache` 规范正文 |
| 分块加载全程（36.56 MB 样本） | 1.15 s | `CHUNKED-TAIL-LOSS` 探针 |

**物理边界**：过滤一次 1 GB 必然要读 1 GB 字节，10 GB/s 量级带宽下地板已在 100–150 ms，**换语言不改变「要读多少字节」**。故 §3 表中「过滤更快」不是 Rust 的收益来源。

## 4. 已定范围（本次探索结论）

Rust 内核承担（连带的都是「建索引」的天然组成，不是新增功能）：

```
 Rust (native kernel, cdylib)                       C# (展示层)
+-------------------------------------+      +--------------------------------+
| logcat 行解析（多格式自动识别）      |      | Loc / 进度文案 / i18n          |
| 9 列索引 + 容量增长 + 增量追加       |      | 虚拟列表渲染 / 列格式化        |
| tag 字典 intern                     |  <-> | 选中复制 / 导出                |
| 崩溃 / ANR 打标（索引期，父行）      | FFI  | sidecar 序列化与身份校验       |
| 编码探测（UTF-8 / GBK）             |      | 设置 / ADB / FileProxy         |
| 全量过滤（块扫描 + SIMD + 归属复核） |      | MCP JSON 薄壳                  |
| 增量过滤（FilterTail）              |      | 崩溃聚合分组（展示统计）       |
+-------------------------------------+      +--------------------------------+
        100% 的 CPU 热点                              几乎不含 CPU 热点
```

**归 Rust**（维护者已拍板，2026-11-07）：崩溃/ANR 打标、编码探测、增量追加与增量过滤。

**不归 Rust**：sidecar 序列化（可后移，见 C2）、文本呈现、`Loc`、UI、ADB / FileProxy、MCP 的 JSON 契约。

**连带效应（正面）**：容量增长改由 Rust 显式管理，现有构建期 LOH 瞬态（历史排查为「连开多文件内存上涨」的机制）从结构上消失；增量追加不再需要 9 处 `Array.Resize` 与新旧数组并存。

## 5. 接缝：文本归谁（待 design 定稿）

唯一决定 FFI 契约形状的决策，比语言本身更关键。

| 方案 | 内容 | 取行文本 | 代价 |
| --- | --- | --- | --- |
| **A（推荐）** | Rust 拥有 mmap + 索引；C# 通过 `text_base()` / `col_ptr(k)` 拿只读切片 | **零 FFI、零拷贝**：`base + offs[i]`，长度 `lens[i]` | 跨语言裸指针生命周期；append 触发 remap 后基址失效 |
| B | C# 拥有 mmap 与列数组；Rust 为纯函数，写入 C# 提供的缓冲区 | 零拷贝（C# 自有基址） | 容量估算/扩容/LOH 瞬态问题原样保留 |
| C | Rust 拥有索引列，C# 拥有 mmap，指针互传 | 零拷贝 | 两个长期存活的外部指针，关闭顺序最脆弱 |

推荐 A 的决定性理由：**C# 取行文本时完全不走 FFI**，只在文档打开时取一次基址，导出 / 复制全文 / 滚动绘制都不会被边界拖慢。现有代码已有 `AcquirePointer` + 退役旧映射的处理经验，属于「已知风险 + 已有对策」。

append 的 remap 有两种收法（design 阶段二选一）：

- 暴露 generation 计数，C# 在追加后重新取址；
- 可变尾部区域与不可变主体**分开映射**，主体基址永不失效。

生命周期不变量（必须进 design）：关闭顺序固定为「停过滤 → 释放 Rust 句柄 → 释放映射」，任何 C# 切片不得跨句柄关闭存活。

## 6. 收益 vs 成本

| 维度 | Rust 相对 C# 现状 | 说明 |
| --- | --- | --- |
| 全量过滤 | **≈0** | 已贴带宽地板（133–151 vs 149–160 ms） |
| 增量过滤 | ≈0 | 逐行复核，非扫描 |
| 建索引（当前单线程） | **大，但语言无关** | 并行化即可；C# 用 `Parallel` + 现成 `ScanPart`/`Assemble` 同样能拿 |
| 建索引内存峰值 | **真赢** | 显式缓冲、无 LOH 倍增 |
| GC 抖动 | 小赢 | 热路径本来就零分配 |
| 边界解耦 | 真赢（强制） | 语言墙让 `Loc` / UI 依赖无法回流 |
| MCP 分发体积 | 赢（仅 MCP 侧） | 单二进制 2–5 MB，无需运行时；GUI 仍带 .NET |
| 维护成本 | **净负** | 双工具链 / 双测试栈 / 双 CI（GitCode + GitHub）/ 双包都要带 native 依赖 |

净账的准确表述：**用「重写引擎」买「内存峰值 + 并行解析 + 边界强制 + MCP 体积」，不买「过滤更快」**。

## 7. 迁移对拍契约（验收面）

迁移期以现 C# 实现为 oracle，双实现只存在于测试工程、不进产物。必须逐位一致：

1. 9 列逐位一致（含 `moff` 续行、`min` 哨兵、`tagId` intern 顺序）
2. 过滤结果集合逐位一致：区分/忽略大小写、混合大小写、多关键词（≤8 与 >8 两条分派路径）、排除
3. Unicode 小写化口径对齐：`ß / ẞ`、土耳其有无点 `i` —— Rust `to_lowercase` 与 C# `ToLowerInvariant` 需实测比对
4. 块扫描跨块重叠（最长关键词字节数 − 1）与起始位置归属去重不漏匹配
5. 分块加载 ≡ 整份加载逐位一致；增量 ≡ 全量一致
6. sidecar 身份校验与列布局不变（否则旧缓存全废）
7. 进度上报节流与取消粒度不退化（UI 感知）
8. 崩溃打标在父行的约定不变；增量追加路径同样打标

## 8. 建议路径与判据

```
阶段 0  量化探针：1 GB 上 Rust 并行建索引 vs C# 并行建索引原型
        同时验证方案 A 的 text_base() 零拷贝在千万行下的可用性
阶段 1  决策：按数据选定 Core 语言，锁定 Core 对外契约形状
阶段 2  既定计划推进：core-extraction -> mcp-server（MCP 卡 D2 顺序）
阶段 3  仅当选 Rust：引擎换实现，C# 只换适配层
```

**建议判据**（阈值为建议值，非既有约定）：

- C# 并行建索引若把每 GB 压到个位数秒且峰值显著下降 → 性能项对 Rust 的诉求归零，留 C#；
- Rust 原型若同口径快 ≥25%、且峰值与 FFI 开销可接受 → 值得整体迁移。

顺序理由：`core-extraction` 的边界形状**取决于语言**——C# Core 暴露对象，Rust Core 必须暴露 C ABI + 批量取文本接口。语言必须先定，否则 C# Core 会被写两遍。

**不合并成一个大 change**：MCP 卡 D7 已明确「工程结构 + 对外 API + 解析抽象」同批改会评审面过大。一起做的应是**决策**，不是**实施**。

## 10. 待澄清

### C1 语言决策时点 vs 既定顺序（阻塞 propose）

- **为什么需要澄清**：`BACKLOG-MCP-AND-FORMATS.md` D2 已倾向 `core-extraction` 先于 `mcp-server`；若语言未定就抽 C# Core，之后转 Rust 等于 Core 写两遍。
- **有哪些方案**：甲 阶段 0 探针后立刻定语言，再抽 Core；乙 先抽 C# Core、MCP 落地，Rust 留到更远；丙 直接定 Rust、跳过探针。
- **当前偏向**：甲。

### C2 sidecar 序列化归属

- **为什么需要澄清**：sidecar 格式是 9 列 + 身份校验的落盘索引，恰在 Rust 索引的所有权边界上；留 C# 则需通过切片读出再序列化，迁 Rust 则 FFI 面变大。
- **有哪些方案**：甲 留 C#（最小迁移面）；乙 随 Rust（一次写盘，少一次全列遍历）；丙 先留 C#、稳定后再评估。
- **当前偏向**：丙（本轮不扩面）。

### C3 DLT 等二进制格式的解码归属

- **为什么需要澄清**：DLT 解码产出文本行再走索引；若 Rust 建索引，解码在 C# 则需先落文本再喂 Rust（多一次写盘），在 Rust 则扩大内核面。
- **有哪些方案**：甲 解码留 C#（Rust 只吃文本字节）；乙 解码入 Rust；丙 等 DLT 真正落地时再定（`DLT-INTEGRATION.md` 已有独立 change 规划）。
- **当前偏向**：丙，本轮标为范围外。

### C4 过滤结果的形状

- **为什么需要澄清**：现状返回 `int[]` 行索引；但状态栏与虚拟列表还需要各维度计数、`markedOnly` 语义、崩溃行的展示摘要。
- **有哪些方案**：甲 仅返回行索引，计数由 C# 侧遍历（现状口径）；乙 返回行索引 + 各维度计数（一次遍历出全量信息）；丙 返回位图压缩（更省内存、导出变慢）。
- **当前偏向**：乙，需在 design 阶段与 UI 实际消费点核对后定稿。
